# Fixed Bugs Log

A changelog of bugs that were tracked in `docs/KNOWN_BUGS.md` and have since been fixed. `KNOWN_BUGS.md` only ever holds *open* items — an entry is removed from it outright the moment it's fixed, not marked done in place — so this file is where the record of "what it was and when it got fixed" lives instead. Git history has the exact diffs; this is a scannable index into that history, one entry per fix, newest first.

## 2026-09-25

### fix: address gaps an ultrareview of the single-writer-tab/sync branch caught
- Cloud ultrareview of the `dev` branch (single-writer-tab work) found six real issues, all fixed:
- **Read-only tab's auto-sync threw instead of failing cleanly:** `sync-engine/index.ts`'s `sync()` called `push()`/`pullChanges()` unconditionally, which throw mid-sync via `core.ts`'s `assertWritable()` as soon as a read-only tab has anything to push/pull, surfacing as a misleading "Sync failed. Check your connection." Gated `sync()` on `isWriterTab()` (mirroring the impersonation check already there), and `sync-indicator.tsx`'s manual button + auto-sync daemon now skip entirely while `isReadOnlyTab` is true instead of flashing an error state every interval.
- **Broken-formula import produced literal "[object Object]":** `product-import-export.ts`'s `cellPlainValue()` had no branch for ExcelJS's error-cell shape (`{error: '#REF!'}`, or nested in a formula's `result`), so it fell through to `String(value)`. Added an `error` check and made the `result` branch recurse through `cellPlainValue()` so a nested error hits it too.
- **Release workflow's root-file deploy could regress the auto-updater feed:** splitting the release workflow's concurrency into a per-tag `deploy-ftp` group and a separate `deploy-ftp-root` group dropped the old FIFO guarantee — a slower-building older tag could reach the shared root-files queue after a faster newer tag and overwrite `updater.json`/`index.php` with the older version. Added a version-compare guard step in `deploy-ftp-root` that fetches the currently-live `updater.json` and skips the deploy outright if the live version is already >= this tag's, so ordering no longer matters.
- **Legacy-row store_id claim never reached the server for deletes:** `SyncController::push()`'s `DELETE` branch never read `$payload`, so `base-helpers.ts`'s `softDelete()` claim (added in the prior day's fix, for the `UPDATE` path) still never landed server-side for a delete. Now applies the payload's `store_id` to the target model (when the column is empty) before authorization and deletion, saving first if it was actually claimed.
- **Promotion-failure left the read-only banner permanently stuck:** `DatabaseProvider.tsx`'s `handleUseThisWindow()` leaves `handoffState` at `"requesting"` pending an async promotion; if that promotion then failed (rehydrate-from-IndexedDB error), nothing ever reset it, since only the success path (`onWriterTabChange(isWriter=true)`) did. `onPromotionFailed`'s handler now also resets `handoffState` to `"offer-force"` so the banner offers a usable next action.
- **Stolen writer lock never notified the old holder:** `tab-lock.ts`'s `stealWriterLock()` steals the Web Lock directly via `{steal: true}`, which the Web Locks spec never signals to the previous holder — a merely-slow (not dead) old writer tab kept believing it was still the writer and kept saving over IndexedDB. Added a `steal-notice` broadcast over the existing handoff `BroadcastChannel`, sent right after a successful steal; every tab (including one busy mid-write) flips itself to read-only as soon as it processes the message.
- Full client vitest suite green (826 passed, up from 816 — 10 pre-existing `sync-indicator` tests needed a `@/lib/db/DatabaseProvider` mock added after `sync-indicator.tsx` started reading `isReadOnlyTab` from it), clean `tsc --noEmit`, full Laravel suite green (346 passed, unchanged).

### fix: address gaps an independent Opus review caught in this same date's H1/C1/architecture-test fixes
- **Commits:** `73e63856` (client), `8a9a5837` (laravel-server)
- A dispatched Opus review of the xlsx→exceljs migration (H1), the single-writer-tab fix (C1), and the `ScopesToTenant` architecture test found three real gaps, all fixed and covered by a regression test that reproduces each before the fix and passes after:
- **H1 remainder — silent row truncation on any blank-row sheet:** `product-import-export.ts`'s `worksheetToSpreadsheet()` used `worksheet.actualRowCount` (the count of *non-empty* rows) as the loop's upper bound instead of `worksheet.rowCount` (the real last row number). Any blank row partway through a sheet — routine in real QuickBooks/Moniebook exports as a section separator — made the loop stop short and silently drop every row after it. Live import data loss; fixed to use `rowCount` (the existing blank-row skip already handles empties correctly).
- **C1 remainder, gap 1 — promotion on a failed rehydrate:** `tab-lock.ts`'s promoted-tab path called `setWriterTab(true)` unconditionally after `onPromoted()`, even if rehydrating from IndexedDB had failed — reopening the exact C1 data-loss hazard on the rehydrate-failure path (a tab writing over the real snapshot with a stale copy it never actually caught up to). `onPromoted()` now returns whether rehydration actually succeeded; a `false`/rejected result keeps the tab read-only and releases the lock rather than promoting on stale data, firing a new `onPromotionFailed()` listener so the UI can tell the user to reload.
- **C1 remainder, gap 2 — migration writes could land before the writer election:** `core.ts` ran schema migrations (including `clearLegacyTransactionsOnce`, a live one-time destructive cleanup for any device that hasn't crossed its flag yet) *before* electing this tab's writer/read-only role, so a tab about to lose the election could still persist that cleanup to the shared IndexedDB snapshot first. Fixed by electing the writer before running migrations, and gating the migration's persistence callback on `isWriterTab()` — a read-only tab still migrates its own in-memory copy (so its own reads see the current schema) but never writes that back to shared storage.
- **Architecture-test remainder — two controller directories invisible to the guard:** `TenantScopingArchitectureTest`'s glob covered `Api/*`, `Api/App/*`, `Api/Web/*` but missed `Api/Admin/*` (9 controllers) and `Api/Public/*` (1), both of which also reference tenant-owned models. Neither hid a real bug (all three now-flagged files have legitimate reasons — `StorefrontController` is public/unauthenticated with no caller identity to scope by; `AdminStoreController`'s `ActivityLog::create()` logs the super_admin's own action, not a tenant query; `AdminPlatformController`'s cross-tenant listing is deliberately platform-wide and super_admin-gated) but they were invisible rather than explicitly allow-listed, defeating the test's own premise. Added both directories to the glob and allow-listed the three files with verified justifications; also documented the scan's known structural blind spots (route-model binding, relationship traversal, service-mediated queries).
- New tests: an xlsx blank-row-truncation regression, an `onPromoted`-failure regression, a migration-persistence-gating regression, and confirmed (by temporarily removing `StorefrontController`'s allow-list entry) that the expanded glob genuinely works. Full client suite green (818 passed, up from 815); full Laravel suite green (346 passed, unchanged).

### fix: single-writer-tab election via Web Locks API to stop cross-tab data loss (C1)
- **Commit:** `04ea4843`
- On the web/PWA build, each browser tab holds its own independent in-memory sql.js database, persisting by wholesale-overwriting a single shared IndexedDB key with no version check, cross-tab lock, or coordination of any kind. Two tabs open at once (or the same install left open twice) could silently destroy each other's committed writes — including already-synced sales — with no error, toast, or retry path. User decision: single-writer-tab via the Web Locks API.
- New `client/lib/db/tab-lock.ts`: exactly one open tab wins an exclusive Web Locks API lock and becomes the writer; every other tab is read-only. When the writer tab closes, the next queued tab is promoted, re-hydrating from IndexedDB first so it never resurrects rows the outgoing writer already changed or deleted before it starts writing itself. Falls back to pre-fix behavior (every tab writes) if the Web Locks API itself is unsupported, since there's no way to coordinate at all in that case.
- `core.ts`'s `execute()`/`transaction()` now refuse to touch the database at all from a non-writer tab (a new `assertWritable()` guard, checked before `db.run()` and before `BEGIN`), throwing a clear error instead of the previous silent last-write-wins overwrite. `DatabaseProvider.tsx` surfaces this with a persistent banner plus a rate-limited toast on write-block, and a success toast on promotion.
- Deliberately scoped to the web/PWA build only — Tauri (desktop/mobile) talks to a real file-backed SQLite database via the Tauri SQL plugin (WAL mode, its own concurrency story) and isn't affected by this in-memory-per-tab problem.
- New test files: `tab-lock.test.ts` (the election logic itself — immediate-writer, contested/read-only-then-promoted, and Web-Locks-unsupported-fallback paths, all stubbing `navigator.locks` since jsdom doesn't implement it) and `read-only-tab-blocks-writes.test.ts` (proves `execute()`/`transaction()` actually consult the election — throws before `BEGIN`, leaves the database untouched, reads still work normally). Full client vitest suite green (815 passed, up from 808), clean `tsc --noEmit` (only the same pre-existing unrelated errors), clean production/static-export build, no new `npm run lint` errors.

### fix: impersonation "End Session" was expected to fail in ordinary use (M4)
- The return-hop handoff code was minted once, at impersonation *start*, with a 60-second TTL — but the UI held onto it for the entire impersonation session, which realistically lasts minutes. Every admin who impersonated for longer than a minute and clicked "End Session" hit the expired-code branch and was bounced to a fresh `/admin/login` instead of returning smoothly. This was the expected outcome of ordinary use, not an edge case.
- Root-caused this differently than either option the original finding suggested: since `impersonateStore()` no longer touches `drx_admin_session` at all (see this same date's cookie-hardening fix), the admin's own `dumosrx.com` session was **never actually disturbed** by impersonating in the first place — it lives entirely in its own independent, HttpOnly, 24h refresh cookie, completely untouched throughout. "End Session" now simply clears the local impersonation flags and navigates straight to `/admin` — no handoff-code redemption, no TTL, no round trip at all. `web/`'s own admin layout (`initSession()` on mount) silently re-establishes the session from that still-valid cookie. This only fails if the admin's own cookie has *itself* expired (a realistic 24h-plus session), landing on the ordinary login flow rather than the previous "session expired" dead end that fired on every normal-length session.
- Simplified `impersonation-banner.tsx`'s `handleEndImpersonation` from an async two-hop `consumeHandoffCode`/`createHandoffCode` exchange to a synchronous state-clear + navigate; removed the now-dead `ending` loading state. Rewrote `impersonation-banner-stale-flag.test.ts` (its scenario — a rejected `consumeHandoffCode` call — no longer applies, since that call no longer happens) to assert the new behavior: no handoff-code calls at all, storage cleared, navigation to `/admin` regardless of the stored code's validity.

### fix: release.yml's workflow-wide concurrency group could silently drop an entire release (L8)
- Same review area: M7's fix gave `release.yml` a single workflow-wide `concurrency: {group: release}` to protect `deploy-ftp`'s "FTP Deploy Root Files" step, which writes to the same shared `/downloads.dumosrx.com/` root regardless of tag. ### fix: assertStoreOwnership's legacy-row claim ran as its own bare statement, outside the write transaction it preceded
- Same review pass: for a pre-migration legacy (`store_id IS NULL`) row, `update()`/`softDelete()` claimed it for the active store via a bare, non-transactional `UPDATE` *before* the actual edit's `transaction()` even started. A failure between the two committed the claim but lost the caller's real edit — and left the row claimed by this store, so a second store later touching the same row was rejected as belonging to someone else, even though nothing had visibly changed from that store's perspective.
- Fixed: `assertStoreOwnership()` no longer performs the claim itself — it returns a discriminated-union `OwnershipCheck` (`{ needsClaim: true, activeStoreId }` or `{ needsClaim: false }`) reporting whether one is needed. `update()`/`softDelete()` now apply the claim as the first statement inside their own `writeUpdate`/`writeSoftDelete` transaction, so the claim and the edit can only ever commit or roll back together. `remove()` (hard delete) ignores `needsClaim` as before — claiming a row only to destroy it in the very next statement protects nothing.

### fix: base-client.ts's 401 handler cleared the auth token on a network blip, undoing token-manager.ts's own hardening one call frame up
- Same review pass: `refreshTokenSilently()` was deliberately hardened to only call `clearToken()` on a definitive 401/403 refresh response, leaving the token untouched on a network error, timeout, captive portal, or transient 5xx during the refresh call. `base-client.ts`'s own 401-handling block undid this: it compared the token before/after the refresh attempt and called `clearToken()` unconditionally whenever the refresh didn't produce a *new* token — which is also exactly what happens on every one of those "not evidence of invalidity" cases, not just a genuinely dead token. - Fixed: `refreshTokenSilently()` now returns a `RefreshOutcome` (`"refreshed"` / `"confirmed-invalid"` / `"unconfirmed"`) instead of `void`, so callers can distinguish "the server confirmed this token is dead" from "couldn't confirm either way." `base-client.ts` now only calls `clearToken()` on `"confirmed-invalid"` (or unconditionally for a 401 from `/login`/`/refresh` themselves, or a retried request's own 401 — both still definitive signals) and retries once on `"refreshed"`; `"unconfirmed"` leaves the token in place. ### fix: live crash — query() didn't recognize sql.js's real corruption error strings
- **Commit:** `cb0ec01c`
- Two Sentry alerts landed on `dumosrx-client` (`bad parameter or other API misuse` and `RangeError: Array buffer allocation failed`, both on `/dashboard`, same timestamp), and separately "PIN login messing up" was reported live. Root cause: `query()`'s row-fetch loop already retries on sql.js's single-shared-connection race (a long read yielding mid-iteration while a write lands on the same connection - see its `writeEpoch`/`QUERY_TORN_READ_ATTEMPTS` comments from an earlier incident), but the catch-block retry only recognized messages containing "closed" or "finalized". sql.js's actual `SQLITE_MISUSE` string and the WASM heap's `RangeError` are two other real spellings of the same race and neither matched, so they crashed through unhandled instead of retrying.
- This got much easier to hit the same day the two Sentry alerts fired: `base-helpers.ts`'s `insert()`/`update()`/`softDelete()`/`remove()` (see the PWA-audit entry above, `1a7d9729`) now each open their own `transaction()` for atomicity, where they previously ran as bare, non-transactional statements - so a `BEGIN` can land mid-yield of some unrelated large `query()` far more often than before. `login()`'s `getUsersByUsernameOrEmail()` is exactly such a `query()`, which is how a concurrent background sync's writes turned into a login-time crash.
- Fixed by broadening the retry-eligible regex to also match "bad parameter", "api misuse", and "allocation failed" - the same single-retry treatment already used for "closed"/"finalized", since these are connection-state corruption from the same pre-existing race, not genuine SQL/data errors.
- Separately, a `dumosrx-server` (Laravel) Sentry alert fired for `RuntimeException: This password does not use the Bcrypt algorithm.` - traced to a local diagnostic script (`environment: local`, stack trace pointing at a one-off scratchpad file) manually confirming a hypothesis already handled in `User::hashPin()`'s own code and comment: PHP's `Hash::isHashed()`/`password_get_info()` doesn't recognize a `$2b$`-prefixed bcrypt hash (which is what the client's bcryptjs produces) as bcrypt, so `hashPin()` deliberately checks for `$2[aby]$` directly instead of trusting `Hash::isHashed()`. No production code path calls `Hash::check()` on the `pin` column (verified: PIN verification is entirely client-side/offline, per `pin-hash.ts`), so this alert reflects confirmed-and-already-mitigated behavior, not an unfixed live bug - not a new fix needed there.

### fix: full-codebase bug sweep — sync privilege escalation, VAT-on-discount, payment webhook/verify race, stock-batch integrity
- An Opus-dispatched read-only scan of `client/`, `web/`, and `laravel-server/` turned up 25 findings (2 critical, 7 high, 10 medium, 6 low — one high item, plaintext staff PINs, deliberately left open in `KNOWN_BUGS.md` for a separate pass). ### fix: receipt/id collisions from time-based, non-unique identifiers
- **Commits:** `f54d7516`, `f0a896ca`
