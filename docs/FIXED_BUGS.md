### A-289 — the client's sync table name was used as a physical table name in the pull cursor
- **Fixed:** 2026-10-19, server only, TDD. The agreement-panel half was already fixed on 2026-10-18 by removing `audit_logs` from both sides of the comparison (`docs/DEVICE_TABLE_AGREEMENT.md`); this closes the general confusion the entry stayed open for.
- **Was:** `SyncController::applyPullCursor()` probed `Schema::hasColumn($table, '_synced_at')` with `$table` being the **client's** sync table name. `getModelForTable()` maps `audit_logs` onto `ActivityLog`, which has no `$table` override, so the pull reads and writes the physical `activity_logs` while the probe asked the unrelated legacy physical `audit_logs` table.
- **No device is affected today, and that is worth stating plainly.** Both tables happen to carry `_synced_at` — `activity_logs` from `add_synced_at_to_remaining_tables`, `audit_logs` from `align_schema_with_client_db`, which created it with the full `_version`/`_synced`/`_synced_at`/`_deleted` set — so the probe returned `true` either way and the cursor was correct by coincidence. **The behaviour of this fix is identical.** What it removes is the coincidence: had the legacy table ever been dropped, or had either table's `_synced_at` differed, every activity-log row whose `updated_at` did not move would have been skipped by the incremental pull for ever, invisibly.
- **Now:** the probe reads `$query->getModel()->getTable()`, which is by construction the physical table the pull queries, and the per-request memo is keyed by that name too. No second `getModelForTable()` call: the query handed in was already built from the resolved model.
- **Sweep, which the fix's brief asked for.** Every other dynamic table name in `app/` resolves correctly already: `stampSyncedAt()` and `reopenPullWindow()` both read `$model->getTable()`; `normalizePushPayload()`'s `store_id` probe reads `$target->getTable()`; `AdminStoreDeletionService::storeScopedTables()` and `ForeignKeyCascadeEmulator` take their names from `Schema::getTableListing()`; `BackfillStoreIds::DERIVATIONS` and `AdminStoreOperationalMetricsService::countScoped()` take theirs from server-side constants. Everywhere `push()` compares `$change['table_name']` it is comparing a sync name to a sync name, which is correct. The one remaining structural instance is `CountsSyncedTableRows::serverTableFingerprint()`'s `DB::table($table)`, which is **safe today only because its `AGREEMENT_TABLES` allowlist happens to contain 25 names that are each their own physical table**; rather than add an indirection nothing needs, `SyncPullCursorPhysicalTableTest` now pins that property, so adding a divergent name to the list fails the suite instead of silently comparing two different tables.
- **Backward compatibility (§11):** no contract changed — same query, same payload, no new field, nothing for a client to understand.
- **Coverage:** `laravel-server/tests/Feature/SyncPullCursorPhysicalTableTest.php` — 2 cases. The first removes `_synced_at` from the legacy physical `audit_logs` in the test database (the only way to make a coincidence observable) and was RED before: `Expected: select * from "activity_logs" where "updated_at" > ? / To contain: _synced_at`. The second is the `AGREEMENT_TABLES` guard, green before and after by design — it exists to stay green.
