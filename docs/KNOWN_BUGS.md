## Open bugs awaiting a fix

#### A-176. `client/`+`laravel-server/` — a `stock_batches` row older than the pull cursor is never re-sent, so some deferred deltas can never resolve
- **Found:** 2026-10-07, while fixing A-173 (see `docs/FIXED_BUGS.md` for the full mechanism and why devices diverge).
- **Location:** `client/lib/db/sync-engine/pull.ts` (incremental pull, cursor by `updated_at`) and `SyncController::pull()`, which has no by-id fetch.
- **What's wrong:** a pulled `stock_movements` row whose `stock_batches` row has not arrived defers its delta, correctly. But the pull is incremental: once the cursor has passed a batch, that batch is only re-sent if it is updated again. A batch created long ago and never touched since therefore **never arrives**, and its deltas stay pending forever. A-173 makes this visible (chronic re-reporting) and safe (reconciliation refuses while deltas are pending), but it does not make the batch arrive.
- **Consequence:** that device's on-hand quantity for the affected batches stays understated indefinitely. **There is a self-service way out, and the error text should point at it:** Settings > Data > "Force full resync" (`forceFullResync()`) clears `_sync_state` and re-pulls every table, which does make a cursor-stranded batch arrive. An earlier version of this entry said there was no way out; that was wrong.
- **The second cause is FIXED (2026-10-07), see `docs/FIXED_BUGS.md` A-176a.** `applyPullTenantScope()` scoped `stock_batches` through a soft-delete-filtered `Product::query()` while `stock_movements` was scoped by `store_id` and pulled `withTrashed()`, so a soft-deleted product's movements arrived without their batches and a full resync could never close the gap. Both that subquery and `counts()`'s mirror of it now use `Product::withTrashed()`.
- **What remains open here is only the cursor half:** a batch whose `updated_at` predates the device's pull cursor is not re-sent by an incremental pull. `forceFullResync()` does recover it, so this is no longer a dead end — but it is a manual step the operator has to know about, and a targeted by-id backfill would remove the need for it entirely.
- **Fix:** a targeted backfill — the client asks for specific record ids it knows it is missing, and the server returns them regardless of cursor position. There is no such endpoint today (`whereIn('id', …)` exists in `pull()` only for the store/user scoping), so this is new API surface plus a client call path, and wants its own scoping. Worth pairing with a decision on whether an unresolvable delta should eventually be surfaced to the store owner rather than only to Sentry.

#### A-175. CI — FTP deploys are not atomic, so production serves a half-old, half-new code tree during every backend and web deploy
- **Found:** 2026-10-07, while scoping the deploy pipeline for A-170. Deliberately logged rather than fixed: the owner chose to keep FTP for now and not land a pipeline rewrite on top of the migration work.
- **Location:** `.github/workflows/deploy-backend.yml` and `deploy-web.yml`, both using `SamKirkland/FTP-Deploy-Action`.
- **What's wrong:** the action uploads changed files one at a time into the live document root. For the duration of an upload, production is serving a mix of old and new files to real traffic. A request landing mid-deploy can execute a new controller against an old service, or load a view whose component has not arrived yet. The window scales with the number of changed files, so the largest changes — the ones most likely to be incompatible across versions — have the longest exposure.
- **Why it has not obviously bitten yet:** PHP's per-request file loading means a request usually touches a small subset of files, and traffic is low enough that most deploys fall between requests. That is luck holding, not a design property.
- **Fix:** SSH is available on this plan (confirmed 2026-10-07), so `rsync` into a release directory plus an atomic symlink swap is the standard answer and removes the window entirely. Worth pairing with `php artisan config:cache`/`view:cache` on the new release before the swap, and with keeping the previous release directory so a rollback is a symlink change rather than a re-upload.
- **Related:** A-170 (migrations never run) and A-174 (the endpoint that runs them) are separate problems on the same pipeline; fixing deploy atomicity does not address either, and neither addresses this.

#### A-162. `client/`+`laravel-server/` — which store id those five stuck `permission_groups` payloads actually carry is still unknown (narrowed, mechanism fixed as A-163)
- **Status:** the *mechanism* by which a row can be queued for one store and pushed under another identity is now fixed — see A-163 in `docs/FIXED_BUGS.md` (`clearDatabaseForNewStore()` left `permission_groups` behind on an account/store switch, and `requeueOrphanedRows()` then re-queued it under the new account). What remains open is only the forensic question of whether that is what actually happened to **this** device, which hinges on one datum nobody has yet: the `store_id` inside those five frozen payloads.
- **Location:** `SyncController::normalizePushPayload()`'s `$allowedStoreIds` guard (`laravel-server`), whose allowed set comes from `resolveOwnershipIdentity()`; the rows themselves come from `ensurePermissionGroupsSeeded()` (`client/lib/db/queries/permission-groups.ts`).
- **What is now established** (beyond A-161's writeup, which this corrects on two points):
  - **The rows were seeded on 2026-09-27**, in a one-day window. `982e8e4b` (2026-09-27) *introduced* the seeding and used `generateId()`; `deterministicDefaultGroupId()` landed later the same day in `a5f40463`. A-161 read the ids' randomness as "a release before 982e8e4b" — before that commit there was no seeding at all, and its deterministic-id check could not have matched by construction.
  - **They were refused on their first push attempt, always.** The guard dates to `132dee87` (2026-09-19), i.e. before the rows existed. There is no regression window and nothing ever accepted them.
  - **The ids are not the deterministic ids of either store this owner really has** (`571582a9…`, and `68e4c0e5…` created 2026-10-05) — consistent with a `generateId()` build, so this says nothing about the store id either way.
- **What the 2026-10-06 prod snapshot ruled out, and what it cannot:** both `user_devices` rows and both `stores` rows belong to one `user_id` (`01a0d876…`), so a second *present-day* account is out. It does **not** speak to 2026-09-27: `user_devices` was created by migration `2026_10_02_000005`, so it holds no history before 2026-10-02, and `UserDeviceTracker::touch()` keys on `(user_id, device_id)` — an earlier account on this same device would only appear as its own row if it had synced since 2026-10-02. A stale-authorization theory is also out: `resolveOwnershipIdentity()` runs `Store::where('user_id', …)` live on every push, not from a cached claim.
- **The strongest remaining candidate, which is cheap to check and was not considered before:** `stores` has used `SoftDeletes` since `2026_09_29_000001_add_soft_deletes_to_stores_table`, and `resolveOwnershipIdentity()`'s `Store::where('user_id', …)` therefore **silently excludes a soft-deleted store**. A third store created and seeded around 2026-09-27 and later soft-deleted (admin panel, or the owner's own store deletion) would produce exactly this refusal forever, with no account switch and no local-only id involved — and a plain `SELECT id, name, user_id, created_at FROM stores` that doesn't ask for `deleted_at` reads as if that store never existed. If this is what happened, the right fix is a decision about rows queued for a store that is gone (drop them client-side, or let the server accept-and-discard), not a tenancy change.
- **The next query to run (read-only), in this order:**
  1. `SELECT id, store_id, name, based_on_role, created_at, updated_at FROM permission_groups WHERE id IN ('392fece4-28a9-4220-bfbf-76cdee14548a','2cc8cdbf-415e-407b-90d8-678c6f6f9de5','16a6f579-b6f5-4fed-b903-bbf8d6c98a73','662ca60f-d088-4e7b-a645-64186d7f1c95','23289841-67ab-487d-9562-4abf88b1a223');` — the five real record ids from Sentry. Expected empty (they were always refused), but if any row exists its `store_id` answers the whole question outright.
  2. `SELECT id, name, user_id, created_at, deleted_at, deleted_by_id, deletion_reason FROM stores WHERE user_id = '01a0d876-79c1-73d9-98b0-7df448f034e8';` — run as raw SQL so soft-deleted rows are included. A third store here, especially one created on or before 2026-09-27 with a non-null `deleted_at`, confirms the soft-delete mechanism above.
  3. Only if both come back empty: `SELECT id, email, role, store_id, created_at FROM users WHERE store_id IN ('571582a9-bc11-43e2-81e9-57999db50294','68e4c0e5-2354-4ff9-98e4-69d3b4c482fa') OR email = 'ibidaadaeze@gmail.com';` — checks for a second `users` row for this person (a staff/PIN row distinct from the owner row) that could have been `$currentUser` on the failing push and hit `resolveOwnershipIdentity()`'s narrow `users.store_id` fallback branch.
- **Also still true, and the reason this class exists at all:** `_sync_queue` is device-global and carries no identity, while push authorization is per-session, so a row queued under one identity is pushed under whatever identity is signed in later. That is deliberate — push is not narrowed by `X-Store-Id`, so one request legitimately carries rows for every store a multi-store owner has — which is why there is no cheap client-side identity filter to add, and why A-163 closes the *orphan* path instead.
- **Worth doing regardless of the answer:** include the payload's `store_id` and the acting user id in `recordSyncFailure()`'s `logCrash()` context (it currently sends only `area`/`table`/`recordId`), so the next occurrence of this class arrives self-diagnosing instead of needing this much archaeology. Note also that A-161's fix (committed on `dev` as `b583703d`) had not reached production when these events fired at 08:38 on 2026-10-06, so those five rows are probably **still** in that iPhone's `_sync_queue` until that deploy lands — reading it directly is the one way to get the payload without any of the queries above, and the window for doing so closes once the fix ships and drops them.

#### A-165. `client/` — a `forbidden` push refusal parks its queue row forever, but making it terminal (as first proposed) would destroy real data — the retry classification is correct, the unbounded parking is the bug
- **Location:** `NON_RETRYABLE_CONFLICT_REASONS` / `REASONS_SETTLING_SOURCE_ROW` in `client/lib/db/sync-engine/push.ts:22-41`; the reason is emitted at `SyncController::push()` `:258` (`authorizeInsertTarget()`), `:409` and `:630` (`authorizeChangeTarget()`, UPDATE and DELETE).
- **Investigated 2026-10-06; the originally-logged fix was attempted and deliberately reverted.** A-165 was first written up as "the same bug class as A-161, just add `forbidden` to both sets." That is **wrong**, and the reason is now verified in code rather than assumed: `forbidden` is genuinely transient in one real shape, so dropping and settling on it would silently destroy a legitimate row. `resolveOwnershipIdentity()` (`SyncController.php`) gives a **staff** session only `[$currentUser->store_id]`, while an **owner** gets every store they own — a strictly narrower envelope. `_sync_queue` is device-global and carries no identity (deliberately — see A-162), and `clearDatabaseForNewStore()` only runs when the selected store *differs* from the local one (`app/setup/use-onboarding.ts:426`), so a staff member signing in onto the owner's **current** store triggers no wipe and drains the owner's **other** stores' queued rows under the narrower scope. Those are refused `forbidden`, and the same frozen payload succeeds the moment the owner signs back in. This is exactly the case `client/AGENTS.md` already called out ("Still open, same incident, not fixed here" — a push rejected `forbidden` is retryable *and correctly so*), which the original A-165 writeup did not account for. A-163's fix narrows this path but does not close it, because it only wipes on a store *change*.
- **What is therefore still genuinely wrong:** the row is never abandoned. `recordSyncFailure()`'s backoff is capped, not bounded, so the row retries hourly forever and re-raises `Sync item stuck after 5 attempts` on every pass — and via pull's pending-local-edit skip, that parked row stops its record being pulled at all for as long as it sits there. That is the real defect, and it is the general "a permanently-parked queue row silently freezes its record's pulls" problem `client/AGENTS.md` records as unaddressed — not a missing set membership.
- **Why not just fixed:** the correct fix is bounded abandonment (give up after N attempts, with the terminal-conflict ledger row as the durable trace, *without* marking the source row synced), plus not letting a parked row block its own pulls. That is a sync-engine design change affecting every retryable reason, not a one-line set addition, and it needs its own scoping — notably what N should be and whether abandonment should be surfaced to the user. Do **not** close this by adding `forbidden` to either set; `client/__tests__/push-settles-permission-denied-rows.test.ts` now pins both classifications side by side and fails if that is attempted.
- **Abandonment cannot be uniform across tables — owner's constraint, 2026-10-07.** "If a sale or stock movement is stuck and is abandoned later, that spoils the data and would cause problems later." This is correct and it narrows the design: a crash report or an audit-log row can be discarded with no business consequence, but a `sales`, `sale_items` or `stock_movements` row is a **business record whose only copy is on that device**. Abandoning one permanently loses revenue data or permanently falsifies on-hand stock — the exact class of corruption `.agents/AGENTS.md` §9 requires tests against. So "give up after N attempts" is only a valid terminal state for diagnostic tables. For business tables the terminal state must be **escalation to a human**, not discard: surface it to the operator (and to the store owner), keep the row, and provide a deliberate retry. That is what makes the stuck-data admin tooling a prerequisite for this work rather than a follow-up to it.
- **And the priority sits upstream of abandonment:** fix the causes. Every stuck row that never happens is one nobody has to adjudicate. Known culprits so far: A-176 (a batch older than the pull cursor is never re-sent), A-168 (a session-relative refusal classified as terminal), PG-18 (refusals that record nothing at all), and the plan-gated queues that never drain (noted in the A-172 fix).

#### A-168. `laravel-server/` — the two `permission_groups` privilege refusals are session-relative too, but are still reported as terminal `permission_denied`
- **Location:** `SyncController::sanitizePermissionGroupSyncPayload()` — the "attempted to grant a permission the caller does not hold" throw and the "caller lacks `manage_roles_permissions`" throw, both `SyncPushPermissionDeniedException`.
- **Problem:** found and deliberately left alone while fixing A-167, which split the *store-scope* refusal into an absolute `permission_denied` and a session-relative `forbidden`. These two throws have the same shape and were not split: the function returns early for a `store_owner`/`admin`/`super_admin` caller, so **every** throw from either check is by definition a non-owner session, and the owner's own session would always have passed. A permission group the owner creates on a shared device, queued and then drained by a staff session signed in afterwards, is therefore refused `permission_denied`, dropped from `_sync_queue` and flagged `_synced = 1` — it never reaches the cloud and no requeue can recover it, even though the owner signing back in would have pushed it cleanly. Unlike A-167's case this needs no second store; one store and one shared device is enough.
- **Why not fixed with A-167:** the blast radius is materially smaller and the fix is materially riskier. It is one table (`permission_groups`), holding role configuration rather than transactional data, and the local row survives — the loss is "this group never reaches the cloud or the owner's other devices", recoverable by the owner re-saving it. Against that, the terminal classification here predates A-161 and is load-bearing in the other direction: `ensurePermissionGroupsSeeded()` makes a client seed five default groups locally, and on a staff device whose store the server has already seeded, `$isFirstTimeDefaultSeed` is false and the permissions diff refuses them — making that refusal retryable would reproduce A-161's `Sync item stuck after 5 attempts` loop for every staff device instead of the one owner device it was fixed for. Resolving it properly means distinguishing a client-seeded default group from an owner-authored custom one at this throw site, which needs its own scoping, and is best done together with A-165's bounded-abandonment work.
- **Locked meanwhile:** `laravel-server/tests/Feature/SyncPushSessionScopedRefusalTest.php::test_permission_group_privilege_refusals_stay_terminal_permission_denied` pins the current behaviour, so the decision is explicit rather than accidental.

## Accepted tradeoffs (no fix planned)

#### P3-1. `client/` — auth bearer token kept in `localStorage` instead of an HttpOnly cookie
- **Location:** `client/lib/api/token-manager.ts:17-50`.
- **Problem:** `auth_token` (the Sanctum bearer token) is read/written via `localStorage`. Any XSS in the client app could read it and exfiltrate a long-lived session token (Sanctum expiry 30 days, client rotates after 7).
- **Why accepted:** `setToken`/`clearToken` mirror the token to native Tauri code (`lib/native/widget-bridge.ts` → Android `TokenStore`, which does use `EncryptedSharedPreferences`) so the home-screen widget can make its own authenticated requests. A real fix needs a dual-path auth design — a real project, not a quick patch. The Tauri build's CSP (`script-src 'self' 'wasm-unsafe-eval'`, no remote or inline script) is a compensating control there, but does not cover the web/PWA build at `app.dumosrx.com`, and even in the bundled app an injected script that satisfies the policy still has same-origin `localStorage` access.

#### PG-14. `web/` — two more nav items are role-gated over permission-gated endpoints (same class as the Operations bug fixed in Phase 1)
- **Found:** code review of admin Phase 1, by deliberately checking every item in `web/components/admin/sidebar-items.ts` against `laravel-server/routes/api.php` after the Operations mismatch was caught live in a browser.
- **Location:** `sidebar-items.ts` — `register-store` and `my-stores`, both gated `roles: ["platform_admin", "agent"]`.
- **What's wrong:** their endpoints gate on a *permission*, not a role. `GET /admin/stores/registered-by-me` is `permission:create_accounts` (`routes/api.php:192-193`), and `POST /admin/stores` throws 403 in `AdminStoreController` unless the caller is super_admin or holds `create_accounts`. The seeder grants `create_accounts` to both roles today, so this is **latent, not live** — but `PUT /admin/roles/{role}/permissions` lets a super_admin revoke it, after which every agent keeps both links and both pages 403.
- **Fix:** gate both on `permissions: ["create_accounts"]`. Note that `checkHasPermission` short-circuits for super_admin, so dropping `roles` entirely would *add* these items to the super_admin nav — keep `roles` alongside if excluding super_admin from "Register Store"/"My Stores" is deliberate.
- **Rule this violates:** `web/AGENTS.md` — "a nav item's gate must match its page's narrowest endpoint gate, not the page's general area." Pre-existing; not introduced by Phase 1, and deliberately not fixed there to keep that phase's diff to its spec.

#### PG-17. `client/`+`laravel-server/` — a device whose rows never reach the server is still invisible (Phase 2b)
- **Found:** stated as an explicit boundary when designing admin Phase 2, not discovered after the fact. See `docs/superpowers/specs/2026-10-06-admin-panel-phase-2-sync-health-design.md`.
- **What Phase 2 does and does not see.** Phase 2 records every push outcome the server *receives*: refusal reasons, the failing record id, per-store accepted/refused tallies. It cannot see `_sync_queue` depth, backlog age, or retry counts, because those are **client-side SQLite tables** (`client/lib/db/schema.ts`). The server has no idea a store is sitting on 500 stuck rows that were never transmitted.
- **Why this matters concretely.** Every sync defect in the recent record — A-161, A-162, A-165, A-166, A-167 — was exactly this shape, and **A-162 is still open precisely because nobody can see which store id those five frozen payloads carry.** Phase 2, on its own, would not have caught it: the rows were refused and settled client-side without the admin panel ever learning of it. (Phase 2 *would* have caught the server-side half, since the refusal reason is now persisted with the record id — which is the datum A-162's investigation has been missing.)
- **Fix (Phase 2b):** have the client report queue depth, oldest-queued timestamp and retry counts alongside its sync request, and store the latest per device/store. Needs a `client/` change, so it ships on the desktop release cycle and admin visibility lags client adoption — which is exactly why it was split out rather than bundled.

#### PG-19. `web/` — `platform_admin`/`agent` have no scoped view of their own registered stores' subscription lifecycle
- **Found:** named as a deliberate v1 boundary when designing admin Phase 3, not discovered after the fact.
- **What's missing:** the Subscriptions worklists (expiring, trials ending, lapsed, failed payments) are `role:super_admin` only, because they carry platform subscription money data that `RegisteredStoreSummary` already withholds from those roles. But `platform_admin` holds `grant_trials` and both roles register stores and track referrals, so "which of *my* stores is expiring this week" is squarely their job and they currently cannot see it.
- **Fix:** a scoped variant filtered on `users.registered_by_id` (the same concept `GET /admin/stores/registered-by-me` already uses), exposing the lists without the platform-wide money figures. The per-action permission gates already work correctly for this, so it is mostly a scoping query plus a second nav entry — note that entry must be gated to match its endpoint, per `web/AGENTS.md`.

#### P3-5. `client/` — PWA install splash screen doesn't follow dark mode
- **Location:** `client/public/manifest.json`.
- **Problem:** `theme_color`/`background_color` are hardcoded to white, so the one-time Android "Add to Home Screen" install splash flashes white for dark-mode users before the page paints. (The in-app browser-chrome tint is unaffected and already dark-mode-aware, via `app/layout.tsx`'s `viewport.themeColor`.)
- **Why accepted:** the Web App Manifest spec has no conditional/media-query support for `theme_color`/`background_color` — it's a single static value, full stop. A dynamic per-request manifest would need a server, which this app's static export doesn't have. No real fix exists; the only lever is picking a different static color that trades which color scheme gets the flash, which is a product call, not a bug fix.

## Engineering notes (tech debt / ongoing risk, not bugs)

These describe the current state of known architectural tradeoffs and performance ceilings — not defects, and not tracked toward a fix. Re-derive before relying on anything here; this isn't re-validated on every pass.

### Performance
- **`db.export()` per write** (web/PWA build): every `execute()` outside a transaction re-serializes the whole local database and writes it to IndexedDB — the dominant long-term scaling risk for a large catalog. Two of its biggest inputs are bounded (`audit_logs`' 730-day local retention window, coalesced multi-image save bursts), but the per-write export itself is unchanged; fixing it properly needs a different persistence model (incremental/OPFS).
- **First PWA install download:** `precache-manifest.json` lists ~399 URLs (~15 MB, including two 650 KB sql.js WASM binaries) fetched on first install — the single largest network cost on a metered connection.
- **Whole-catalog in-memory search:** `getProductsWithDetails()` loads the entire catalog and `product-database.tsx` fuzzy-searches it in memory (debounced). Fine to ~10k products; beyond that the transform+filter+sort chain is O(catalog) on the main thread every filter change.
- **`validateSync()`'s per-request chain** (`SubscriptionService`, `SystemConfig::getVal`, `PermissionGroupSeeder::ensureSeeded`, `enforceStaffLimits`) adds roughly 10 queries to every push/pull before any data is touched.
- **`getStockMovements()` with no window** loads the whole table when searching/filtering — a large result set in React state at scale, independent of indexing, since nothing narrows the predicate.

### Offline / sync
- **Server-side row-lock duration:** `SyncController::push()` holds `lockForUpdate()` locks for the whole outer transaction. Bounded with the current ~50-change batch size, but the first place to look if "Lock wait timeout" shows up in server logs.
- **Tab-lock residual notes:** `resetDatabase()`/`clearDatabaseForNewStore()` call `db.run()` directly rather than through `reserveDbSlot()`, so they can interleave with an in-flight yielding `query()`. A stolen-from tab only learns it lost the lock via the `steal-notice` broadcast, which a frozen tab receives only on thaw — `writerTab` stays `true` until that notice arrives.

### Architecture
- **One hand-rolled tenant-resolution copy remains:** `DashboardService` still hand-rolls the staff→owner lookup instead of a shared `Request`-free helper; `TenantScopingArchitectureTest` only scans controllers, not services.
- **File-size guideline exceeded by design in a few hot spots:** `client/lib/db/core.ts` (~1,640 lines), `laravel-server/.../SyncController.php` (~2,700 lines), and `client/app/setup/use-onboarding.ts` (~640 lines, flagged by `/code-review` during the A-156 fix) are all well past the project's 350-line guideline — known, not tracked toward a split. `getProductsWithDetails()`-style "load everything, filter in React" is the deliberate norm for catalog/customer/PO lists; where that stops being fine isn't written down anywhere.
- **Two client-side sale-recording paths exist:** `recordSaleItemStock` (POS/online orders) and `local-database.ts::createSale` (demo seeding only) — the second still writes `stock_batches.quantity` via a raw `UPDATE` rather than through `update()`, so a demo-seeded batch is the one batch the version model never saw.
- **`composer audit`/`npm audit` are not run in CI.**
- **`sw.js` has no automated test coverage**, despite two prior cache-poisoning fixes.
