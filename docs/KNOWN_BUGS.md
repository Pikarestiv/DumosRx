## Open bugs awaiting a fix

#### A-230. `client/` — the subscription sync advances the whole `stores` pull window although it only applies four fields of what it fetched
- **Found:** 2026-10-10, while fixing A-228 in the same writer.
- **Location:** `lib/db/sync-engine/index.ts` — `syncSubscriptionStatus()`'s `STAMP_STORES_WINDOW_SQL`.
- **What's wrong:** it pulls with `last_synced: { stores: "" }`, so the server returns the **full** store records, applies only `SUBSCRIPTION_FIELDS` (`subscription_tier`, `status`, `suspension_reason`, `license_token`, `updated_at`) to protect local-only columns — correct, and covered by tests — and then stamps `_sync_state.last_synced_at` for `stores` with the response's `server_timestamp`. The ordinary pull therefore asks for stores changed *after* that stamp, and any server-side change to a non-subscription column (`name`, `address`, `receipt_footer`, storefront fields) that fell inside the skipped interval is never re-sent, because the row's `updated_at` is now behind the window. The device keeps a stale value indefinitely unless that store is edited again.
- **Why it has not obviously bitten:** store-profile edits mostly originate on the device, and the owner dashboard's edits bump `updated_at` again on the next change. A single server-side rename landing between a sync round and the next subscription poll is enough.
- **Fix:** either stop stamping the window here (this path is not a pull of `stores`, it is a projection of it — the ordinary pull owns that cursor), or apply every synced column it received, as `pull.ts` does, rather than a five-field subset. The first is smaller and matches who owns the column; `__tests__/sync-subscription-status.test.ts` "stamps the stores pull cursor with the server timestamp" pins the current behaviour and would be the test to change, so check first whether a free-tier device (full sync off) relies on this stamp for anything.

#### A-217. `laravel-server/`+`client/` — a clamped batch's stored quantity is a sum-level clamp on the server and a per-movement replay on the client, so the two can never agree
- **Found:** 2026-10-10, in the review that produced A-215/A-216.
- **What's wrong:** where a batch's log sums below zero, the server stores `max(0, SUM(quantity))` (`HealthSyncReconciliationRepairService`, `SyncController::writeQuantityReconciliation()`) while the client's `replayMovements()` applies `max(0, running + delta)` **after every movement**. The per-movement floor is always ≥ the floored sum, so for any batch that ever went negative mid-log the two figures differ permanently, by construction. Neither side is drifting; they are computing different functions.
- **Consequence:** the client's daily heal converges on its own replay and then leaves the batch alone, so it does not thrash — but the device and the server hold different numbers for that batch indefinitely, and every server-side value report (admin "Total Stock Value", the repair command's own `from`/`to` columns) is computed from the lower one. The repair command already warns that a clamped batch "needs a physical count", which is the honest answer for the stock figure; it is not an answer for the two formulas disagreeing.
- **The planned resolution already exists on paper:** the derived-stock-quantity design (`docs/superpowers/specs/2026-10-10-derived-stock-quantity-design.md`) defines `onHand` as a single floor over the whole sum on **both** sides, which removes the disagreement by making the client stop replaying per movement. A-217 is the interim state until that ships.
- **Fix:** make one definition authoritative. The server should replay the log in order with the per-movement floor exactly as the client does (the ordering problem `client/AGENTS.md` describes for `created_at` has to be solved first — `rowid` is local-only), or the clamped shortfall should be recorded explicitly instead of being lost in a `max()`. Out of scope for A-215/A-216, which deliberately changed neither formula.

#### A-214. `client/`+`laravel-server/` — the 146 fabricated `sync_reconciliation` movements from the 2026-10-10 Health Sync run are still in the log
- **Found:** 2026-10-10, after it happened in production. See A-213 for the design flaw this is the live instance of.
- **What happened:** at `2026-10-10 08:53:29` a single Health Sync run wrote **144 `sync_reconciliation` movements totalling −13,104 units** on store `571582a9`, zeroing products the log says held real stock (`vitamin c white counting` −1,626 against a log of 1,626; `fesolate` −1,528; `folic acid counting` −1,405), plus 2 movements (−18) on store `68e4c0e5`. Activity log confirms one run per store, same second, under the owner's account. It was pressed by a human: at the time the only callers were the Settings → Data button (`hooks/use-settings-sync.ts`) and the DevTools hook — nothing triggered it automatically. That button has since been removed (A-213), leaving the DevTools hook as the only caller.
- **Cause, and the code fixes that shipped:** a succeeded sync round is not a complete one, so a device mid-rebuild after `forceFullResync()` read 0 for every not-yet-rebuilt batch and asserted those zeros. The pre-flight now requires a complete movement-log window, the endpoint records the asserting device, and Health Sync itself is refused outright — see `docs/FIXED_BUGS.md` A-214 and A-213. **Those changes stop it happening again; they do not undo what happened.**
- **Repair, written and tested, not yet run:** `php artisan sync:repair-health-sync-reconciliation` (reports by default, writes only with `--apply`, `--store=<id>` narrows it) reverses each of the 146 movements with a compensating `sync_reconciliation_reversal` movement carrying `reference_id` = the row it cancels, and sets each batch to the sum of its whole log minus the bad deltas — so post-incident sales, deliveries and counts are kept rather than overwritten. It is idempotent, bounded to the run's own write-time window `2026-10-10 08:53:00`–`08:54:00` (A-216 — an upper bound alone also caught the legitimate 2026-10-02 A-148 restoration), reports any un-reversed reconciliation outside that window rather than hiding it, and is safe to run during trading hours: a batch a till moves underneath the repair is abandoned whole (no quantity write, no reversal), listed in the output, and finished by the next run. See `laravel-server/AGENTS.md`, "Health Sync zeroing repair". **What remains:** the founder must run it (report mode first) against production, and devices only converge on their next sync — a device that is missing a batch row entirely replays the reversal only once that batch arrives, which takes the ~10 rounds `docs/FIXED_BUGS.md` A-176b describes. Any batch the report flags as summing below zero still needs a physical count. This bullet is the repair side only; the prevention side (the pre-flight and the endpoint itself) is still open above.
- **Contributing factor worth recording:** a Force Full Resync had been recommended minutes earlier to clear a separate problem, and the Health Sync control sat directly beneath it in Settings → Data. A destructive action adjacent to a routine one, with no guard of its own, is a trap the product sets rather than an operator error. (That adjacency is gone: the Health Sync card was removed on 2026-10-10, so Force Full Resync now stands alone in that group.)

#### A-212. `client/` — the "oversold" alert matches a free-text reason string in a 30-day window, so it reports past events and never a current deficit
- **Found:** 2026-10-10, in review of the derived-stock-quantity design. A reviewer questioned whether the alert actually detects a negative balance; it does not.
- **Location:** `client/lib/db/queries/inventory.ts:426` (`getOversoldAlerts()`), consumed by `use-dashboard-overview.ts` and `use-stock-batch-alerts.ts`.
- **What's wrong:** the query selects movements `WHERE sm.reason LIKE '%oversold%'` within the last 30 days, grouped per product, `LIMIT 5`, reporting `MAX(ABS(sm.quantity))`. So it answers "which products had a movement somebody labelled oversold recently, and how big was the largest one" — **not** "which products' movements currently sum below zero, and by how much". Four separate weaknesses: it depends on free text in `reason` rather than on arithmetic; a deficit older than 30 days silently drops off while still being real; `MAX(ABS(...))` is the size of one movement, not the shortfall; and only five rows are ever returned.
- **Consequence, and why it matters now:** the derived-quantity design (`docs/superpowers/specs/2026-10-10-derived-stock-quantity-design.md`) stores the clamped quantity and relies on the movement log to carry the oversell signal. That reasoning is sound — the raw sum is always computable from the log — but it was argued on the basis that the alert already surfaces it, and this query does not. **Worse: if the arithmetic changes and nothing writes an "oversold" reason any more, this alert goes permanently silent while deficits keep accumulating.** The forcing moment at receiving needs the same raw number, so both depend on a query that does not yet exist.
- **Fix:** add a query that reports, per product, the raw (unclamped) sum where it is below zero, with the size of the deficit — the same grouped sum the recompute already performs, without the clamp. It must fire on a negative sum, report the shortfall, and clear when a count settles it. Replace `getOversoldAlerts()`'s reason-matching with it rather than running both, and keep the alert out of a time window: a deficit is current state, not an event. **It needs the same freshness condition as a stock count (A-211):** on a till that is behind, a raw sum can be negative only because a delivery has not arrived yet, so alerting on it produces false deficits and sends staff to count shelves that are fine. Either compute it on the server, where the log is complete, or show it on a till only when that till has synced recently.

#### A-211. `client/` — a stock count still records the difference it saw, not the number counted; a device behind sync is now warned, not prevented
- **Found:** 2026-10-10, in review of the derived-stock-quantity design (`docs/superpowers/specs/2026-10-10-derived-stock-quantity-design.md`).
- **Shipped so far (the cheap guard):** the cycle-count review step warns when this device has not completed a successful sync in the last 60 minutes, and when the server reports another till in the same store that has not synced in that window, and the submit button is held until the counter acknowledges it. See `docs/FIXED_BUGS.md` A-211. It is deliberately not a block — a till with no connectivity for two days must still be able to count.
- **What is still open:** `submitStockAudit()` (`client/lib/db/queries/inventory.ts:659`) still writes `countedQty - currentSystemQty`, a delta against this device's belief. A warned-and-acknowledged count on a stale device is still wrong by exactly the amount that has not arrived. The correct fix is to record the count as an **absolute observation** ("at this moment a human counted 8") and derive the correction from it; the honest difficulty, which must not be hand-waved, is that a count taken offline and a sale that arrives afterwards but is dated earlier are genuinely ambiguous, and this codebase already knows not to trust `created_at` for ordering (commit `24257592`). That belongs in its own design.
- **Also still unwarned:** the other two callers of `submitStockAudit()` — the catalog quick edit (`components/products/catalog-list.tsx`) and the CSV product import (`lib/db/queries/product-import.ts`) — reconcile stock through the same delta with no freshness check at all.

#### A-209. `client/` — the `audit_logs` dedup rewrites a pending `_sync_queue` payload in place, which is lost if that row is already in flight
- **Found:** 2026-10-10, while fixing A-203. Not a regression from it; the path is older.
- **Location:** `lib/db/core.ts:1243-1262` (`logAction`'s dedup branch).
- **What's wrong:** on a repeat of the same action it bumps `occurrence_count` on the local `audit_logs` row and rewrites that row's pending `_sync_queue` INSERT payload **in place**. `getPendingSyncItems()` reads queue rows, the push awaits the network, and `markSynced()` then deletes the pushed rows by id and flags the record `_synced = 1`. A bump landing inside that window is written into a row that is about to be deleted, so the server keeps the pre-bump `occurrence_count` and the local row reads `_synced = 1` with a value that was never sent.
- **Consequence:** an undercounted `occurrence_count` on the server for a coalesced audit entry. Low stakes — telemetry, not money or stock — which is why it is logged rather than fixed in the same pass, but it is the same silent-divergence shape as A-203 and it will quietly mislead anyone counting repeats.
- **Fix:** the same shape A-203 used — delete the pending row and insert a fresh one carrying the merged payload, so a row already in flight cannot swallow the bump. `addToSyncQueue()` in `base-helpers.ts` is the reference.
#### A-208. `laravel-server/` — an admin till access code never expires, so a forgotten one stays a working credential for ever
- **Found:** 2026-10-10, reviewing the super_admin code-visibility change (`docs/FIXED_BUGS.md` A-207).
- **Location:** `app/Models/AdminTillCode.php:27` — `scopeActive()` is `whereNull('revoked_at')` and nothing else.
- **What's wrong:** the *session* a code opens expires after four hours (`AdminTillSessionService::MAX_SESSION_HOURS`), but the *code* itself has no lifetime. It is valid from issue until someone explicitly revokes it. Nothing prompts that, nothing ages it out, and an admin who leaves the company keeps a working till credential until a human remembers the row exists.
- **Why it matters more now:** before 2026-10-10 a forgotten code was at least unreadable — only its bcrypt hash was stored, so even its owner could not recover it. A-207 deliberately made codes recoverable by a super_admin (encrypted at rest, audited), which is the right call for the operational need but turns a forgotten code into a **durable, readable** credential. The two changes are individually defensible and compound.
- **Consequence:** the blast radius of a stale row grows with time rather than shrinking. The three-active-codes cap limits how many exist per admin but says nothing about how old they are, and the cap is itself pinned to `EQUALIZED_CHECKS` because `verify()` does a fixed number of bcrypt comparisons for timing equalisation — so raising it to make room is not free either.
- **Fix:** give a code an `expires_at` and include it in `scopeActive()`, defaulting to something short enough that a forgotten one dies on its own (90 days is a starting point, not a researched number). Existing rows have no expiry, so §11 applies: treat a null `expires_at` as "never expires" on read and backfill deliberately rather than letting the filter silently retire every live code the day it ships. Surfacing age and `last_used_at` in the reveal card — already returned by `revealAll()` — is the cheap half, and worth doing even if the expiry is deferred.

#### A-206. `client/` — a non-JSON 2xx from the sync API is reported without the one detail that would identify it, leaving a device stuck in a pull loop nobody can diagnose
- **Found:** 2026-10-10 in Sentry (`DUMOSRX-CLIENT-20`, 9 events, first seen 2026-10-07, still occurring on the current build `a120bf9c`).
- **Location:** `client/lib/api/base-client.ts:62-74` (`parseJsonResponse()`).
- **What's wrong:** A-171 made this failure name its endpoint, status and content-type, which was the right first step. It stops there by design — the entry records that a `response.clone()` excerpt was removed because `.json()` has already consumed the body. True of that approach, but the body is recoverable by reading `response.text()` **once** and calling `JSON.parse()` on the string, which never needs `clone()`. Without it the report cannot distinguish the three causes that produce this on shared hosting: a truncated body (PHP hitting `memory_limit`/`max_execution_time` mid-stream after the 200 and the headers are already committed), a valid body with a PHP warning appended after the closing brace, and an HTML error page served as 200. The live events carry `content-type: application/json`, which rules out the third and leaves two indistinguishable.
- **Consequence:** the throw aborts the whole pull round. On `DRX-BKDBKL4Q5` (Chrome on Android) this is almost certainly why that device reports **0 batches across 0 batches** for a 2,495-product store in the Device Stock Agreement panel, showing as a −46,097 "divergence": its first full pull keeps dying partway and it has never completed one. The panel therefore counts an empty device as diverged, which is its own small reporting defect — an unmeasured device is not a disagreeing one.
- **Fix:** read the body as text once, `JSON.parse` it, and on failure report `byteLength` plus the first and last ~120 characters. Length and tail separate truncation from appended output immediately. If truncation is confirmed, the pull also needs to survive it — retry the page at a smaller size rather than failing the round, since a device that cannot complete its first pull has no path forward on its own.


#### A-204. `laravel-server/` — a sync command is marked `sent` the moment it is handed out, is never re-offered, and has no timeout, so a device that does not answer loses it permanently
- **Found:** 2026-10-10. A `send_device_report` issued against `DRX-ZKI5K81UG` sat at `status = 'sent'`, `acted_at = NULL`, `result = NULL` while that device went on syncing normally. No report, no refusal, no error — and no way to ask again.
- **Location:** `app/Services/Admin/SyncCommandService.php:92-126` (`pendingFor()` claims by `UPDATE ... SET status = 'sent'`), `recordOutcome()` at `:129`.
- **What's wrong:** claiming on handout is correct — it stops a device that syncs twice applying a command twice. But `sent` is **terminal**: `pendingFor()` only ever selects `pending`, nothing moves a `sent` row back, and no timeout exists. So every way a device can fail to answer — a build old enough to ignore the `sync_commands` key entirely, a closed tab, a crashed round, a throw before `recordOutcome()` — ends with the command silently consumed. The admin panel then shows neither "queued" nor an outcome, and the operator's only tell is a report that never arrives.
- **Consequence:** remote support is unreliable in exactly the situation it exists for — a device in trouble. It also hides the real cause: the symptom reads as "the device ignored me" when the answer was "that build has never heard of sync commands". Worse, the panel's control is re-enabled (no `pending` row matches), so an operator can reissue indefinitely and lose each one the same way.
- **Fix:** keep claim-on-handout, add redelivery. Record `sent_at` and re-offer a `sent` command whose outcome has not arrived within a window (the device applies at most once because `recordOutcome()` is idempotent on `id`), or expire it to `failed` with a result the panel can show, e.g. "handed to the device but never acknowledged". Surfacing `sent` distinctly from `pending` in `store-sync-health-section.tsx` is the minimum, so an unanswered command is visible at all.
- **Related:** the immediate trigger was a device running a bundle that predates sync commands. A PWA keeps its cached shell until the service worker is replaced, so "deploy the fix" and "the field has the fix" are not the same event — any remote-support feature has to assume a mixed fleet (root `AGENTS.md` §11).


#### A-199. `laravel-server/` — two endpoints resolve a Personal Access Token from the request body without checking its abilities
- **Found:** 2026-10-09, second adversarial review of the on-till admin inspection plan.
- **Location:** `app/Http/Controllers/Api/Admin/AdminStoreController.php:518-529` (`restoreSession`), `app/Http/Controllers/Api/AuthHandoffController.php:32-48` (`create`).
- **What's wrong:** both call `PersonalAccessToken::findToken($validated['token'])` on a token taken from the **request body** and act on its owner without ever checking that token's abilities. `restoreSession` then mints an `admin-refresh` cookie for that owner, and the public cookie-only `/admin/session/refresh` (`routes/api.php:58`) turns that into a general-ability `web` token. The bearer on the request only has to satisfy `auth:sanctum`, which the till's own `['*']` sync token does.
- **Consequence:** any Sanctum token belonging to a super_admin, however narrowly scoped it was meant to be, can be escalated to a durable full superadmin session by whoever holds it. No such narrow token is minted today, which is why this is latent rather than live — but it is precisely why the on-till inspection credential is deliberately **not** a Sanctum token (see `docs/superpowers/specs/2026-10-09-on-till-admin-inspection-design.md`). Any future narrowly-scoped token walks straight into it.
- **Fix:** require `->can('*')` (or an explicit expected ability) on the body token in both handlers, and prefer deriving the identity from the authenticated bearer rather than from a body token at all.

#### A-193. `client/` — the stock-integrity Sentry report does not coalesce, so a drifted device uploads a new bug row daily
- **Found:** 2026-10-08, adversarial review of the stock-integrity branch before merge.
- **Location:** `client/lib/db/sync-engine/stock-auto-heal.ts` (the report moved there from `health-check.ts` with the 2026-10-10 auto-heal, and its `area` is now `stock-autoheal`), `client/lib/utils/error-logger.ts`.
- **What's wrong:** `logCrash()` writes a `feedback` row and queues it for sync, and its fingerprint (`area|message|firstStackLine`) does not normalise digits while the message embeds the counts and net delta — so a device whose numbers move uploads a brand-new bug row every day instead of coalescing.
- **Consequence:** daily synced noise from any device with persistent divergence. Not data loss. **Much narrower since 2026-10-10:** the heal now folds the drift on the first report, so a device only keeps reporting if it holds `unreconstructable` batches, a heal refusal, or a heal that will not converge — all of which are genuinely worth a row a day. The underlying `logCrash` fingerprint gap is unchanged and still applies to every other digit-bearing report.
- **Fix:** `logCrash`'s fingerprint is `area|message|firstStackLine` with no digit normalisation, while the message embeds the counts and net delta — so a device whose numbers move uploads a new synced `feedback` row every day instead of coalescing. Either normalise digits in the fingerprint or move the counts out of the message into the context payload. (The missing `stock_movements(stock_batch_id)` index, originally logged here as the other half, was added 2026-10-09.)

#### A-189. `laravel-server/` — 5,088 products across two stores reference each other's `categories` rows, so their category can never reach any device
- **Found:** 2026-10-08, investigating a store reporting "duplicates" and a catalogue that showed `UNCATEGORIZED` on 98.6% of products even after a factory reset and a clean re-sync.
- **Location:** `categories.store_id` / `products.category_id` data, plus `SyncController::pull()`'s `'categories' => $query->whereIn('store_id', $storeIds)` scoping.
- **What's wrong:** products belonging to store `68e4c0e5` carry a `category_id` owned by store `571582a9`, and 2,628 of `571582a9`'s products point the other way — the two stores are cross-wired. (Both belong to the same owner, two branches of one business; the defect is not owner-specific — the unscoped match that caused it would equally have merged two *unrelated* customers' categories, which is why the repair never touches the other store's rows regardless of who owns them.) The pull correctly refuses to send another store's `categories` rows, and `whereIn` never matches `NULL` either, so the client receives a `category_id` it cannot resolve. The catalogue's `LEFT JOIN categories` yields NULL and renders "Uncategorized". The server is self-consistent throughout (`SELECT COUNT(*) ... category_id IS NULL` returns 0), which is why this is invisible from the server side.
- **Origin:** the push-time natural-key collision handler matched a pushed category by name *without* scoping to the store, so a bulk import pushing `drugs` was remapped onto an unrelated store's `drugs`. The code was scoped by `2026_09_12_000000_scope_category_uniqueness_to_store.php`; the rows it had already mis-pointed were never repaired. The affected store still owns its own 0-product `machine`, `toiletries` and `wine` rows, which is the fingerprint of the remap.
- **Consequence:** no client-side action fixes it — not a resync, not a factory reset, not Health Sync — because the referenced row is one the device is never allowed to receive. It is also live cross-tenant coupling: a rename or delete in the other store silently re-labels or orphans this store's products, which is the hazard the comment at `SyncController.php:1607` already warns about.
- **Root cause closed 2026-10-08.** `findDuplicateInsertConflict()` matched a pushed category/supplier by name against the payload's own store **or any NULL-store row**, and `push()` backfills the caller's store onto the payload before that check — so a store pushing a name that matched one of the nine retired NULL-store seed categories (`Analgesics`, `Antimalarials`, `Vitamins & Supplements`, …) was merged onto the unowned row, and `pull()`'s `whereIn` never sends it. The NULL fallback is gone; a payload that genuinely carries no `store_id` still matches NULL-store rows, which is the pre-multi-tenancy path the `id_map` regression tests cover. Regression coverage: `SyncEndpointTest::test_push_does_not_merge_a_store_scoped_category_into_a_null_store_row`. The two existing `id_map` duplicate-name tests had fixtures creating the pre-existing row with no `store_id` at all; they now create it in the caller's store, which is the only shape a real duplicate can take once push backfills the store — their assertions are unchanged.
- **Fix:** `php artisan sync:repair-cross-tenant-categories` (`App\Services\Sync\CrossTenantCategoryRepairService`). Reports by default; `--apply` writes, `--store=` narrows. It finds or creates a same-named category owned by the product's own store and repoints the product, never touching the other tenant's rows. Products with a NULL `store_id` (9 on production) are reported and skipped — they have no owning store to repoint to and need one assigned first. Uses Eloquent so `updated_at` is PHP-generated UTC: a raw `UPDATE ... NOW()` here would write a timestamp ~4h behind UTC and the corrected rows could never pass the pull's `updated_at` filter (root `AGENTS.md` §7). Covered by `tests/Feature/CrossTenantCategoryRepairTest.php` (9 cases).
- **Still open:** the command exists but has not been run against production. Re-pointing 5,088 products bumps their `updated_at`, so every device for both stores re-pulls them on its next sync — intended here, but it is the same blast radius A-185 describes, so run it per-store with `--store=` rather than unscoped.

#### A-188. `client/` — `no such table: permission_groups` on one device, **mechanism unconfirmed** (do not treat the obvious explanations as the cause; three are already ruled out)
- **Found:** 2026-10-08, triaging Sentry `DUMOSRX-CLIENT-1P` — 3 events, 1 user, culprit `/inventory/:tab`. Logged deliberately as unconfirmed: the telemetry is real, but the code-side mechanism could not be established and is not worth guessing at.
- **Location:** unknown. The query sites are `client/lib/db/queries/permission-groups.ts` and `client/lib/hooks/use-permission-groups.ts`; the table is declared in `client/lib/db/schema.ts` (`CREATE TABLE IF NOT EXISTS permission_groups`, the fourth-from-last statement in `SCHEMA_SQL`).
- **Ruled out, so nobody re-walks these:**
  - **"The local schema predates the table and nothing creates it."** Every path that opens a database runs `SCHEMA_SQL` before anything can query it: `initDatabaseInternal()` on both the Tauri and sql.js branches, `rehydrateFromIndexedDb()` on writer-lock promotion, and `restoreDatabase()` (which also re-runs `runSchemaMigrations()`, specifically so an older backup comes up current). `query()`/`execute()` each `await initDatabase()` when `db` is null, so there is no pre-init read window.
  - **"A `SYNC_COLUMN_MIGRATIONS` ordering problem."** That list only `ALTER TABLE ... ADD COLUMN`s, and `runSchemaMigrations()` runs strictly *after* `SCHEMA_SQL`, so it cannot be what creates the table and cannot run before it exists.
  - **"The sql.js single-blob abort."** `SCHEMA_SQL` is handed to sql.js as one `db.run()`, and a throwing statement silently skips every later statement including `CREATE TABLE`s — the hazard `schema.ts`' own comment at the top of the index section documents, and the reason `READ_PATH_INDEXES` lives in `schema-migrations.ts` instead (see A-6 in `docs/FIXED_BUGS.md`). The only candidate trigger in the blob is `CREATE INDEX idx_sync_conflicts_unresolved ON _sync_conflicts(table_name, record_id, resolved_at)` at a line *before* `permission_groups`, which would abort the rest on a device whose `_sync_conflicts` lacks `resolved_at`. Checked: `_sync_conflicts` and that index shipped in the same commit (`ea1fcc41`), the table was never released without `resolved_at`, and no device can be in that state. In the web branch the enclosing `try` also falls back to a *fresh* database on any throw, which would have every table.
- **A latent hazard found while ruling the above out, not a bug today:** `_sync_conflicts` has **no entry in `SYNC_COLUMN_MIGRATIONS`**, and its index sits inside `SCHEMA_SQL` naming three of its columns. The moment a fourth column is added to that table and referenced from that index, every pre-existing local database aborts the schema blob at that line and loses **every one of the twenty `CREATE TABLE`s after it** — `customer_payments` through `supplier_payments`, i.e. `stores`, `users`, `audit_logs`, the whole procurement and loyalty set, `feedback`, `stock_movements`, `payment_accounts`, `permission_groups`, `system_configs`, `requested_products` — with no migration able to recover them, because the recovery pass runs after the statement that aborted. Either move this index into `READ_PATH_INDEXES` alongside the seventeen already there, or add `_sync_conflicts` to `SYNC_COLUMN_MIGRATIONS` before touching it.
- **Consequence as it stands:** 3 events on 1 device, and whatever permission read triggered it failed on that device — `use-permissions.ts` has a documented fallback for a user with no synced `permission_groups` row, but a thrown "no such table" is not that path. Low volume, no known data loss.
- **Needs a repro before any fix.** What would settle it: the device's `SELECT name FROM sqlite_master WHERE type='table'` (which other tables are missing tells you *where* in `SCHEMA_SQL` it stopped, if it stopped at all), the app version on that device, and whether it is the Tauri or the web/PWA build — the Tauri branch splits `SCHEMA_SQL` on `;` and runs each statement separately with no error swallowing, so a mid-blob abort there would have thrown out of `initDatabase()` loudly rather than leaving a half-built schema. Do not ship a defensive `CREATE TABLE IF NOT EXISTS` at the query site; that hides the mechanism without fixing it.

#### A-178. `laravel-server/` — a throttled sync inflates `changes_refused`, so a healthy store on a busy device reads as failing

- **Location:** `SyncFailureRecorder` / the `sync_throttled` path into `sync_health_daily`.
- **What's wrong:** `sync_throttled` is recorded as a refusal and counted in `changes_refused`, the same bucket as `permission_denied` and `version_conflict`. - **Location:** `NON_RETRYABLE_CONFLICT_REASONS` / `REASONS_SETTLING_SOURCE_ROW` in `client/lib/db/sync-engine/push.ts:22-41`; the reason is emitted at `SyncController::push()` `:258` (`authorizeInsertTarget()`), `:409` and `:630` (`authorizeChangeTarget()`, UPDATE and DELETE).
- **Investigated 2026-10-06; the originally-logged fix was attempted and deliberately reverted.** A-165 was first written up as "the same bug class as A-161, just add `forbidden` to both sets." That is **wrong**, and the reason is now verified in code rather than assumed: `forbidden` is genuinely transient in one real shape, so dropping and settling on it would silently destroy a legitimate row. `resolveOwnershipIdentity()` (`SyncController.php`) gives a **staff** session only `[$currentUser->store_id]`, while an **owner** gets every store they own — a strictly narrower envelope. `_sync_queue` is device-global and carries no identity (deliberately — see A-162), and `clearDatabaseForNewStore()` only runs when the selected store *differs* from the local one (`app/setup/use-onboarding.ts:426`), so a staff member signing in onto the owner's **current** store triggers no wipe and drains the owner's **other** stores' queued rows under the narrower scope. Those are refused `forbidden`, and the same frozen payload succeeds the moment the owner signs back in. This is exactly the case `client/AGENTS.md` already called out ("Still open, same incident, not fixed here" — a push rejected `forbidden` is retryable *and correctly so*), which the original A-165 writeup did not account for. A-163's fix narrows this path but does not close it, because it only wipes on a store *change*.
- **What is therefore still genuinely wrong:** the row is never abandoned. `recordSyncFailure()`'s backoff is capped, not bounded, so the row retries hourly forever and re-raises `Sync item stuck after 5 attempts` on every pass — and via pull's pending-local-edit skip, that parked row stops its record being pulled at all for as long as it sits there. That is the real defect, and it is the general "a permanently-parked queue row silently freezes its record's pulls" problem `client/AGENTS.md` records as unaddressed — not a missing set membership.
- **Unblocked 2026-10-07.** The stuck-data tooling now provides the somewhere-to-escalate-to this needed: per-device queue reports surface what is stuck, and `sync_commands` lets an operator retry it deliberately. Bounded abandonment can now be designed against a real escalation path rather than inventing one — but the two decisions it still needs are unchanged: what N should be, and whether abandonment is surfaced to the store owner.
- **Why not just fixed:** the correct fix is bounded abandonment (give up after N attempts, with the terminal-conflict ledger row as the durable trace, *without* marking the source row synced), plus not letting a parked row block its own pulls. That is a sync-engine design change affecting every retryable reason, not a one-line set addition, and it needs its own scoping — notably what N should be and whether abandonment should be surfaced to the user. Do **not** close this by adding `forbidden` to either set; `client/__tests__/push-settles-permission-denied-rows.test.ts` now pins both classifications side by side and fails if that is attempted.
- **Abandonment cannot be uniform across tables — owner's constraint, 2026-10-07.** "If a sale or stock movement is stuck and is abandoned later, that spoils the data and would cause problems later." This is correct and it narrows the design: a crash report or an audit-log row can be discarded with no business consequence, but a `sales`, `sale_items` or `stock_movements` row is a **business record whose only copy is on that device**. Abandoning one permanently loses revenue data or permanently falsifies on-hand stock — the exact class of corruption `.agents/AGENTS.md` §9 requires tests against. So "give up after N attempts" is only a valid terminal state for diagnostic tables. For business tables the terminal state must be **escalation to a human**, not discard: surface it to the operator (and to the store owner), keep the row, and provide a deliberate retry. That is what makes the stuck-data admin tooling a prerequisite for this work rather than a follow-up to it.
- **And the priority sits upstream of abandonment:** fix the causes. Every stuck row that never happens is one nobody has to adjudicate. Known culprits so far: A-168 (a session-relative refusal classified as terminal), PG-18 (refusals that record nothing at all), and the plan-gated queues that never drain (noted in the A-172 fix). A-176b and A-205, both causes of a permanently stranded row, are fixed — see `docs/FIXED_BUGS.md`.

#### A-168. `laravel-server/` — the two `permission_groups` privilege refusals are session-relative too, but are still reported as terminal `permission_denied`
- **Location:** `SyncController::sanitizePermissionGroupSyncPayload()` — the "attempted to grant a permission the caller does not hold" throw and the "caller lacks `manage_roles_permissions`" throw, both `SyncPushPermissionDeniedException`.
- **Problem:** found and deliberately left alone while fixing A-167, which split the *store-scope* refusal into an absolute `permission_denied` and a session-relative `forbidden`. These two throws have the same shape and were not split: the function returns early for a `store_owner`/`admin`/`super_admin` caller, so **every** throw from either check is by definition a non-owner session, and the owner's own session would always have passed. A permission group the owner creates on a shared device, queued and then drained by a staff session signed in afterwards, is therefore refused `permission_denied`, dropped from `_sync_queue` and flagged `_synced = 1` — it never reaches the cloud and no requeue can recover it, even though the owner signing back in would have pushed it cleanly. Unlike A-167's case this needs no second store; one store and one shared device is enough.
- **Why not fixed with A-167:** the blast radius is materially smaller and the fix is materially riskier. It is one table (`permission_groups`), holding role configuration rather than transactional data, and the local row survives — the loss is "this group never reaches the cloud or the owner's other devices", recoverable by the owner re-saving it. Against that, the terminal classification here predates A-161 and is load-bearing in the other direction: `ensurePermissionGroupsSeeded()` makes a client seed five default groups locally, and on a staff device whose store the server has already seeded, `$isFirstTimeDefaultSeed` is false and the permissions diff refuses them — making that refusal retryable would reproduce A-161's `Sync item stuck after 5 attempts` loop for every staff device instead of the one owner device it was fixed for. Resolving it properly means distinguishing a client-seeded default group from an owner-authored custom one at this throw site, which needs its own scoping, and is best done together with A-165's bounded-abandonment work.
- **Locked meanwhile:** `laravel-server/tests/Feature/SyncPushSessionScopedRefusalTest.php::test_permission_group_privilege_refusals_stay_terminal_permission_denied` pins the current behaviour, so the decision is explicit rather than accidental.

#### A-155. `client/` — a brand-new signup still doesn't land straight on `/dashboard`, even after the A-154 fix
- **Location:** likely `components/dashboard/dashboard-layout.tsx`'s `if (!user) router.push("/login")` guard (`dashboard-layout.tsx:200-204`), reached right after `app/setup/use-onboarding.ts`'s `finishNewAccountSetup()`/`startSyncProcess()` call `login()` then `router.push("/dashboard")`.

## Accepted tradeoffs (no fix planned)

#### P3-1. `client/` — auth bearer token kept in `localStorage` instead of an HttpOnly cookie
- **Location:** `client/lib/api/token-manager.ts:17-50`.
- **Problem:** `auth_token` (the Sanctum bearer token) is read/written via `localStorage`. Any XSS in the client app could read it and exfiltrate a long-lived session token (Sanctum expiry 30 days, client rotates after 7).
- **Why accepted:** `setToken`/`clearToken` mirror the token to native Tauri code (`lib/native/widget-bridge.ts` → Android `TokenStore`, which does use `EncryptedSharedPreferences`) so the home-screen widget can make its own authenticated requests. A real fix needs a dual-path auth design — a real project, not a quick patch. The Tauri build's CSP (`script-src 'self' 'wasm-unsafe-eval'`, no remote or inline script) is a compensating control there, but does not cover the web/PWA build at `app.dumosrx.com`, and even in the bundled app an injected script that satisfies the policy still has same-origin `localStorage` access.

#### PG-14. `web/` — two more nav items are role-gated over permission-gated endpoints (same class as the Operations bug fixed in Phase 1)
- **Found:** code review of admin Phase 1, by deliberately checking every item in `web/components/admin/sidebar-items.ts` against `laravel-server/routes/api.php` after the Operations mismatch was caught live in a browser.

## Engineering notes (tech debt / ongoing risk, not bugs)

These describe the current state of known architectural tradeoffs and performance ceilings — not defects, and not tracked toward a fix. Re-derive before relying on anything here; this isn't re-validated on every pass.

### Performance
- **`db.export()` per write** (web/PWA build): every `execute()` outside a transaction re-serializes the whole local database and writes it to IndexedDB — the dominant long-term scaling risk for a large catalog. Two of its biggest inputs are bounded (`audit_logs`' 730-day local retention window, coalesced multi-image save bursts), but the per-write export itself is unchanged; fixing it properly needs a different persistence model (incremental/OPFS).
- **First PWA install download:** `precache-manifest.json` lists ~399 URLs (~15 MB, including two 650 KB sql.js WASM binaries) fetched on first install — the single largest network cost on a metered connection.
- **Whole-catalog in-memory search:** `getProductsWithDetails()` loads the entire catalog and `product-database.tsx` fuzzy-searches it in memory (debounced). Fine to ~10k products; beyond that the transform+filter+sort chain is O(catalog) on the main thread every filter change.
- **`validateSync()`'s per-request chain** (`SubscriptionService`, `SystemConfig::getVal`, `PermissionGroupSeeder::ensureSeeded`, `enforceStaffLimits`) adds roughly 10 queries to every push/pull before any data is touched.
- **`getStockMovements()` with no window** loads the whole table when searching/filtering — a large result set in React state at scale, independent of indexing, since nothing narrows the predicate.

### Offline / sync
- **Server-side row-lock duration:** `SyncController::push()` holds `lockForUpdate()` locks for the whole outer transaction. Bounded with the current ~50-change batch size, but the first place to look if "Lock wait timeout" shows up in server logs.
- **Tab-lock residual notes:** `resetDatabase()`/`clearDatabaseForNewStore()` call `db.run()` directly rather than through `reserveDbSlot()`, so they can interleave with an in-flight yielding `query()`. A stolen-from tab only learns it lost the lock via the `steal-notice` broadcast, which a frozen tab receives only on thaw — `writerTab` stays `true` until that notice arrives.

### Architecture
- **One hand-rolled tenant-resolution copy remains:** `DashboardService` still hand-rolls the staff→owner lookup instead of a shared `Request`-free helper; `TenantScopingArchitectureTest` only scans controllers, not services.
- **File-size guideline exceeded by design in a few hot spots:** `client/lib/db/core.ts` (~1,640 lines), `laravel-server/.../SyncController.php` (~2,700 lines), and `client/app/setup/use-onboarding.ts` (~640 lines, flagged by `/code-review` during the A-156 fix) are all well past the project's 350-line guideline — known, not tracked toward a split. `getProductsWithDetails()`-style "load everything, filter in React" is the deliberate norm for catalog/customer/PO lists; where that stops being fine isn't written down anywhere.
- **The admin users/stores backend quartet was already over 350 lines before the 2026-10-08 admin-panel Phase 1 work touched it, and stayed over, not pushed over:** `AdminUserService.php` (546 → 610), `AdminStoreService.php` (565 → 584), `AdminStoreController.php` (518 → 557) and `AdminUserController.php` (549 → 552, the one of the four not called out when this phase started). None of the four were split, by design — the phase's rule was that only a file it pushed *past* 350 gets split, and all four were already past it. Every class the phase actually created (`Filters/UserListFilters.php`, `Filters/StoreListFilters.php`, `Support/ListSortResolver.php`, `Support/QueryInput.php`, `AdminStoreReferrerService.php`) is well under the limit.
- **Two client-side sale-recording paths exist:** `recordSaleItemStock` (POS/online orders) and `local-database.ts::createSale` (demo seeding only) — the second still writes `stock_batches.quantity` via a raw `UPDATE` rather than through `update()`, so a demo-seeded batch is the one batch the version model never saw.
- **`composer audit`/`npm audit` are not run in CI.**
- **`sw.js` has no automated test coverage**, despite two prior cache-poisoning fixes.
- **The admin list-sort pagination-stability tests cannot fail under the test suite's SQLite engine (found 2026-10-08, admin-panel Phase 1 final review).** `AdminListSortingTest::store_pagination_is_stable_under_a_tie_heavy_status_sort` and `::user_pagination_is_stable_under_a_tie_heavy_role_sort` exist to pin the deterministic `->orderBy('stores.id')` / `->orderBy('users.id')` tiebreaker on the explicit-sort paths in `AdminStoreService`/`AdminUserService`. The production code is correct and should stay. But `phpunit.xml` runs against SQLite `:memory:`, and SQLite returns tied rows in a deterministic rowid order across two sequential identical SELECTs — so removing both tiebreaker lines leaves **both tests still passing** (verified by doing exactly that during review). MySQL gives no such guarantee, so the defect the tests describe is real in production while the tests provide no regression protection against the tiebreaker being dropped later. Making them engine-agnostic needs a different approach than fetching two pages and comparing id sets.
