#### A-290. `web/` — the store-details Sync tab has no client permission gate, so a delegated operator sees five cards that cannot load
- **Found:** 2026-10-19, while splitting the store-details page into tabs (`web/AGENTS.md`, "Store details is three tabs"). Pre-existing: the same five panels sat unguarded on the single-column page, where they were merely three cards among sixteen rather than a whole tab.
- **Location:** `web/components/admin/stores/details/store-sync-tab.tsx` and the badge in `store-detail-tabs.tsx`, against `laravel-server/routes/api.php:244-252` — every one of `admin/sync/stores/{id}`, `stock-divergence`, `table-agreement` and `queue-state` carries `middleware('permission:view_platform_health')`.
- **What's wrong:** the page gates nothing client-side. A `platform_admin` or `agent` without `view_platform_health` can open the store, see a **Sync** tab, and land on five panels that each render their own "unavailable" state from a 403. The badge degrades correctly — `syncVerdict()` returns `Unavailable`, neutral, which is honest — but the tab itself should not be offered. The panel-level *actions* were already gated (`device-row-actions.tsx`, `stuck-item-actions.tsx`, `device-report-action.tsx` each hide rather than disable on this exact permission), so the convention and the helper both exist; only the container was never gated.
- **Fix:** `checkHasPermission(user, "view_platform_health")` from `use-admin-auth-store` around the `TabsTrigger` and the `TabsContent` for `sync`, the way `app/admin/operations/page.tsx:45` already gates a whole page, plus a `resolveTab()` fallback to `overview` so a deep link to `?tab=sync` from a shared URL does not open an empty tab. Hide, do not disable, matching the three action components beside it.
- **Deliberately not fixed with the tabs change**, which was scoped to layout and the badge; gating is a permission decision and belongs with a logged-in browser smoke test per `.agents/AGENTS.md` §9.

#### A-288. `laravel-server/` — the `store_id` backfill now exists, but `requested_products` and a multi-store owner's rows still cannot be attributed
- **Found:** 2026-10-18, while building the per-table agreement fingerprint (`docs/DEVICE_TABLE_AGREEMENT.md`). Pre-existing data asymmetry, surfaced rather than caused by the new instrument.
- **Mostly fixed 2026-10-18** by `sync:backfill-store-ids` — see `laravel-server/AGENTS.md`, "`store_id` backfill", for the mechanism, the per-table derivation and its confidence. This entry stays open only for the residue below.
- **Location:** `App\Console\Commands\BackfillStoreIds::DERIVATIONS` against `CountsSyncedTableRows::scopeToStore()` and `SyncController::applyPullTenantScope()`, which filter on `store_id` for the 20 directly-scoped tables.
- **What's wrong, originally:** the device fills `store_id` on every legacy row it holds; the server's migrations never backfilled the column for the 11 tables of `add_store_id_to_domain_tables`. `NULL` never matches `where('store_id', ...)`, so such a row is counted locally, excluded in the cloud, and — since the pull uses the same filter — can never be delivered to any device either. `.agents/AGENTS.md` §11 "scoping filters are a contract too" verbatim. The six child tables are immune: the server scopes them through their parent and treats their own `store_id` as non-authoritative everywhere.
- **What the backfill cannot do, which is why this is still open:**
  - **`requested_products` has no owner column at all** — no `user_id`, no FK to anything store-scoped. Its NULL rows can never be attributed by any derivation and the command reports them untouched. If any exist, that table's agreement delta will not reach zero and the rows stay invisible to the sync engine permanently. Fixing it needs a signal that does not exist today (e.g. stamping `created_by` going forward, then attributing by that).
  - **A multi-store owner's rows are refused on purpose.** Where the owning store cannot be derived with certainty the row keeps its NULL and is counted as unattributable rather than guessed — a row stranded invisible is bad, a row handed to the wrong pharmacy is far worse.
- **Blast radius still unmeasured:** the counts need `SELECT COUNT(*) WHERE store_id IS NULL` per table against production, which §12 forbids without clearance. `sync:backfill-store-ids` with no flags is exactly that measurement and writes nothing; run it before deciding whether any of this matters.
- **To close:** run the dry run on production, then `--apply`, then confirm the agreement panel's residual `row_delta` reaches zero on every directly-scoped table. If `requested_products` is the only table left non-zero, close this and open a narrow entry for it.

#### A-289. `laravel-server/` — the sync table-name string is used as a physical table name in more than one place
- **Found:** 2026-10-18, while establishing A-288's table list. Not introduced by it.
- **Location:** `CountsSyncedTableRows::AGREEMENT_TABLES` (`'audit_logs'`, counted via `DB::table($table)`) against `SyncController::getModelForTable()`, where `'audit_logs' => ActivityLog::class` and `ActivityLog` has no `$table` override, so it resolves to the physical `activity_logs`.
- **What's wrong:** the client's local table is `audit_logs` and its rows push to, and pull from, the server's `activity_logs`. The agreement digest counts the *other*, physical `audit_logs` table — the legacy cruft `add_store_id_to_activity_logs` identified as unused. So the cloud side of the `audit_logs` fingerprint is near-zero while the device reports its whole activity log: a large permanent row delta that is an instrument error, not a data divergence. A real divergence on that table is simultaneously undetectable.
- **The agreement-panel half is already fixed:** `'audit_logs'` was removed from `AGREEMENT_TABLES` and from the client's
  fingerprint (see `docs/DEVICE_TABLE_AGREEMENT.md`, "The `audit_logs` false delta"), so the panel no longer reports that
  false delta. **What stays open is the general confusion**, which also appears in `applyPullCursor()`'s
  `Schema::hasColumn($table, '_synced_at')` — the next table whose client and server names differ will hit it again.
- **Fix:** resolve the physical table through `getModelForTable()` (the way `SyncSchemaParityTest` already does) rather than using the client's sync table-name string as a physical name, or map `audit_logs → activity_logs` in `scopeToStore()`. One place. Until then, treat the `audit_logs` row of the agreement panel as unmeasured.

#### A-287. `laravel-server/` — a mis-stamped product's batch never moves in the cloud again, because the movement is accepted and only its delta is refused
- **Found:** 2026-10-18, raised by the review of A-280 and recorded rather than folded into it.
- **Location:** `SyncController::applyStockBatchDeltas()` (where A-280's refusal sits) vs `authorizeInsertTarget('stock_movements')` (where it arguably belongs).
- **What's wrong:** A-280 refuses the *delta* but the *movement row* is still accepted, because `authorizeInsertTarget()` resolves a movement's ownership from its own `store_id`, which `normalizePushPayload()` backfills from the session. For a mis-stamped product (the A-248 shape — a `products.store_id` pointing at the wrong store), the till keeps pushing movements that are accepted and whose deltas are all refused, so **that batch's cloud quantity never moves again** while the device keeps deriving its own from its local log. A permanent single-batch divergence, visible only in `sync_failures`. Before A-280 the quantity moved — on the wrong store's batch — so this is a knowing trade, not a regression: silent cross-tenant mutation was worse.
- **Why it is not already fixed:** the refusal entry carries `'id' => null` (an accumulated delta has no queue row), and `push.ts`'s failure loop opens `if (f.id == null) continue;`, so the device is told nothing at all. It is not even parked the way A-165 parks a `forbidden` row.
- **Fix:** move the ownership check up into `authorizeInsertTarget('stock_movements')` so the **whole movement** is refused, with the change's own id, and parks visibly under the existing retry machinery instead of the delta being refused invisibly. That makes the mis-stamp surface as a stuck queue row — which is the signal an operator can act on — rather than as a frozen quantity nobody can see. Check A-165's parking semantics first: `forbidden` is the retryable/parked reason and is the right one here, not `permission_denied`, because a staff session's scope is narrower than its owner's and the same payload can succeed later.

#### A-286. `laravel-server/` — `_synced_at` is stamped per change inside the push loop, not at commit, so A-282's lag is mitigation rather than a fix
- **Found:** 2026-10-18, raised by the review of A-282 and deliberately left for its own change.
- **Location:** `SyncController::push()` — the per-change `$now` stamps (`:300`, `:412`, `:664`) against the outer `DB::commit()` after `applyStockBatchDeltas()`.
- **What's wrong:** a row's `_synced_at` records when its change was *processed*, not when it became *visible*, so a pull can legitimately stamp a watermark newer than rows that are still uncommitted. A-282's 60s lag hides the ordinary case but is explicitly not a bound: `max_execution_time` is CPU time on Linux and does not count time blocked in MySQL, the host is LiteSpeed with no override, and because `:493` takes `lockForUpdate()` **per change** a contended push can accumulate several `innodb_lock_wait_timeout` waits (50s each by default) and still commit rows stamped minutes earlier. Those rows are lost on any device that pulled in between, silently — `checkSyncHealth()` covers five tables by count and an update changes no count.
- **Fix:** collect every `(table, id)` the push actually wrote and re-stamp `_synced_at = now()` for that set immediately before the outer commit. The exposed window then shrinks to the commit itself and the lag only has to cover clock skew. Reuse `reopenPullWindow()`'s discipline — query builder, never Eloquent, so `updated_at` and `_version` do not move — and keep the per-change stamp as the initial value so a row written by a path that is not tracked is still stamped at all. Once it lands, `PULL_WATERMARK_LAG_SECONDS` can drop to a few seconds; say so in the same change.

#### A-283. both — a `stock_movements` or `stock_batches` delete is a hard delete, and making it soft needs the quantity accumulator first
- **Found:** 2026-10-18, audited alongside A-281 and deliberately excluded from it.
- **Location:** `app/Models/StockMovement.php`, `app/Models/StockBatch.php` (no `SoftDeletes`, both tables have `deleted_at`); `SyncController::push()`'s DELETE branch; `applyStockBatchDeltas()`.
- **What's wrong:** both are in `pull()`'s table list and neither uses the trait, so a pushed DELETE destroys the row — for `stock_movements` that is the log entry a batch's quantity is derived from. Nothing queues either delete today (verified: no client caller `softDelete`s these two; `batch-quantity.ts` and `retention.ts` both say so in their own comments), so this is a latent capability rather than a live defect, which is why it is filed rather than fixed.
- **Why the trait alone would be wrong, which is the whole reason it is deferred:** `client/AGENTS.md`'s batch-quantity rules state that a deleted *receipt* movement must be classified as `{-q, -max(0,q)}` or the batch reads as a carve-out and keeps units it no longer holds — a silent write-off in the other direction. The server side needs the matching work: `applyStockBatchDeltas()` would have to **reverse** a deleted movement's delta, which it has no concept of today. Adding `SoftDeletes` without both halves turns a hard delete into a soft one that silently leaves the quantity wrong, which is worse than the current state where nothing can delete these at all.
- **Fix:** do it with the derived-quantity design (`docs/superpowers/specs/2026-10-10-derived-stock-quantity-design.md`), where quantity is a projection over the log and a soft-deleted movement simply drops out of the sum — at which point the trait is the whole fix. Until then, `client/AGENTS.md`'s movement-delete note is the warning to read first.

#### A-278. `laravel-server/` — the rest of the raw-`update()`-without-`_version` family, after A-277 closed the `users` half
- **Found:** 2026-10-18, the full sweep A-277's brief asked for: every `->update([...])` / `->increment()` / `->decrement()` in `app/` and `database/`, filtered to the 31 tables `SyncController::getModelForTable()` versions. Reported rather than fixed because none of them is `users.is_active` — A-277's reason for being fixed immediately was that it is an access-control value, and none of these is.
- **`_version` is only ever moved by `SyncController`'s accepted-push path (`:649`).** Nothing else in the codebase bumps it — no model event, no observer. So an **Eloquent model-instance** `$model->update([...])` is just as exposed as a query-builder one, which is wider than the A-245/A-276 write-up implied. `_version` is also not in most models' `$fillable`, so an instance `update()` cannot bump it even if asked; these need the query-builder form (`Model::whereKey($id)->update([...])`) or `increment('_version', 1, $extra)`.
- **Real instance — `app/Services/Admin/AdminCatalogService.php:133-134`.** `Product::query()->...->update(['generic_name' => 'General'])` and the `manufacturer` one beside it. Both columns are freely client-pushable (the product edit form sends them), `products` is versioned, and this is an admin-triggered bulk backfill over a whole store — exactly A-245's shape, on exactly A-245's table. A device holding the pre-backfill copy of any touched product writes its blank value back at an equal version. **Fix:** the documented `'_version' => DB::raw('COALESCE(_version, 0) + 1')`; it already has a `$dryRun` branch, which must keep leaving the version alone.
- **Latent, and better fixed by the exemption than by a bump — `stores.storefront_dirty_at`,** written bare in four places (`app/Models/Product.php:90`, `app/Models/Store.php:199` inside the `saved` hook, `app/Http/Controllers/Api/Internal/StorefrontRebuildController.php:62`, `app/Console/Commands/RebuildStorefrontIfDirty.php:97`). No client sends the column today, so `forceFill` never overwrites it and nothing is broken — but it is **not** in `STORE_SYNC_FORBIDDEN_FIELDS`, which is the only thing that would make it genuinely exempt rather than accidentally safe. **Fix:** add `storefront_dirty_at` to `STORE_SYNC_FORBIDDEN_FIELDS` and leave all four writes bare. It is a server-owned rebuild watermark, it sits beside `paystack_fee_dirty_at` which is already on that list for the same reason, and a version bump on the `Store::saved` hook would make every storefront toggle re-push the store row to every device for nothing.
- **Unassessed by table — `app/Services/Admin/ForeignKeyCascadeEmulator.php:54`.** `DB::table($reference['table'])->whereIn($col, $ids)->update([$col => null])` walks the FK graph at runtime, so which tables it writes depends on the schema, and versioned ones are certainly among them. It runs only on an admin cascade delete, where the parent row is going away, so the practical exposure is small — but it is the one site in the sweep whose target set cannot be read off the source.
- **Already-run migrations, listed so the next person does not re-find them:** `2026_10_15_000001_backfill_receipt_footer_default` (`stores.receipt_footer`, client-pushable), `2026_10_01_000000_clear_store_id_on_store_owners` (`users.store_id`), `2026_09_29_000003_retag_bulk_import_stock_movements`, `2026_09_28_100000_make_users_password_nullable`. Nothing can be done about them retroactively — editing a migration that has already run changes nothing — but **the rule applies to future ones**, which is the point of writing them down.
- **Confirmed clean, so nobody re-checks:** `SyncController:2626` and `HealthSyncReconciliationRepairService:258` are the documented `stock_batches.quantity` exemption; `SystemConfigController:117` and `SyncSubaccountFeeRates:51` write `paystack_fee_dirty_at`, which is in `STORE_SYNC_FORBIDDEN_FIELDS`; `RolesAndPermissionsSeeder:141,147` write `users.role_id`, which is in `USER_SYNC_FORBIDDEN_FIELDS`. Everything else in the sweep targets an unversioned table (`subscriptions`, `coupons`, `coupon_usages`, `notifications`, `online_orders`, `payment_intents`, `sync_commands`, `admin_till_*`, `role_permissions`, `sync_health`, `licenses`, `email_templates`).
- **The general rule** is in `laravel-server/AGENTS.md`, "A raw `update()` on a synced table must move `_version`".

#### A-275. both — money is a binary float on the device and an exact decimal on the server, with no decimal library anywhere
- **Found:** 2026-10-17, from the owner asking whether a third-party package should have been handling money arithmetic. Not from a reported symptom; nothing is known to have mis-totalled yet.
- **What's wrong:** `cost_price` is `decimal(10,2)` server-side (`2024_01_20_000004_create_inventory_system_tables.php:64,83`) and `REAL` — IEEE 754 double — in the local SQLite schema (`client/lib/db/schema.ts:48,158`, and `cost_price_override` at `:490`). The same money value is therefore exact on one side of the sync and binary-approximate on the other, and every total the device computes (`SUM(cost_price * quantity)`) accumulates binary error that the server's decimal arithmetic does not. There is **no decimal library in the project at all**: nothing in `client/package.json`, `web/package.json` or `composer.json` — no `decimal.js`, `big.js`, `dinero`, `brick/math`. Money is raw JS numbers client-side throughout.
- **Where it does NOT matter, so this is not urgent:** the weighted-average cost (`getAverageCostPrice`, `client/lib/db/queries/products.ts:75-83`) is derived on read for display only and never stored — margin, COGS and FEFO deduction each read a batch's own `cost_price`, so there is no re-averaging loop compounding an error into stored data. An earlier reading of this entry's author assumed there was; there is not. Quantities are integers and are rebuilt from `stock_movements`, so stock figures are unaffected.
- **Where it could matter:** the stock-agreement panel compares a device's own valuation against the cloud's (`client/lib/db/queries/stock-fingerprint.ts`, `StockDivergenceService`), i.e. it compares a float sum against a decimal sum of the same rows. Every snapshot observed to date agrees exactly, so the error is currently below the displayed precision — but the two sides are computed in different number systems, which is an asymmetry waiting on a large enough batch count or a value with more binary slop. Any future code that *stores* a divided money value (an apportioned transfer or procurement cost — the stored costs ending `.14`, `.39`, `.43`, `.21`, `.87` show division does happen somewhere upstream and land in storage) would make it a real rounding bug rather than a display one.
- **Fix:** store money as integer minor units (kobo, centimes) and never divide without deciding where the remainder goes; or, less invasively, keep the columns and put `decimal.js`/`big.js` in front of every client-side money sum and `brick/math` or integer arithmetic server-side. Either is a cross-cutting change touching the schema on both sides, so it needs the §5 cross-repo schema check and a §11 backward-compatibility plan — old bundles will keep sending floats indefinitely.
- **Do not fold this into A-271.** That entry's `decimal(10,2)` overflow at values ≥ 100,000,000 is a separate, already-documented failure of the same column; this entry is about the representation on either side of it.

#### A-271. `client/` — a cost edit the pull cannot reach keeps one device's stock value permanently apart from another's
- **Found:** 2026-10-15, from the owner's report that two of Cynthia's tills **agree with the server on quantity** and still disagree with each other on total stock value. Quantities agreeing is what makes this a cost problem: quantity is stripped from the pull and rebuilt from `stock_movements`, so it reconciles independently of anything in the row.
- **Half of it is fixed** — see `docs/FIXED_BUGS.md` "A-271 (part)". A sale no longer bumps a batch's `_version`, so her cost corrections stop being refused as conflicts and silently reverted. That path loses edits; it does not by itself hold two devices apart.
- **What stays open:** `pull.ts:352-360` skips any pulled row that has **any** pending `_sync_queue` entry, with no time limit. While a `stock_batches` edit sits in that queue — a non-terminal failure, `retry_count >= 5`, or merely parked behind a backed-off sibling — the device keeps its own `cost_price` and the server's never lands on it, while its quantities keep agreeing through movements. That is a value-only divergence that persists for as long as the row is stuck. One concrete trigger: a `cost_price` at or above 100,000,000 overflows the server's `decimal(10,2)` and errors on every retry for ever, which is reachable in CFA and naira.
- **A second, rarer path:** after a terminal conflict drop the row is left `_synced = 0` with no queue entry, and `requeueOrphanedRowsOnce()` (`reconcile-identity.ts:149-170`, on a crash-flagged boot) re-queues it as a whole-row push that conflicts again — re-shielding the row from each pull. This is the only path that pins both the cost and the rewind budget.
- **Evidence to gather before fixing either**, now that the device report carries it (2026-10-15, `laravel-server/AGENTS.md` "Remote device report"): request a report from both devices and read `rewind_count` per table, "Batch edits the server refused" (resolved rows included — A-268), and "Batch costs on this device", where `SHIELDED` marks exactly the rows the pull cannot reach. Then compare those ids against the server. A device `_version` behind the server's with a different cost is the known shape; equal versions with different costs would be something new. Zero-code checks available today: `device_queue_reports.stuck_items` for the laptop, per-device `device_value_sum - server_value_sum`, and `grep "version conflict for stock_batches" storage/logs/laravel*.log`.
- **Candidate fix, not yet taken:** skip a pulled row only when its pending queue entry is **not** quantity-only (payload keys within `{quantity, updated_at, _version, _synced, store_id, user_id}`). A quantity-only local edit carries nothing a pulled row can clobber, since `quantity` is deleted from the pulled payload anyway, so the skip buys nothing and costs this. It would also let `stock_batches` drain skip-free in a selling shop, which is what currently keeps the rewind budget spent. Deliberately deferred until the report says which path is live — the stuck-queue case may need the stuck row cleared rather than the skip relaxed.
- **Not yet asked of the owner**, and it would narrow this in one answer: whether Cynthia sees a conflict toast when she saves a cost price, and whether the old price comes back when she reopens the product. The second is the signature of the lost-edit path that is now fixed; a value gap with neither symptom points at the stuck queue.

#### A-270. `client/` — the receipt number a customer reads out cannot be searched for
- **Found:** 2026-10-15, while auditing the A4 receipt's length (see `client/AGENTS.md`, "The receipt earns every line it prints").
- **What's wrong:** the receipt prints `RCT-<first 8 of sale.id>` (`receipt-view.tsx`'s `shortId`) and the foot barcode encodes the full `sale.id` UUID. Sales history searches `customer_name`, `transaction_number` and `item_names` (`pos-transaction-history.tsx:163-167`) — `transaction_number` is the `TXN-…` value set in `use-pos-payment.ts:169`, and it is **never printed anywhere**. So the one identifier a customer holds is the one identifier staff cannot look up, and the barcode is unscannable by design: nothing in the app has a scan path for it.
- **Fix:** add `transaction_number` to `ReceiptTransaction`, print it as the receipt number, and barcode that instead of the UUID. That also makes the barcode worth the paper — until then `show_barcode_on_receipt` (2026-10-15) exists partly so a store can stop printing a decoration.
- **Not urgent:** staff can find the sale by customer or item today. It is cheap and it removes a daily annoyance at the counter.

#### A-269. `client/` — a part-paid sale prints "Total paid" with no balance owing
- **Found:** 2026-10-15, in the same receipt audit.
- **What's wrong:** `ReceiptView` prints `Total paid` and, when it is larger than the total, `Change`. A credit or partial payment prints a smaller `Total paid` and **nothing stating what is still owed**, so the customer's copy records neither the debt nor its amount. The reader has to subtract two numbers to learn they owe money.
- **Fix:** a `Balance due` line whenever `amountPaid < total`, mirroring `Change`. One conditional block; it must not be toggleable (a customer needs it to dispute the debt).
- **Noted while shortening the receipt**, which made the gap obvious: the shortening rules deliberately keep `Total paid` in exactly this case, so the line it needs beside it is the one that is missing.

#### A-268. `client/` — the sync conflict log marks a lost edit resolved when any later change touches the same row
- **Found:** 2026-10-15, vetting the cost-price divergence between Cynthia's two tills.
- **What's wrong:** `resolveConflictsForRecords` (`push.ts:483` → `conflict-log.ts:96-110`) resolves a record's logged conflicts when *any* subsequent change to that record is accepted. On `stock_batches` that is routine: a sale pushes a quantity-only update seconds later and marks the dropped `cost_price` conflict resolved, although the cost never reached the server. The ledger that exists to outlive the toast therefore under-reports exactly the case it was built for — a silently discarded edit — and the device-diagnostics report, which lists unresolved conflicts only (`diagnostics-detail.ts:66-75`), inherits the blind spot.
- **Fix:** resolve a conflict only when a later accepted change carries the **same fields** as the dropped one, rather than merely the same `record_id`. The conflict row already stores a `fields` list (`conflict-log.ts:32`).
- **Why it matters now:** it is the reason "her cost edit vanished" leaves no durable trace to find afterwards, and so the reason the divergence had to be diagnosed from the code rather than from the device's own ledger.

#### A-267. `client/` — two persisted time guards outside the health check still trust this device's clock
- **Found:** 2026-10-14, in the vet of A-234's fix. Neither is urgent; recorded so the next clock pass has the list rather than re-deriving it.
- **(a) `login-lockout.ts`** persists `lockedUntil` as epoch milliseconds in `localStorage`. A clock moved **forward** clears a PIN lockout early; moved back, it extends one. It is a brute-force guard, so the direction that matters is "cleared early" — but the party with access to the OS clock is the store owner, who already has the PIN, so the exposure is close to nil. Deliberately not fixed: tightening it would lock out an honest user whose clock reset mid-lockout, which is the A-266 shape again.
- **(b) `base-client.ts:97-101`** compares `Date.now()` against a persisted `authTokenIssuedAt` to decide a silent refresh. A clock moved back past the issue time means the refresh never fires and the user meets a 401 instead; the recovery is the ordinary re-login path, so it degrades rather than breaks.
- **The shape both share**, and the reason they are not `isIntervalElapsed()` candidates: they are not "has an interval elapsed" guards but "is this instant past a stored deadline", where a future-reading clock is the dangerous direction rather than the safe one. The real fix for both is the same as for the trading-day work: a server-anchored clock the device can consult, rather than `Date.now()`. See A-247.

#### A-266. `client/` — a customer desktop keeps losing its date, and the clock lock stops the till until it can verify online
- **Found:** 2026-10-14, reported by the founder from the field. **Not measured in the repo, which is why it is written down here** — a review session dismissed it as hypothetical on the grounds that the only clock evidence in the codebase is A-247's ~8-hours-fast till. Both are real: the fast till is the measured one, this is the observed one.
- **What is observed:** a specific customer PC repeatedly loses its date and time. The classic cause is a dead CMOS battery (CR2032), which resets the clock to a BIOS default on power-off — and a Nigerian pharmacy takes several power cuts a week, so the reset recurs until the part is replaced. Unconfirmed: whether it is the battery, a BIOS clock reset by switching off at the wall, or something else. Nobody has opened the machine.
- **Why it matters beyond the clock:** the licence guard keeps a `last_monotonic_time` watermark and locks the till when wall time reads below it (`client/lib/licensing/licensing-manager.ts`). A battery reset is always a backwards jump, so each reset locks that till. The way out is to correct the clock and verify against the server, which needs connectivity **at that moment** — during a power cut, in a shop, that is not guaranteed. The failure mode is "cannot sell until the internet comes back", and for a pharmacy still half on paper, every lock is an argument for the paper.

#### A-265. `client/` — a cycle count on a batch carrying an oversell deficit silently does nothing the first time, and the ledger ends up double-counting the correction
- **Found:** 2026-10-14, while reading the one production row the A-264 exposure query returned. Confirmed by running the real `insert()` hook against the live shape.
- **The live case:** batch `868a8d17` ("Opening Stock" for `gluformin`, store `571582a9`, created 2026-09-25) has 4 units of inbound movements and a log summing to **−2** — 6 units went out where 4 ever arrived. Stored quantity 0, which is correct under the derived definition.
- **What happens:** a staff member who finds 2 units on the shelf and counts them writes a `+2` adjustment. The log then sums to 0, so the rebuilt quantity is **still 0** — the count appears to have done nothing. Counting again writes a second `+2`, the log reaches +2, and the figure finally reads 2. The number is now right and the stock ledger records **+4 of found stock for 2 real units**, with no indication that the first adjustment was absorbed.
- **Corrected 2026-10-14 (design pass), three ways.** (a) **It is not every count.** `applyStockAdjustmentDelta()` lands found stock on `getOrCreateTargetBatchForProduct()`'s first result, ordered by expiry then `created_at`, which need not be the batch holding the deficit. `gluformin` has one batch, so it is; on a multi-batch product the count lands elsewhere, the product total reads correctly first time, and the deficit sits on its own batch until something touches *that* batch. The deficit is permanent either way, and the silent-absorption case is intermittent rather than universal. (b) **The server is already disagreeing on this batch, today.** Stage 0 arithmetic forgives the deficit per push, so after the first `+2` the server holds 2 while the client holds 0, and the gap widens by the deficit on every count — this is A-217 live, not hypothetical. (c) **A compensating movement must be inbound `+N`, not a `shrinkage` row.** An oversell means the ledger was short of *inbound*: six units left a batch that logged four, so the missing two are receipts that were never recorded. A negative row would take the sum to −4, i.e. the opposite of the fix, and `shrinkage` would additionally land it in `getStockLosses()`'s reason matching and present an unrecorded receipt as a loss. The 2026-10-10 derived-quantity spec says "shrinkage" in its own Stage 4 bullet and in "One behaviour change, stated plainly"; **that wording is wrong and this entry inherited it.**
- **Why:** this is the deliberate behaviour change in the derived-quantity design (`docs/FIXED_BUGS.md`, "Derived stock quantity, Stage 1") seen from the counting screen. One floor over the sum carries an oversell's deficit forward, so the next inbound pays the deficit off before it adds anything. The pre-Stage-1 per-movement floor forgave the deficit instead, and that count stuck first time. Not a defect in the arithmetic — the arithmetic is doing what it was asked to — but the user-visible consequence was not traced when the trade-off was accepted.
- **Stage 1 shipped 2026-10-14** (`docs/FIXED_BUGS.md`, "A-212 / A-265 stage 1"): the deficit is now derived from the log by `getBatchDeficits()`, the oversold alert reports what is actually owed instead of matching a reason string in a 30-day window, and the counting screen names each short product and says a count will pay the shortfall off before it adds anything. Nothing about any write changed, so the defect itself is untouched — it is merely visible now, which is what every later stage needs as its field signal.
- **Fix:** designed in `docs/superpowers/specs/2026-10-14-oversell-compensating-movement-design.md`. When `deductFromBatch()` oversells a batch, write an inbound `+N` `adjustment` carrying `reference_type = "oversell"` in the same transaction, so the log never sums below zero, the deficit becomes a visible and syncing ledger fact, and the floor stops carrying anything. Reusing `adjustment` with a reference type — the `PRODUCT_IMPORT_REFERENCE_TYPE` pattern — avoids a new `movement_type` that twelve readers would mislabel and every shipped bundle would not know; no schema change, so `npm run test:schema` has nothing to check.
- **Decide before fixing:** it changes what the stock ledger says happened, so it is the owner's call, not a correctness fix to be applied quietly. The interim mitigation is to tell staff that a shortfall-carrying batch needs the deficit counting through — which nobody should have to know.
- **Scale:** one batch across all five stores today (the A-264 query finds it with `quantity = 0 AND log_sum < 0`). It grows by one every time a stale on-screen count lets a cashier oversell, so it is a slow accumulation rather than a one-off.

#### A-264. `client/` — a legacy batch whose stock has reached zero cannot get its unlogged units back, because nothing distinguishes it from an ordinary empty batch
- **Found:** 2026-10-14, in the adversarial vet of the derived-quantity Stage 1 change (`docs/FIXED_BUGS.md`, "Derived stock quantity, Stage 1"). Not a regression from it — the pre-Stage-1 incremental write had the same blind spot from the other direction — but Stage 1 is what makes the boundary exact, so it is worth stating.
- **What's wrong:** the A-148 carve-out is judged as `stored > the log's inbound total before this change`. That is the best test available from data the device holds, but it expires, and **this entry twice stated the boundary wrongly — corrected 2026-10-14 by an independent review.** Write `stored = U + Σlog` where `U` is the unlogged residue and `Σlog = inbound − outbound`; the test `stored > inbound` reduces to **`U > cumulative outbound`**. The inbound cancels. So the batch leaves the carve-out the moment its outbound total overtakes the residue, and on a batch that has since had a *logged* delivery that happens **while stock is still on the shelf** — not "once `stored` reaches 0", which is only true for a batch with no logged inbound at all.
- **Worked example, pinned in `client/__tests__/batch-quantity-recompute.test.ts`:** a legacy batch holding 100 unlogged units receives a logged delivery of 200 (reads 300, correct) and sells 150 (reads 150, correct). The next sale of 10 takes cumulative outbound to 160, past the residue of 100: the batch rebuilds to **40** where the shelf holds **140**. One hundred units written off, propagating to every device as the movement arrives. The same shape ends A-264's own repair case: 100 → sell 95 → find 10 reads 15 correctly, then three more sales take it to **0** where 8 units remain.
- **Measured against production, read-only, 2026-10-14, and the exposure is zero.** Across all five store groupings (2,657 + 2,101 + 2,253 + 1,416 live batches plus 10 unscoped): `unlogged_opening_stock` 0, `carve_out_now` 0, `unaccounted_units` 0. Not one batch on any live store holds stock its inbound movements cannot account for, so there is no residue anywhere for this to lose. One batch on `571582a9` matches the `quantity = 0 AND log < 0` shape, which is the upper bound's known false positive — an ordinary oversell, since that store has no unlogged stock to decay. The oldest batches on the two trading stores post-date `a36b00e7` (2026-09-19), which is consistent: imports have logged a movement per batch since then. **Consequence: Stage 4 is not urgent, and A-213's endpoint can be deleted rather than kept for a class that is empty.** Re-measure before concluding that permanently — a restored backup or an older import could reintroduce the class.
- **Worked example:** a pre-`a36b00e7` import batch holds 100 units with no movement row. 100 are sold (log `−100`, stored 0, correct). A customer returns 100: the log sums to 0, so the batch rebuilds to **0**, where the shelf holds 100. The same arithmetic reaches every other device as the movements arrive.
- **Why it is not fixed here:** the residue — `stored − MAX(0, Σ log)` at the moment the batch was still inside the carve-out — is not written down anywhere, and by the time it matters the number is gone. Nor is this a regression: the pre-Stage-1 incremental model had the same blind spot from the other direction. "Once a carve-out, always a carve-out" needs state the row does not have. Guessing from the log is not available either: a batch drifted *above* its log by the A-197 class and a decayed legacy batch are indistinguishable by `stored`, `Σ log` and inbound alike, which is exactly the ambiguity the spec's Stage 4 exists to remove.
- **Fix:** the spec's Stage 4 `opening_quantity` — a nullable column holding the unexplained residue, backfilled server-side as `MAX(0, quantity − SUM(log))` for batches with no inbound movement, pulled down as immutable server-authoritative truth, with `onHand = opening_quantity + Σ log`. Cross-repo schema change (root `AGENTS.md` §5). It also dissolves A-213's retirement condition, so the two should ship together.
- **Exposure:** bounded to batches whose opening stock has no movement row — imports before `a36b00e7` (2026-09-19) and the rest of the A-148 class. Measured at zero (above). No telemetry would show it if it returned: `unreconstructable` counts only batches still *above* their inbound, so one that has already decayed is invisible, which is why the query is recorded here rather than left to be re-derived.
- **The query**, read-only, to re-run in phpMyAdmin with the `SET` in the same block (root `AGENTS.md` §7 — `created_at` is a `TIMESTAMP` and converts on read):
  ```sql
  SET time_zone = '+00:00';

  SELECT p.store_id, COUNT(*) AS live_batches,
         SUM(CASE WHEN COALESCE(m.inbound,0) = 0 AND sb.quantity > 0 THEN 1 ELSE 0 END) AS unlogged_opening_stock,
         SUM(CASE WHEN sb.quantity > COALESCE(m.inbound,0) THEN 1 ELSE 0 END) AS carve_out_now,
         SUM(CASE WHEN sb.quantity > COALESCE(m.inbound,0) THEN sb.quantity - COALESCE(m.inbound,0) ELSE 0 END) AS unaccounted_units,
         SUM(CASE WHEN sb.quantity = 0 AND COALESCE(m.total,0) < 0 THEN 1 ELSE 0 END) AS decayed_upper_bound,
         MIN(sb.created_at) AS oldest_batch, MAX(sb.created_at) AS newest_batch
    FROM stock_batches sb
    JOIN products p ON p.id = sb.product_id
    LEFT JOIN (SELECT stock_batch_id,
                      SUM(CASE WHEN quantity > 0 THEN quantity ELSE 0 END) AS inbound,
                      SUM(quantity) AS total
                 FROM stock_movements WHERE deleted_at IS NULL
                GROUP BY stock_batch_id) m ON m.stock_batch_id = sb.id
   WHERE sb.deleted_at IS NULL
   GROUP BY p.store_id;
  ```
  Scoping mirrors `StockDivergenceService::serverFingerprint()` (batches through `products.store_id`, `deleted_at IS NULL`, no `is_active` filter) so the figures are comparable with the admin panel's own.

#### A-248. `laravel-server/` — a legacy row with no `store_id` pushed from a device whose active store has changed is stamped with the **wrong** store, silently moving products between tenants
- **Found:** 2026-10-12. The owner runs two stores (`571582a9` "Nest Pharmacy", `68e4c0e5` "Agidi") and signed into the second on `DRX-HO4QM3TWU`, a till previously used for the first. The Device Stock Agreement panels then showed a **matched signed pair**: store 1's devices at 2628 batches vs cloud 2626 (**+18**), store 2's `DRX-ZKI5K81UG` at 1952 vs cloud 1954 (**−18**). Same two batches, same 18 units, opposite signs — two batches counted under one store by the devices and under the other by the server.
- **Mechanism.** `normalizePushPayload()` (`SyncController.php:1810-1817`) backfills `store_id` from **the pushing session's active store** for any INSERT on a `STORE_ID_BACKFILL_TABLES` table whose payload has none — and `products` is on that list (`:2004-2012`). `_sync_queue` is **not store-scoped** (`base-helpers.ts:506-514` selects the whole queue; `queue-state.ts:64` counts it unscoped), so a device carries one store's backlog into whatever store is active next. A legacy product row with a NULL local `store_id`, queued from store 1 and pushed while store 2 is active, is therefore stamped `store_id = store 2`. Its `stock_batches` rows are not: `stock_batches` is absent from the backfill list and the client sets their `store_id` itself. The product has changed tenant; its batches have not.
- **Why the panel shows it as ±18 rather than as an error:** the client's fingerprint counts batches by `stock_batches.store_id` and the server's by the owning product's `store_id` (A-246), so a product that crossed stores makes one store read high by exactly its batches' units and the other read low by the same amount. The arithmetic mismatch in A-246 is what *reveals* this; the mis-stamped product is the underlying data defect.
- **Consequence:** silent cross-tenant movement of catalogue rows, repeating every time a device with legacy queued rows is used under a different store of the same owner. The owner sees stock totals that no sync can reconcile. Nothing is logged — the push succeeds.
- **CONFIRMED 2026-10-12 against production (read-only SELECT).** Exactly two products, 18 units, matching the panel's ±18 to the unit: `2db0a273-8619-4904-9d18-6f2b606f3def` "swibetic card" (14 units) and `2e084a56-6bd6-4375-a2c4-e29b88761fb0` "pure heaven can" (4). Both carry `products.store_id = 68e4c0e5` (store 2) while every one of their `stock_batches` rows carries `571582a9` (store 1). Direction of the corruption is therefore store 1 → store 2 on the product row only, which is what the active-store backfill does. The blast radius is two rows, not the catalogue.
- **Direction settled 2026-10-12.** Both products were created `2026-09-25 09:03:09`, in the same second as their first batch — store 1's registration day and its initial catalogue import. Store 2 was not registered until 2026-10-05, so neither product can have originated there: **store 1 is correct and the `products.store_id` value is the corrupted side.** Both rows carry `_version = 12`, so the repair must write 13 or a device still holding 12 will be accepted and revert it (the same mechanism as A-245, fixed 2026-10-18 — see `docs/FIXED_BUGS.md` A-276).
- **Verify (read-only, both stores):** `SELECT p.id, p.name, p.store_id AS product_store, b.store_id AS batch_store, SUM(b.quantity) AS units FROM products p JOIN stock_batches b ON b.product_id = p.id WHERE p.store_id <> b.store_id GROUP BY p.id, p.name, p.store_id, b.store_id` — two products totalling 18 units confirms it. Run `SET time_zone = '+00:00';` first if using phpMyAdmin (§7).
- **Mechanism narrowed to the client claim path, not the server backfill (2026-10-12).** The snapshot taken before the repair shows both rows at `updated_at = 2026-10-08 17:33:24` — the same second, and **two days after** `4f90f06a` (2026-10-06) restricted the server's `store_id` backfill to INSERTs only. A server-side backfill therefore cannot be what stamped them. What fits is (a) below: on 2026-10-08 these two products were edited on a device with store 2 active, their local `store_id` was NULL, and `update()` stamped the active store into both the row and the outgoing payload, which the server applied verbatim because `:1818` only rejects stores outside `$allowedStoreIds` — and for an owner that is every store they own. **The fix must therefore target the client claim path and the owner-scope check; restraining the server backfill would not have prevented this incident.**
- **The client-side recurrence path the server fix does not cover (2026-10-12 review).** `update()`/`softDelete()` stamp the **active** store into any local row whose `store_id IS NULL`, and into its push payload (`base-helpers.ts:128-131, 289-292`); the server then applies that explicit value via `forceFill` because `:1818`'s check only rejects stores outside `$allowedStoreIds`, and for an owner that set is *every* store they own. **This is the path that actually moved two products between stores in production, and it is still open.** A second path — `backfillStoreIdOnLegacyRows()` claiming NULL rows with an unordered `(SELECT id FROM stores LIMIT 1)` — was **fixed 2026-10-12** (it now skips unless the device holds exactly one store); see `docs/FIXED_BUGS.md`, "A-248 (part b)".
- **Correction on timing:** the stamp on these two rows most likely came from the **pre-2026-10-06 UPDATE path** — `4f90f06a` restricted the backfill to INSERTs one day after store 2 was registered — not from the INSERT branch. A bare UPDATE from a store-2 session can no longer re-stamp an existing row, so moving a device off store 2 guards against a path that is already closed; (a) and (b) above are the live ones.
- **Fix.** Never infer `store_id` from the active store for an **existing** record: the `INSERT` branch at `:1812-1815` should only backfill when the row is genuinely new to the server, and an existence-probe-flipped INSERT (`:321-337`) must not be treated as new — it already unsets `store_id` for exactly this reason at `:333-334`, which is the right instinct applied in only one of the two places. Longer term the queue should carry the store it was written under and refuse to push rows belonging to a different one; §11 applies, so the payload needs a new field rather than a reinterpreted one.

#### A-247. `client/` — a till whose OS clock is hours fast writes future-dated rows, and nothing detects or corrects it
- **Found:** 2026-10-12. The admin store-detail Recent Activity list showed rows reading "7 hours from now" alongside correct ones. **Cause established** from `DRX-HO4QM3TWU`'s own device report: every device-generated timestamp in it is **7h59m ahead of the server's**. The report self-reports `Last sync: 2026-10-12T20:14:15Z` and crashes at `19:30:59Z`; Sentry, which timestamps server-side, recorded those same crashes at `11:32:04Z`. The offset is not a round number, so it is a mis-set/drifted OS clock, not a timezone configuration.
- **Why it reaches the server:** client-generated `created_at`/`updated_at` ride the push payload, so a skewed clock writes future timestamps straight into MySQL. The mixed output in one activity list is simply rows from a skewed device interleaved with rows from correct ones — not two code paths, which was the first guess here and was wrong.
- **Consequence, and it is not cosmetic:** every row that till writes is dated ~8 hours ahead, **including sales**. Anything sold after ~16:00 local is attributed to the next calendar day, so trading-day counts, daily revenue, AOV and any Z-report on that store are already wrong — silently, and in the direction nobody checks. Secondary: a future-dated `updated_at` keeps satisfying every other device's `updated_at > watermark` filter until the clock catches up, so those rows are re-pulled on every round for ~8 hours.
- **What exists today:** `stores.last_monotonic_time` and the `LicenseGuard` anti-backdating logic defend the *subscription* against a clock moved backwards. Nothing defends *data* against a clock moved forwards, and no surface warns the operator.
- **Fix:** the server already knows the truth. It returns its own time on every sync response, so the client can compare and (a) surface a visible warning on the till when the skew exceeds a minute or two, and (b) report it once per session with `area: clock-skew` so the fleet is auditable. Do **not** silently rewrite the device's timestamps — §11: rows already written with skewed values exist in the field and the server must keep accepting them. A repair for already-stored rows is a separate question and needs the skew per device, which is why (b) matters.
- **Owner's decision, 2026-10-18: the already-written rows will NOT be repaired. Prevention only.**
  So this entry's remaining scope is exactly the fix above — the on-device skew warning and the once-per-session
  `area: clock-skew` report — plus the server-side flag (see `laravel-server/AGENTS.md`, clock-skew boundary check):
  accept a future-dated `created_at`/`updated_at`, never clamp or reject it, and surface it in `sync_failures` with
  reason `clock_skew`. Do **not** propose a timestamp repair for the stored rows again. The consequence is accepted
  and understood: trading-day counts, daily revenue and AOV for the days `DRX-HO4QM3TWU` traded before 2026-10-12
  are permanently ~8 hours shifted for sales after ~16:00 local, in both Nest stores that device served.
  The repair was declined because the reporting window has passed and a production write to `sales.created_at`
  carries more risk than the wrong numbers on historical days.
- **Status: the skew was real and is now gone on that device; the rows it wrote are not.** Confirmed by separating live from stored values in the same report: the filename uses `localStamp(new Date())` (`export-filename.ts:17,37`) and read `1318` local, correct against a real 12:18Z, while `getLastSyncTime()` (stored) read `20:14:15.657Z` and `readSyncOutcome()` read `20:14:16.098Z`. The decisive pairing is that **the server recorded that same round as `12:15:14+00:00` in `_sync_state`** — one sync, two clocks, 7h59m apart. The till's clock now agrees with real time to within a minute. So this is a *historical* skew whose damage is already committed, not an ongoing one.
- **Residue a resync does not clear.** (a) Rows written during the skew keep their future timestamps — that is what the future-dated activity rows are, and if any `sales` row is among them its revenue is booked on the wrong trading day. (b) `localStorage`'s `LAST_CHECK_KEY` holds a future value. **Fixed 2026-10-14** (`docs/FIXED_BUGS.md` A-234): the guard is now `isIntervalElapsed()`, which reads a future stamp as due, so a fast clock no longer suppresses the daily health check and `healStockIntegrity()` with it. Before that it did, for as long as it took real time to pass the stored value — about eight hours here, and permanently on a clock that had been reset. `forceFullResync()` still does not touch localStorage, and the stamp stays wrong until it is overwritten; it just no longer decides anything.
- **Blast radius measured 2026-10-12 (read-only).** `sales`: **0 rows** future-dated — no revenue is mis-attributed, which was the only serious risk. `activity_logs`: **224 rows**, spanning `17:19:32`–`20:12:41` device-time (≈ 09:20–12:13Z real). **224 is a floor, not a total:** the query tested `created_at > UTC_TIMESTAMP()`, so rows written earlier in the skew have since fallen into the past and are invisible to it, and no per-row true time is recoverable.
- **Ruling: do not repair the affected rows.** `activity_logs` is the audit trail; rewriting its timestamps to a guessed offset makes it less trustworthy, not more, and §11 applies — rows already in the field must stay readable as written. The practical cost is that those entries sort wrongly until real time passes the stored values, then read as past events at the wrong hour. **A future reader reconstructing 2026-10-12 from this store's activity log should know that roughly 224 entries from `DRX-HO4QM3TWU` are ≈7h59m ahead of when they happened.**
- **Operator action:** enable automatic time sync on every till. `DRX-HO4QM3TWU` was ~8h fast up to ≈12:15Z on 2026-10-12 and is now correct; how long it had been skewed is unknown, and the rest of the fleet is unaudited.
- **A backwards clock cannot hide a row from the pull, measured read-only against production 2026-10-14.** Worth writing down because the opposite is the obvious fear and it is wrong: `applyPullCursor()` (`SyncController.php:977`) filters on `_synced_at > watermark OR updated_at > watermark` for any table that has `_synced_at`, falling back to `updated_at` alone for one that does not. **All 29 tables in the pull list carry `_synced_at` in both the production and dev schemas** (`information_schema` says 34 tables have it per database; every pulled table is among them, including `stock_movements`, `stock_batches` and the conditionally-created `prescriptions`/`prescription_items`). The server stamps `_synced_at` itself on every accepted push, so a row carrying a nonsense `updated_at` still matches, sorts first under `ORDER BY updated_at`, and is delivered once. The query to re-check, which needs no selected database: `SELECT table_schema, table_name FROM information_schema.columns WHERE column_name = '_synced_at' AND table_schema NOT IN ('mysql','information_schema','performance_schema','sys')`. Note `DATABASE()` is NULL in a phpMyAdmin tab opened at server level, which returns zero rows and reads exactly like a missing column.
- **What a wrong clock does still break**, in descending order of cost: (1) **trading-day attribution**, measured in this entry; (2) **timestamp-decided conflicts** — `resolveUpdateConflict()`'s fallback compares `updated_at` when a row has no version tracking, which is the `stale_timestamp` refusal class, so a backwards-clock device's edits always lose; (3) **guards comparing a stored stamp to `Date.now()`** — the *silent-skip* half is closed (`docs/FIXED_BUGS.md` A-234): a future or unreadable stamp now reads as due, so a wrong clock can no longer switch the daily health check off. What replaced it is noise rather than silence, and is stated in that entry: on a till whose clock stays ahead, the stamp it writes is future again, so the check runs on **every app open and reconnect** until the clock is corrected. Two persisted guards outside the health check are logged separately as A-267. The clock watermark the licence guard already keeps (`last_monotonic_time`, `licensing-manager.ts`, with its online-only recovery and A-191's lockout case) is the nearest thing to a trusted floor this codebase has; generalising it into the sync path is the shape any fix should take, and `docs/superpowers/specs/2026-10-08-license-clock-recovery-design.md` is the prior art.
- **If a re-stamp repair is ever written:** root `AGENTS.md` §7 — never `NOW()`. Two previous attempts to bump `updated_at` that way never propagated, because this box's MySQL runs ~4h behind UTC and the new stamp landed in the past relative to the watermark it was meant to clear.

#### A-217. `laravel-server/`+`client/` — a clamped batch's stored quantity is clamped over the whole log on the client and over one push on the server, so the two can still disagree
- **Found:** 2026-10-10, in the review that produced A-215/A-216.
- **Half fixed, 2026-10-13 (Stage 1).** The client no longer replays per movement: it holds `MAX(0, Σ log)` (`docs/FIXED_BUGS.md`, "Derived stock quantity, Stage 1"). A-217 is the interim state until that ships.
- **Fix:** make one definition authoritative. The server should replay the log in order with the per-movement floor exactly as the client does (the ordering problem `client/AGENTS.md` describes for `created_at` has to be solved first — `rowid` is local-only), or the clamped shortfall should be recorded explicitly instead of being lost in a `max()`. Out of scope for A-215/A-216, which deliberately changed neither formula.

#### A-188. `client/` — `no such table: permission_groups` on one device, **mechanism unconfirmed** (do not treat the obvious explanations as the cause; three are already ruled out)
- **Found:** 2026-10-08, triaging Sentry `DUMOSRX-CLIENT-1P` — 3 events, 1 user, culprit `/inventory/:tab`. Logged deliberately as unconfirmed: the telemetry is real, but the code-side mechanism could not be established and is not worth guessing at.
- **Location:** unknown. The query sites are `client/lib/db/queries/permission-groups.ts` and `client/lib/hooks/use-permission-groups.ts`; the table is declared in `client/lib/db/schema.ts` (`CREATE TABLE IF NOT EXISTS permission_groups`, the fourth-from-last statement in `SCHEMA_SQL`).
- **Ruled out, so nobody re-walks these:**
  - **"The local schema predates the table and nothing creates it."** Every path that opens a database runs `SCHEMA_SQL` before anything can query it: `initDatabaseInternal()` on both the Tauri and sql.js branches, `rehydrateFromIndexedDb()` on writer-lock promotion, and `restoreDatabase()` (which also re-runs `runSchemaMigrations()`, specifically so an older backup comes up current). `query()`/`execute()` each `await initDatabase()` when `db` is null, so there is no pre-init read window.
  - **"A `SYNC_COLUMN_MIGRATIONS` ordering problem."** That list only `ALTER TABLE ... ADD COLUMN`s, and `runSchemaMigrations()` runs strictly *after* `SCHEMA_SQL`, so it cannot be what creates the table and cannot run before it exists.
  - **"The sql.js single-blob abort."** `SCHEMA_SQL` is handed to sql.js as one `db.run()`, and a throwing statement silently skips every later statement including `CREATE TABLE`s — the hazard `schema.ts`' own comment at the top of the index section documents, and the reason `READ_PATH_INDEXES` lives in `schema-migrations.ts` instead (see A-6 in `docs/FIXED_BUGS.md`). The only candidate trigger in the blob is `CREATE INDEX idx_sync_conflicts_unresolved ON _sync_conflicts(table_name, record_id, resolved_at)` at a line *before* `permission_groups`, which would abort the rest on a device whose `_sync_conflicts` lacks `resolved_at`. Checked: `_sync_conflicts` and that index shipped in the same commit (`ea1fcc41`), the table was never released without `resolved_at`, and no device can be in that state. In the web branch the enclosing `try` also falls back to a *fresh* database on any throw, which would have every table.
- **A latent hazard found while ruling the above out, not a bug today:** `_sync_conflicts` has **no entry in `SYNC_COLUMN_MIGRATIONS`**, and its index sits inside `SCHEMA_SQL` naming three of its columns. The moment a fourth column is added to that table and referenced from that index, every pre-existing local database aborts the schema blob at that line and loses **every one of the twenty `CREATE TABLE`s after it** — `customer_payments` through `supplier_payments`, i.e. `stores`, `users`, `audit_logs`, the whole procurement and loyalty set, `feedback`, `stock_movements`, `payment_accounts`, `permission_groups`, `system_configs`, `requested_products` — with no migration able to recover them, because the recovery pass runs after the statement that aborted. Either move this index into `READ_PATH_INDEXES` alongside the seventeen already there, or add `_sync_conflicts` to `SYNC_COLUMN_MIGRATIONS` before touching it.
- **Consequence as it stands:** 3 events on 1 device, and whatever permission read triggered it failed on that device — `use-permissions.ts` has a documented fallback for a user with no synced `permission_groups` row, but a thrown "no such table" is not that path. Low volume, no known data loss.
- **Needs a repro before any fix.** What would settle it: the device's `SELECT name FROM sqlite_master WHERE type='table'` (which other tables are missing tells you *where* in `SCHEMA_SQL` it stopped, if it stopped at all), the app version on that device, and whether it is the Tauri or the web/PWA build — the Tauri branch splits `SCHEMA_SQL` on `;` and runs each statement separately with no error swallowing, so a mid-blob abort there would have thrown out of `initDatabase()` loudly rather than leaving a half-built schema. Do not ship a defensive `CREATE TABLE IF NOT EXISTS` at the query site; that hides the mechanism without fixing it.

#### A-175. CI — FTP deploys are not atomic, so production serves a half-old, half-new code tree during every backend and web deploy

#### A-165. `client/` — a `forbidden` push refusal parks its queue row forever, but making it terminal (as first proposed) would destroy real data — the retry classification is correct, the unbounded parking is the bug
- **Location:** `NON_RETRYABLE_CONFLICT_REASONS` / `REASONS_SETTLING_SOURCE_ROW` in `client/lib/db/sync-engine/push.ts:22-41`; the reason is emitted at `SyncController::push()` `:258` (`authorizeInsertTarget()`), `:409` and `:630` (`authorizeChangeTarget()`, UPDATE and DELETE).
- **Investigated 2026-10-06; the originally-logged fix was attempted and deliberately reverted.** A-165 was first written up as "the same bug class as A-161, just add `forbidden` to both sets." That is **wrong**, and the reason is now verified in code rather than assumed: `forbidden` is genuinely transient in one real shape, so dropping and settling on it would silently destroy a legitimate row. `resolveOwnershipIdentity()` (`SyncController.php`) gives a **staff** session only `[$currentUser->store_id]`, while an **owner** gets every store they own — a strictly narrower envelope. `_sync_queue` is device-global and carries no identity (deliberately — see A-162), and `clearDatabaseForNewStore()` only runs when the selected store *differs* from the local one (`app/setup/use-onboarding.ts:426`), so a staff member signing in onto the owner's **current** store triggers no wipe and drains the owner's **other** stores' queued rows under the narrower scope. Those are refused `forbidden`, and the same frozen payload succeeds the moment the owner signs back in. This is exactly the case `client/AGENTS.md` already called out ("Still open, same incident, not fixed here" — a push rejected `forbidden` is retryable *and correctly so*), which the original A-165 writeup did not account for. A-163's fix narrows this path but does not close it, because it only wipes on a store *change*.
- **What is therefore still genuinely wrong:** the row is never abandoned. `recordSyncFailure()`'s backoff is capped, not bounded, so the row retries hourly forever and re-raises `Sync item stuck after 5 attempts` on every pass — and via pull's pending-local-edit skip, that parked row stops its record being pulled at all for as long as it sits there. That is the real defect, and it is the general "a permanently-parked queue row silently freezes its record's pulls" problem `client/AGENTS.md` records as unaddressed — not a missing set membership.
- **Unblocked 2026-10-07.** The stuck-data tooling now provides the somewhere-to-escalate-to this needed: per-device queue reports surface what is stuck, and `sync_commands` lets an operator retry it deliberately. Bounded abandonment can now be designed against a real escalation path rather than inventing one — but the two decisions it still needs are unchanged: what N should be, and whether abandonment is surfaced to the store owner.
- **Why not just fixed:** the correct fix is bounded abandonment (give up after N attempts, with the terminal-conflict ledger row as the durable trace, *without* marking the source row synced), plus not letting a parked row block its own pulls. That is a sync-engine design change affecting every retryable reason, not a one-line set addition, and it needs its own scoping — notably what N should be and whether abandonment should be surfaced to the user. Do **not** close this by adding `forbidden` to either set; `client/__tests__/push-settles-permission-denied-rows.test.ts` now pins both classifications side by side and fails if that is attempted.
- **Abandonment cannot be uniform across tables — owner's constraint, 2026-10-07.** "If a sale or stock movement is stuck and is abandoned later, that spoils the data and would cause problems later." This is correct and it narrows the design: a crash report or an audit-log row can be discarded with no business consequence, but a `sales`, `sale_items` or `stock_movements` row is a **business record whose only copy is on that device**. Abandoning one permanently loses revenue data or permanently falsifies on-hand stock — the exact class of corruption `.agents/AGENTS.md` §9 requires tests against. So "give up after N attempts" is only a valid terminal state for diagnostic tables. For business tables the terminal state must be **escalation to a human**, not discard: surface it to the operator (and to the store owner), keep the row, and provide a deliberate retry. That is what makes the stuck-data admin tooling a prerequisite for this work rather than a follow-up to it.
- **And the priority sits upstream of abandonment:** fix the causes. Every stuck row that never happens is one nobody has to adjudicate. Known culprits so far: A-168 (a session-relative refusal classified as terminal), PG-18 (refusals that record nothing at all), and the plan-gated queues that never drain (noted in the A-172 fix). A-176b and A-205, both causes of a permanently stranded row, are fixed — see `docs/FIXED_BUGS.md`.

#### A-168. `laravel-server/` — the two `permission_groups` privilege refusals are session-relative too, but are still reported as terminal `permission_denied`

## Engineering notes (tech debt / ongoing risk, not bugs)

These describe the current state of known architectural tradeoffs and performance ceilings — not defects, and not tracked toward a fix. Re-derive before relying on anything here; this isn't re-validated on every pass.

### Performance
- **`db.export()` per write** (web/PWA build): every `execute()` outside a transaction re-serializes the whole local database and writes it to IndexedDB — the dominant long-term scaling risk for a large catalog. Two of its biggest inputs are bounded (`audit_logs`' 730-day local retention window, coalesced multi-image save bursts), but the per-write export itself is unchanged; fixing it properly needs a different persistence model (incremental/OPFS).
- **First PWA install download:** `precache-manifest.json` lists ~399 URLs (~15 MB, including two 650 KB sql.js WASM binaries) fetched on first install — the single largest network cost on a metered connection.
- **Whole-catalog in-memory search:** `getProductsWithDetails()` loads the entire catalog and `product-database.tsx` fuzzy-searches it in memory (debounced). Fine to ~10k products; beyond that the transform+filter+sort chain is O(catalog) on the main thread every filter change.
- **`validateSync()`'s per-request chain** (`SubscriptionService`, `SystemConfig::getVal`, `PermissionGroupSeeder::ensureSeeded`, `enforceStaffLimits`) adds roughly 10 queries to every push/pull before any data is touched.
- **`getStockMovements()` with no window** loads the whole table when searching/filtering — a large result set in React state at scale, independent of indexing, since nothing narrows the predicate.

### Offline / sync
- **Server-side row-lock duration:** `SyncController::push()` holds `lockForUpdate()` locks for the whole outer transaction. Bounded with the current ~50-change batch size, but the first place to look if "Lock wait timeout" shows up in server logs.
- **Tab-lock residual notes:** `resetDatabase()`/`clearDatabaseForNewStore()` call `db.run()` directly rather than through `reserveDbSlot()`, so they can interleave with an in-flight yielding `query()`. A stolen-from tab only learns it lost the lock via the `steal-notice` broadcast, which a frozen tab receives only on thaw — `writerTab` stays `true` until that notice arrives.

### Architecture
- **One hand-rolled tenant-resolution copy remains:** `DashboardService` still hand-rolls the staff→owner lookup instead of a shared `Request`-free helper; `TenantScopingArchitectureTest` only scans controllers, not services.
- **File-size guideline exceeded by design in a few hot spots:** `client/lib/db/core.ts` (~1,640 lines), `laravel-server/.../SyncController.php` (~2,700 lines), and `client/app/setup/use-onboarding.ts` (~640 lines, flagged by `/code-review` during the A-156 fix) are all well past the project's 350-line guideline — known, not tracked toward a split. `getProductsWithDetails()`-style "load everything, filter in React" is the deliberate norm for catalog/customer/PO lists; where that stops being fine isn't written down anywhere.
- **The admin users/stores backend quartet was already over 350 lines before the 2026-10-08 admin-panel Phase 1 work touched it, and stayed over, not pushed over:** `AdminUserService.php` (546 → 610), `AdminStoreService.php` (565 → 584), `AdminStoreController.php` (518 → 557) and `AdminUserController.php` (549 → 552, the one of the four not called out when this phase started). None of the four were split, by design — the phase's rule was that only a file it pushed *past* 350 gets split, and all four were already past it. Every class the phase actually created (`Filters/UserListFilters.php`, `Filters/StoreListFilters.php`, `Support/ListSortResolver.php`, `Support/QueryInput.php`, `AdminStoreReferrerService.php`) is well under the limit.
- **Two client-side sale-recording paths exist:** `recordSaleItemStock` (POS/online orders) and `local-database.ts::createSale` (demo seeding only) — the second still writes `stock_batches.quantity` via a raw `UPDATE` rather than through `update()`, so a demo-seeded batch is the one batch the version model never saw.
- **`composer audit`/`npm audit` are not run in CI.**
- **`sw.js` has no automated test coverage**, despite two prior cache-poisoning fixes.
- **The admin list-sort pagination-stability tests cannot fail under the test suite's SQLite engine (found 2026-10-08, admin-panel Phase 1 final review).** `AdminListSortingTest::store_pagination_is_stable_under_a_tie_heavy_status_sort` and `::user_pagination_is_stable_under_a_tie_heavy_role_sort` exist to pin the deterministic `->orderBy('stores.id')` / `->orderBy('users.id')` tiebreaker on the explicit-sort paths in `AdminStoreService`/`AdminUserService`. The production code is correct and should stay. But `phpunit.xml` runs against SQLite `:memory:`, and SQLite returns tied rows in a deterministic rowid order across two sequential identical SELECTs — so removing both tiebreaker lines leaves **both tests still passing** (verified by doing exactly that during review). MySQL gives no such guarantee, so the defect the tests describe is real in production while the tests provide no regression protection against the tiebreaker being dropped later. Making them engine-agnostic needs a different approach than fetching two pages and comparing id sets.
