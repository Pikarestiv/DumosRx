## Open bugs awaiting a fix

#### A-231. `web/` — A-224 stopped the admin card rendering a server exception, but the raw text still reaches the production console and the telemetry POST
- **Found:** 2026-10-10, second adversarial review of the release batch.
- **Location:** `web/lib/api/base-client.ts:224` keeps `rawServerMessage` and feeds it to `:252`'s `console.error` (in production, not just dev), `:235`'s log buffer and `:261`'s `/logs/client-error` POST, both via `sanitizePayload()` (`web/lib/api/logger.ts:85-90`).
- **What's wrong:** `sanitizePayload` masks **by key name**. A-224's payload was a bcrypt hash and an encrypted till code embedded in the *value* of a SQL exception's `message`; `message` is not a sensitive key, so the value passes through verbatim. A-224's commit subject is true of the card and not of the console.
- **Consequence:** an authenticated admin's own browser console, and the telemetry store, still receive the material A-224 removed from the screen. Low severity on its own — but one keystroke away during a screen-share or a support call, which is exactly the setting an admin panel is used in.
- **Fix:** run the console and telemetry paths through the same gate as the rendered message, or sanitise by value shape as well as key name. Keeping the raw text for telemetry was deliberate (nothing should be lost from diagnostics), so the better answer is probably to send it to a field that is masked, not to drop it.

#### A-232. `client/` — two load-bearing comments in `stock-integrity.ts` state things that are not true
- **Found:** 2026-10-10, second adversarial review. Exactly the class of claim that caused today's other defects, so recorded rather than quietly corrected.
- **Location:** `client/lib/db/sync-engine/stock-integrity.ts:55-59`.
- **(a)** *"Depends on no movement ever being soft-deleted… Nothing soft-deletes one today."* False: the pull's UPDATE branch (`pull.ts:347-360`) writes `_deleted` for an existing `stock_movements` row **without reversing the delta it already applied**, so a server-side void does soft-delete one — which is why `deferred-stock-deltas.ts:80-89` and `pull.ts:252` exist at all.
- **(b)** The stated hazard is also backwards. A soft-deleted *inbound* movement leaves `batchQuantity > inboundTotal`, so A-215 already refuses it; a soft-deleted *outbound* one makes the fold write the quantity **up**, matching what the server derives. The comment warns of a destructive case that is handled and misses the behaviour that actually occurs.
- **(c)** `:55-56`'s *"the way both the pull and the server do"* asserts a cross-repo equivalence that does not hold: the pull floors per movement (`pull.ts:412`) while `SyncController::applyStockBatchDeltas` (`:1342-1347`) accumulates per batch across a whole push and applies one floored UPDATE. Related to A-217.
- **Why it matters:** a future agent reading "the first void-sale soft-delete would make a fold destroy stock" may act on a risk that is already closed, or trust an equivalence that is false.

#### A-233. `laravel-server/` — the repair's conditional update cannot fail, so `skipped: 0` does not mean what an operator would read it to mean
- **Found:** 2026-10-10, second adversarial review.
- **Location:** `app/Services/Sync/HealthSyncReconciliationRepairService.php:240-260`.
- **What's wrong:** `$stored` is read under `lockForUpdate()` inside the transaction, so the row is held for the rest of it and nothing can change `quantity` before the `where('quantity', $stored)` update. The conditional therefore never fails in production. The lock is the real protection and it works; but commit `cdb5b50e` claims "a conditional update so a concurrent push is skipped and reported rather than clobbered", describing a mechanism that cannot fire, and `skipped` only ever counts **missing batch rows**.
- **Consequence:** not a safety defect — the lock does the job. But an operator reading `skipped: 0` will conclude no concurrent push was skipped, and that number cannot say otherwise. The test pinning it presumably passes by stubbing the lock away (SQLite compiles `lockForUpdate()` out).
- **Fix:** either describe the lock as the mechanism and drop the dead conditional, or keep the conditional and say in the output what `skipped` actually counts.

#### A-234. `client/` — A-223's guard silently disables the daily health check on a device with a corrupt stored timestamp
- **Found:** 2026-10-10, second adversarial review.
- **Location:** `client/lib/db/sync-engine/health-check.ts:101` — `if (!getLastSyncTime()) return;`.
- **What's wrong:** since A-223, an unparseable value returns `null`, so the device takes the "never synced" branch and skips the row-count deficit check **and `healStockIntegrity()`** entirely. Before the fix the value was truthy and the check ran — though the app was also crash-screened on every page, so nothing ran anyway.
- **Consequence:** small and self-healing — the first successful round re-stamps a valid value (`index.ts:188`) and the check resumes. Worth knowing because the auto-heal is the thing that silently stops.
- **Fix:** distinguish "never synced" from "cannot read the timestamp"; the latter should not suppress a health check that does not depend on the value.

#### A-239. `client/` — the device that asserted the A-214 zeros will double those 144 products when it pulls the repair's reversals
- **Found:** 2026-10-11, vetting what the A-214 repair does to each device. The biggest risk in this incident's tail and previously unlogged anywhere.
- **Location:** `client/lib/db/sync-engine/reconcile-quantities.ts:28-56` (`storeReconciliationMovementLocally`) against `pull.ts:403-423`.
- **What's wrong:** the asserting device seeded its own 144 `sync_reconciliation` rows locally with `_synced = 1` and **never applied their deltas** — correctly, since its own quantity was already the number it had asserted. Once its interrupted rebuild finished it therefore holds the true quantity against a movement log whose sum is zero. The repair's `sync_reconciliation_reversal` rows are new to that device, so they take the INSERT branch, which has no `movement_type` special-case, and their positive deltas land **on top of** a quantity that was never reduced.
- **Consequence:** that one device goes to roughly **2× on 144 products (~+13,104 over the cloud)** after its next sync — the inverse of what the owner is watching for. Batches with a logged opening movement are `diverged` and fold back on the next health check; batches with no opening movement (the A-148 class) are `unreconstructable`, so they stay doubled with no automatic repair at all. Under A-238 the fold can be up to 48 hours away.
- **Confirmed live, 2026-10-11:** `DRX-ZKI5K81UG` reports **64,765 against a cloud of 50,977 on store `571582a9` — +13,788**, which is the incident's own 13,104 plus 684 of ordinary drift, in a report taken *after* the 10/10 17:58 repair. No other arithmetic produces that number: a device that was merely offline through the window pulls the −13,104 **and** the +13,104 and nets to zero, so only a device that took the reversals **without** the incident deltas can sit one incident-size above cloud. **Two mechanisms can leave it in that state and the fingerprint cannot tell them apart:** (a) it is the asserting device, which seeded its own incident rows `_synced = 1` and never applied them; or (b) it pulled the incident movements while their `stock_batches` rows had not yet arrived and the deferred deltas were then lost — the A-197/A-229 class, which is this repo's most frequent defect and must not be assumed away. Attribution needs the device's own `_pending_stock_deltas` and movement log, read in a support session; the remedy is the same either way. Every other device on that store reads within +23. Note the same device reads exactly 0 against store `68e4c0e5`, so the condition is per-store, not per-device. Verified against production 2026-10-11: cloud `571582a9` is 2,626 batches / 50,977 units, the 144 reversals total +13,104, and `device_stock_reports.reported_at` puts both `ZKI5K81UG` (09:03) and `8DY6G5XH8` (08:09) **after** the 10/10 17:58 apply — so `8DY6G5XH8`'s +18 is a genuine post-repair agreement and `ZKI5K81UG`'s +13,788 is a genuine post-repair doubling. The other three devices' fingerprints predate the incident entirely and say nothing about their current state; each will net to zero when it next syncs, because it pulls both halves.
- **How to identify it in general:** after a sync, it is the device whose `device_stock_reports` row reads ~+13k **over** cloud while every other device reads ~0. Per A-214's own note it is the device on which a Force Full Resync was run minutes before Health Sync.
- **Fix / handling:** nothing that pushes its figures up — Health Sync is already refused, which closes the obvious wrong move. Read `window.__verifyStockIntegrity()` in a support session to see how many of the 144 are `unreconstructable`, then `window.__foldStockQuantities()` for the rest; the refused ones need a physical count. A general fix belongs with Stage 4's `opening_quantity`, which dissolves the `unreconstructable` class.

#### A-252. `laravel-server/` + `web/` — a device that stops reporting leaves a permanent "diverged" row, so the stock-agreement panel accumulates dead tills that can never clear
- **Found:** 2026-10-12. Clearing site data on a machine mints a new device id (it lives in `localStorage`), so the old id stops reporting forever while its last snapshot stays on screen. `DRX-Y8UK10GC3` is frozen at **+2689 units, 14:17**, having been replaced by `DRX-Z6H12KGXZ` — which agrees exactly. One real machine, two rows, one of them permanently and misleadingly red.
- **Location:** `StockDivergenceService::forStore()` (`:46-49`) selects the 50 most recent `DeviceStockReport` rows for the store with **no recency filter and no way to dismiss one**. The row is keyed on `(store_id, device_id)` and only ever updated by that device's own push, so an id that never pushes again never changes.
- **Consequence:** the panel's headline ("6 of 8 devices disagree with the cloud") degrades over time regardless of fleet health, and the worst-looking numbers are usually the deadest. It inverts the panel's purpose: an owner scanning it sees alarm from devices that no longer exist, and the live divergence that matters is buried among them. The same shape as an *unmeasured* device being scored as a disagreeing one — absence of a measurement is not evidence of disagreement.
- **Fix:** age the rows. Mark any report older than ~48h as stale and exclude it from the "N of M disagree" count (render it greyed with its age, rather than hiding it — a device that went quiet is itself worth seeing). An explicit "forget this device" action for a retired till is the companion, since a reinstalled machine legitimately changes id. `user_devices.last_synced_at` already gives the recency signal, and `ResolvesDeviceLabels` is already joined here.
- **Related:** every wipe or new browser profile adds an id permanently — this account reached 13 known devices on 2026-10-12 for perhaps five physical machines. Worth a thought about whether a device id should be derivable rather than random, but that is a bigger question and §11 applies.

#### A-251. `client/` — the Settings diagnostics panel has no nav entry, so it is unreachable by clicking even in the sessions that gate it
- **Found:** 2026-10-12. An impersonating admin could not find it; neither could a till-inspection session. The gate is correct and the door was never built.
- **Location:** `client/app/(dashboard)/settings/[tab]/settings-client.tsx:243-246` renders `<TabsContent value="diagnostics">` when `isTillInspectionSession() || isImpersonatedSession()`. `NAV_GROUPS` in `settings-tab-nav.tsx:46-135` has **no `diagnostics` item**, so no `<TabsTrigger>` with that value is ever rendered. The label exists in the title map (`settings-client.tsx:88`), which is what makes the omission easy to miss.
- **Consequence: undiscoverable, not unreachable.** `/settings/diagnostics` does work — `diagnostics` is in `ALL_SETTINGS_TABS` (`lib/constants/settings-tabs.ts:45`) and `canAccessSettingsTab()` returns true for either support session (`:94-96`) — but there is no trigger to click, so the only way in is to already know the URL. Support reaches for it during exactly the incident where it is needed, finds nothing in the rail, and concludes the feature is broken.
- **One trap when testing it, which cost a round here on 2026-10-12.** Typing the URL inside an *ordinary* logged-in session falls back to Appearance (`use-settings-tab-resolution.ts:62-65`), because the impersonation flags are written only by the handoff at `app/auth/callback/page.tsx`. They live in **localStorage**, so they survive tabs and reloads — but they are never present in a session the user logged into normally. Verifying this panel means arriving through the admin panel's impersonation link, not opening the URL in a session that happens to be signed in.
- **Why it slipped:** this is §9's named failure exactly — the session gate was verified, the nav's visibility list was not. The `/inspect` route works because it mounts the panel directly rather than through the tab nav, so the feature looked tested.
- **Fix:** add the item to `NAV_GROUPS` with visibility matching the panel's own condition, not `adminOnly` (an impersonating admin and an inspection session are not the same thing as a store admin). Then click to it in both session types before calling it done.

#### A-250. `client/` — the manual "Rebuild stock from movement history" button skips the completeness guard the automatic healer applies
- **Found:** 2026-10-12, while directing an owner to use it on a diverged till.
- **Location:** `client/components/settings/device-diagnostics.tsx:308` calls `foldStockQuantities()` directly. The guard lives one layer up, in `stock-auto-heal.ts`'s `skipReason()` (`:32-36`), which refuses the fold when `movementLogIsComplete()` is false or an inspection session is active — and only `healStockIntegrity()` consults it.
- **What's wrong:** the fold writes an absolute quantity derived from whatever movements the device currently holds. On a device mid-catch-up the log is known-incomplete, so the automatic path declines; the manual path, which an operator reaches during exactly the kind of incident where a device *is* mid-catch-up, does not. The more dangerous invocation has the weaker guard.
- **It also bypasses the inspection-session guard, on a page that advertises itself as read-only.** `skipReason()` refuses the automatic fold when `isTillInspectionSession()` is true; the manual button does not consult it. And the only surfaces that render this panel are gated to exactly those sessions — `settings-client.tsx:243` (`isTillInspectionSession() || isImpersonatedSession()`) and `app/inspect/page.tsx`, whose own copy reads *"Read from its local database; nothing is changed by opening this page."* True of opening it; false of the Rebuild button it hosts. An admin inspecting a customer's till can write to that till's stock from a screen that promises it cannot.
- **Consequence:** an operator following support advice can rewrite every diverged quantity on a partially-synced till from a partial log. Local-only (raw `execute()`, nothing queued), so it is recoverable by a resync plus another fold — but it will look like the repair made things worse, and the audit row records a correction that was never real.
- **Fix:** move `skipReason()` into `foldStockQuantities()` (or call it from the dialog), so both entry points share one gate. The confirm dialog should name the reason when it refuses rather than hiding the button.

#### A-249. `client/` — `_sync_state` has no store dimension while the pull is scoped to one store, so a two-store device declares the inactive store synced without ever receiving its rows
- **Found:** 2026-10-12, answering "does a force resync on one store resync the other store on the same PC?". It does not, and the reason is worse than the question.
- **Location:** `client/lib/db/schema.ts:274-280` — `_sync_state` is `PRIMARY KEY (table_name)`, with no `store_id`. Server side `resolvePullTenantScope()` (`SyncController.php:1193-1203`) narrows `storeIds` to the single `X-Store-Id` the client sends (`client/lib/api/client.ts:33`), and the window is stamped per table on completion (`pull.ts:546`, server `now()` from `SyncController.php:888`).
- **What's wrong:** one watermark per table, one store's rows per pull. A sync under store A pulls only store A, then advances `products.last_synced_at` to *now* — a claim that covers store B's rows too. The incremental filter is `_synced_at > X OR updated_at > X`, so every store-B row older than that stamp is permanently outside the window. The device cannot discover them again; nothing errors.
- **Consequence:** on a device used for two stores, whichever store is inactive is continuously declared synced while being starved. This is the straightforward explanation for `DRX-HO4QM3TWU` reporting **0 units across 0 batches** for store `68e4c0e5` while its windows read recent — store 2's rows fall outside a watermark that store-1 syncs keep pushing forward. `forceFullResync()` does not escape it: `DELETE FROM _sync_state` (`index.ts:60`) is table-keyed and therefore clears **both** stores' windows, then refills only the active store's and stamps every table to now — repairing the active store and leaving the other with a false watermark. Resyncing after each switch ping-pongs the damage rather than fixing it.
- **Fix:** key `_sync_state` on `(table_name, store_id)` — a schema change, so §11 applies: the old single-row-per-table form must keep working for devices that have not migrated, and a migration has to decide which store an existing row's watermark belonged to (safest: treat it as belonging to the device's active store and leave the others NULL so they pull from scratch).
- **Field evidence that the switcher is the trigger, and the whole chain (2026-10-12).** Aggregating `area: sync-pull-window` by device over 24h: `DRX-Y8UK10GC3` store 1 — 450 events; `DRX-HO4QM3TWU` store 2 — 136; `DRX-HO4QM3TWU` store 1 — 48. **Both offenders are the two devices that used the store switcher, each hitting it under both stores. The devices that only ever served one store (`DRX-OCGGTOPX2`, `DRX-8DY6G5XH8`) produced none.** The chain: a switch remounts the app → `requeueOrphanedRowsOnce()` mass-requeues every `_synced = 0` row as an INSERT (observed as 2 queued → 2683 across one switch) → each batch of 50 is refused `version_conflict` → every refusal calls `rewindPullWindow()` (`push.ts:519-521`) → `MAX_PULL_WINDOW_REWINDS = 3` is spent inside the first batch → the re-pull that would set `_synced = 1` is refused from then on (`RESTORE_SQL` never resets `rewind_count`) → the rows stay unsynced, get requeued, and conflict again indefinitely. A-248, A-249 and the rewind-exhaustion loop are three faces of one defect, and the switcher is what lights it.
- **It also pollutes the admin panel beyond the device itself.** A fingerprint row is written under whatever store was active at push time, so every device ever switched into a store leaves a row in *that* store's agreement panel reporting its partial copy. Observed 2026-10-12 on store `68e4c0e5`: **five of six rows were devices that serve store `571582a9`** (two Amawbia tills, the owner's laptop, a stranded Android till and a retired Mac), each disagreeing by a different amount, while the store's own device was merely 48 batches behind on newly received stock. The panel's headline becomes unreadable and the one row that matters is buried. Together with A-252 (no recency filter, no dismiss) this makes the panel actively misleading for any owner with two stores.
- **Symptom to recognise:** a device in this state reports a *stuck, wrong* stock fingerprint that no sync corrects — `DRX-Y8UK10GC3` sat at +2655 units across 2654 batches while in the loop. It reads as catch-up lag and is not; the device cannot converge until `_sync_state` is cleared. `forceFullResync()` is the only operator-side exit, because it is the one thing that resets `rewind_count`.
- **This is a broken shipped feature, not an operational footnote.** The store switcher (`store-context.tsx:316`, `header-store-switcher.tsx`) is sold on the enterprise plan and is the whole point of multi-store support; A-249 means it silently starves whichever store is not active, on every device that uses it. Telling an owner "don't switch stores" withdraws the feature. Prioritise accordingly — above A-206, which strands one device, where this one breaks the feature for everyone who has two stores.
- **Related observation, same incident, not yet explained:** on 2026-10-12 `DRX-HO4QM3TWU` reported **2 queued** under store 1 at 12:02 and **2683 queued** under store 2 at 12:24 — the queue grew by ~2681 across the switch. That is the mass-requeue shape `base-helpers.ts:525-530` warns about (rows whose `_synced` was never flipped back are treated as orphans by `requeueOrphanedRows()` on the next boot), and a store switch that remounts the app is a boot. Worth confirming whether a switch reliably mass-requeues, because if so every switch also costs a full re-push of the catalogue.
- **Until then:** one device per store. A device that must serve both needs a full resync after every switch, and the operator has to know the other store's watermark is now lying.

#### A-248. `laravel-server/` — a legacy row with no `store_id` pushed from a device whose active store has changed is stamped with the **wrong** store, silently moving products between tenants
- **Found:** 2026-10-12. The owner runs two stores (`571582a9` "Nest Pharmacy", `68e4c0e5` "Agidi") and signed into the second on `DRX-HO4QM3TWU`, a till previously used for the first. The Device Stock Agreement panels then showed a **matched signed pair**: store 1's devices at 2628 batches vs cloud 2626 (**+18**), store 2's `DRX-ZKI5K81UG` at 1952 vs cloud 1954 (**−18**). Same two batches, same 18 units, opposite signs — two batches counted under one store by the devices and under the other by the server.
- **Mechanism.** `normalizePushPayload()` (`SyncController.php:1810-1817`) backfills `store_id` from **the pushing session's active store** for any INSERT on a `STORE_ID_BACKFILL_TABLES` table whose payload has none — and `products` is on that list (`:2004-2012`). `_sync_queue` is **not store-scoped** (`base-helpers.ts:506-514` selects the whole queue; `queue-state.ts:64` counts it unscoped), so a device carries one store's backlog into whatever store is active next. A legacy product row with a NULL local `store_id`, queued from store 1 and pushed while store 2 is active, is therefore stamped `store_id = store 2`. Its `stock_batches` rows are not: `stock_batches` is absent from the backfill list and the client sets their `store_id` itself. The product has changed tenant; its batches have not.
- **Why the panel shows it as ±18 rather than as an error:** the client's fingerprint counts batches by `stock_batches.store_id` and the server's by the owning product's `store_id` (A-246), so a product that crossed stores makes one store read high by exactly its batches' units and the other read low by the same amount. The arithmetic mismatch in A-246 is what *reveals* this; the mis-stamped product is the underlying data defect.
- **Consequence:** silent cross-tenant movement of catalogue rows, repeating every time a device with legacy queued rows is used under a different store of the same owner. The owner sees stock totals that no sync can reconcile. Nothing is logged — the push succeeds.
- **CONFIRMED 2026-10-12 against production (read-only SELECT).** Exactly two products, 18 units, matching the panel's ±18 to the unit: `2db0a273-8619-4904-9d18-6f2b606f3def` "swibetic card" (14 units) and `2e084a56-6bd6-4375-a2c4-e29b88761fb0` "pure heaven can" (4). Both carry `products.store_id = 68e4c0e5` (store 2) while every one of their `stock_batches` rows carries `571582a9` (store 1). Direction of the corruption is therefore store 1 → store 2 on the product row only, which is what the active-store backfill does. The blast radius is two rows, not the catalogue.
- **Direction settled 2026-10-12.** Both products were created `2026-09-25 09:03:09`, in the same second as their first batch — store 1's registration day and its initial catalogue import. Store 2 was not registered until 2026-10-05, so neither product can have originated there: **store 1 is correct and the `products.store_id` value is the corrupted side.** Both rows carry `_version = 12`, so the repair must write 13 or a device still holding 12 will be accepted and revert it (A-245).
- **Verify (read-only, both stores):** `SELECT p.id, p.name, p.store_id AS product_store, b.store_id AS batch_store, SUM(b.quantity) AS units FROM products p JOIN stock_batches b ON b.product_id = p.id WHERE p.store_id <> b.store_id GROUP BY p.id, p.name, p.store_id, b.store_id` — two products totalling 18 units confirms it. Run `SET time_zone = '+00:00';` first if using phpMyAdmin (§7).
- **Mechanism narrowed to the client claim path, not the server backfill (2026-10-12).** The snapshot taken before the repair shows both rows at `updated_at = 2026-10-08 17:33:24` — the same second, and **two days after** `4f90f06a` (2026-10-06) restricted the server's `store_id` backfill to INSERTs only. A server-side backfill therefore cannot be what stamped them. What fits is (a) below: on 2026-10-08 these two products were edited on a device with store 2 active, their local `store_id` was NULL, and `update()` stamped the active store into both the row and the outgoing payload, which the server applied verbatim because `:1818` only rejects stores outside `$allowedStoreIds` — and for an owner that is every store they own. **The fix must therefore target the client claim path and the owner-scope check; restraining the server backfill would not have prevented this incident.**
- **Two client-side recurrence paths the server fix does not cover (2026-10-12 review).** (a) `update()`/`softDelete()` stamp the **active** store into any local row whose `store_id IS NULL`, and into its payload (`base-helpers.ts:128-131, 289-292`); the server then applies that explicit value via `forceFill` because `:1818`'s check only rejects stores outside `$allowedStoreIds`, and for an owner that set is *every* store they own. (b) `backfillStoreIdOnLegacyRows()` (`schema-migrations.ts:642-653`) runs on boot and stamps every NULL `store_id` with `(SELECT id FROM stores LIMIT 1)` — **no `ORDER BY`**, so on a device whose local `stores` table holds two of them SQLite's pick is arbitrary and may be the wrong one, silently, for every store-scoped table. Its comment ("this device's one pre-migration store") was true when written and is false on any multi-store device. Both paths are owner-side and neither is addressed by restraining the server backfill.
- **Correction on timing:** the stamp on these two rows most likely came from the **pre-2026-10-06 UPDATE path** — `4f90f06a` restricted the backfill to INSERTs one day after store 2 was registered — not from the INSERT branch. A bare UPDATE from a store-2 session can no longer re-stamp an existing row, so moving a device off store 2 guards against a path that is already closed; (a) and (b) above are the live ones.
- **Fix.** Never infer `store_id` from the active store for an **existing** record: the `INSERT` branch at `:1812-1815` should only backfill when the row is genuinely new to the server, and an existence-probe-flipped INSERT (`:321-337`) must not be treated as new — it already unsets `store_id` for exactly this reason at `:333-334`, which is the right instinct applied in only one of the two places. Longer term the queue should carry the store it was written under and refuse to push rows belonging to a different one; §11 applies, so the payload needs a new field rather than a reinterpreted one.

#### A-246. `laravel-server/` + `client/` — the Device Stock Agreement panel compares two differently-scoped counts, so a permanent small delta is arithmetic rather than drift
- **Found:** 2026-10-12, after the owner synced four devices on store `571582a9` and all of them resolved to the *same* `+18`. Three devices (`DRX-OCGGTOPX2`, `DRX-8DY6G5XH8`, `DRX-HO4QM3TWU`) reported identical fingerprints — 50998 units across **2628** batches against cloud 50980 across **2626**. Devices agreeing to the unit while the cloud differs by a fixed amount is the signature of a yardstick mismatch, not of drift.
- **Location:** `client/lib/db/sync-engine/stock-fingerprint.ts:24-27` counts `FROM stock_batches WHERE store_id = ? AND (_deleted = 0 OR _deleted IS NULL)`. `app/Services/Admin/StockDivergenceService.php:83-85` counts `whereIn('product_id', Product::withTrashed()->where('store_id', $storeId))->whereNull('deleted_at')`.
- **What's wrong:** one scopes on `stock_batches.store_id`, the other on the owning product's `store_id`. They are the same set only when every batch's product row exists and agrees. They differ for a batch whose product row is absent server-side, whose product belongs to another store, or which is soft-deleted server-side without `_deleted` having reached the device. `withTrashed()` means a *discontinued* product is correctly included (that was A-173's fix), so the surviving candidates are a missing/cross-store product row and an unpropagated server-side delete.

#### A-247. `client/` — a till whose OS clock is hours fast writes future-dated rows, and nothing detects or corrects it
- **Found:** 2026-10-12. The admin store-detail Recent Activity list showed rows reading "7 hours from now" alongside correct ones. **Cause established** from `DRX-HO4QM3TWU`'s own device report: every device-generated timestamp in it is **7h59m ahead of the server's**. The report self-reports `Last sync: 2026-10-12T20:14:15Z` and crashes at `19:30:59Z`; Sentry, which timestamps server-side, recorded those same crashes at `11:32:04Z`. The offset is not a round number, so it is a mis-set/drifted OS clock, not a timezone configuration.
- **Why it reaches the server:** client-generated `created_at`/`updated_at` ride the push payload, so a skewed clock writes future timestamps straight into MySQL. The mixed output in one activity list is simply rows from a skewed device interleaved with rows from correct ones — not two code paths, which was the first guess here and was wrong.
- **Consequence, and it is not cosmetic:** every row that till writes is dated ~8 hours ahead, **including sales**. Anything sold after ~16:00 local is attributed to the next calendar day, so trading-day counts, daily revenue, AOV and any Z-report on that store are already wrong — silently, and in the direction nobody checks. Secondary: a future-dated `updated_at` keeps satisfying every other device's `updated_at > watermark` filter until the clock catches up, so those rows are re-pulled on every round for ~8 hours.
- **What exists today:** `stores.last_monotonic_time` and the `LicenseGuard` anti-backdating logic defend the *subscription* against a clock moved backwards. Nothing defends *data* against a clock moved forwards, and no surface warns the operator.
- **Fix:** the server already knows the truth. It returns its own time on every sync response, so the client can compare and (a) surface a visible warning on the till when the skew exceeds a minute or two, and (b) report it once per session with `area: clock-skew` so the fleet is auditable. Do **not** silently rewrite the device's timestamps — §11: rows already written with skewed values exist in the field and the server must keep accepting them. A repair for already-stored rows is a separate question and needs the skew per device, which is why (b) matters.
- **Status: the skew was real and is now gone on that device; the rows it wrote are not.** Confirmed by separating live from stored values in the same report: the filename uses `localStamp(new Date())` (`export-filename.ts:17,37`) and read `1318` local, correct against a real 12:18Z, while `getLastSyncTime()` (stored) read `20:14:15.657Z` and `readSyncOutcome()` read `20:14:16.098Z`. The decisive pairing is that **the server recorded that same round as `12:15:14+00:00` in `_sync_state`** — one sync, two clocks, 7h59m apart. The till's clock now agrees with real time to within a minute. So this is a *historical* skew whose damage is already committed, not an ongoing one.
- **Residue a resync does not clear.** (a) Rows written during the skew keep their future timestamps — that is what the future-dated activity rows are, and if any `sales` row is among them its revenue is booked on the wrong trading day. (b) `localStorage`'s `LAST_CHECK_KEY` holds a future value, and `health-check.ts:105` computes `Date.now() - lastChecked < CHECK_INTERVAL_MS`; a future stamp makes that difference negative, so **the daily health check and `healStockIntegrity()` are suppressed on that device until real time passes the stored value** (~8 hours). `forceFullResync()` does not touch localStorage. Same shape as A-234/A-238: a stored timestamp the guard cannot distinguish from a legitimate one.
- **Blast radius measured 2026-10-12 (read-only).** `sales`: **0 rows** future-dated — no revenue is mis-attributed, which was the only serious risk. `activity_logs`: **224 rows**, spanning `17:19:32`–`20:12:41` device-time (≈ 09:20–12:13Z real). **224 is a floor, not a total:** the query tested `created_at > UTC_TIMESTAMP()`, so rows written earlier in the skew have since fallen into the past and are invisible to it, and no per-row true time is recoverable.
- **Ruling: do not repair the affected rows.** `activity_logs` is the audit trail; rewriting its timestamps to a guessed offset makes it less trustworthy, not more, and §11 applies — rows already in the field must stay readable as written. The practical cost is that those entries sort wrongly until real time passes the stored values, then read as past events at the wrong hour. **A future reader reconstructing 2026-10-12 from this store's activity log should know that roughly 224 entries from `DRX-HO4QM3TWU` are ≈7h59m ahead of when they happened.**
- **Operator action:** enable automatic time sync on every till. `DRX-HO4QM3TWU` was ~8h fast up to ≈12:15Z on 2026-10-12 and is now correct; how long it had been skewed is unknown, and the rest of the fleet is unaudited.

#### A-212. `client/` — the "oversold" alert matches a free-text reason string in a 30-day window, so it reports past events and never a current deficit
- **Found:** 2026-10-10, in review of the derived-stock-quantity design. A reviewer questioned whether the alert actually detects a negative balance; it does not.
- **Location:** `client/lib/db/queries/inventory.ts:426` (`getOversoldAlerts()`), consumed by `use-dashboard-overview.ts` and `use-stock-batch-alerts.ts`.
- **What's wrong:** the query selects movements `WHERE sm.reason LIKE '%oversold%'` within the last 30 days, grouped per product, `LIMIT 5`, reporting `MAX(ABS(sm.quantity))`. #### A-188. `client/` — `no such table: permission_groups` on one device, **mechanism unconfirmed** (do not treat the obvious explanations as the cause; three are already ruled out)
- **Found:** 2026-10-08, triaging Sentry `DUMOSRX-CLIENT-1P` — 3 events, 1 user, culprit `/inventory/:tab`. Logged deliberately as unconfirmed: the telemetry is real, but the code-side mechanism could not be established and is not worth guessing at.
- **Location:** unknown. The query sites are `client/lib/db/queries/permission-groups.ts` and `client/lib/hooks/use-permission-groups.ts`; the table is declared in `client/lib/db/schema.ts` (`CREATE TABLE IF NOT EXISTS permission_groups`, the fourth-from-last statement in `SCHEMA_SQL`).
- **Ruled out, so nobody re-walks these:**
  - **"The local schema predates the table and nothing creates it."** Every path that opens a database runs `SCHEMA_SQL` before anything can query it: `initDatabaseInternal()` on both the Tauri and sql.js branches, `rehydrateFromIndexedDb()` on writer-lock promotion, and `restoreDatabase()` (which also re-runs `runSchemaMigrations()`, specifically so an older backup comes up current). `query()`/`execute()` each `await initDatabase()` when `db` is null, so there is no pre-init read window.
  - **"A `SYNC_COLUMN_MIGRATIONS` ordering problem."** That list only `ALTER TABLE ... ADD COLUMN`s, and `runSchemaMigrations()` runs strictly *after* `SCHEMA_SQL`, so it cannot be what creates the table and cannot run before it exists.
  - **"The sql.js single-blob abort."** `SCHEMA_SQL` is handed to sql.js as one `db.run()`, and a throwing statement silently skips every later statement including `CREATE TABLE`s — the hazard `schema.ts`' own comment at the top of the index section documents, and the reason `READ_PATH_INDEXES` lives in `schema-migrations.ts` instead (see A-6 in `docs/FIXED_BUGS.md`). The only candidate trigger in the blob is `CREATE INDEX idx_sync_conflicts_unresolved ON _sync_conflicts(table_name, record_id, resolved_at)` at a line *before* `permission_groups`, which would abort the rest on a device whose `_sync_conflicts` lacks `resolved_at`. Checked: `_sync_conflicts` and that index shipped in the same commit (`ea1fcc41`), the table was never released without `resolved_at`, and no device can be in that state. In the web branch the enclosing `try` also falls back to a *fresh* database on any throw, which would have every table.
- **A latent hazard found while ruling the above out, not a bug today:** `_sync_conflicts` has **no entry in `SYNC_COLUMN_MIGRATIONS`**, and its index sits inside `SCHEMA_SQL` naming three of its columns. The moment a fourth column is added to that table and referenced from that index, every pre-existing local database aborts the schema blob at that line and loses **every one of the twenty `CREATE TABLE`s after it** — `customer_payments` through `supplier_payments`, i.e. `stores`, `users`, `audit_logs`, the whole procurement and loyalty set, `feedback`, `stock_movements`, `payment_accounts`, `permission_groups`, `system_configs`, `requested_products` — with no migration able to recover them, because the recovery pass runs after the statement that aborted. Either move this index into `READ_PATH_INDEXES` alongside the seventeen already there, or add `_sync_conflicts` to `SYNC_COLUMN_MIGRATIONS` before touching it.
- **Consequence as it stands:** 3 events on 1 device, and whatever permission read triggered it failed on that device — `use-permissions.ts` has a documented fallback for a user with no synced `permission_groups` row, but a thrown "no such table" is not that path. Low volume, no known data loss.
- **Needs a repro before any fix.** What would settle it: the device's `SELECT name FROM sqlite_master WHERE type='table'` (which other tables are missing tells you *where* in `SCHEMA_SQL` it stopped, if it stopped at all), the app version on that device, and whether it is the Tauri or the web/PWA build — the Tauri branch splits `SCHEMA_SQL` on `;` and runs each statement separately with no error swallowing, so a mid-blob abort there would have thrown out of `initDatabase()` loudly rather than leaving a half-built schema. Do not ship a defensive `CREATE TABLE IF NOT EXISTS` at the query site; that hides the mechanism without fixing it.

#### A-178. `laravel-server/` — a throttled sync inflates `changes_refused`, so a healthy store on a busy device reads as failing
- **Found:** 2026-10-07, reviewing the Phase 2 recorder after PG-18.
- **Location:** `SyncFailureRecorder` / the `sync_throttled` path into `sync_health_daily`.
- **What's wrong:** `sync_throttled` is recorded as a refusal and counted in `changes_refused`, the same bucket as `permission_denied` and `version_conflict`. #### A-165. `client/` — a `forbidden` push refusal parks its queue row forever, but making it terminal (as first proposed) would destroy real data — the retry classification is correct, the unbounded parking is the bug
- **Location:** `NON_RETRYABLE_CONFLICT_REASONS` / `REASONS_SETTLING_SOURCE_ROW` in `client/lib/db/sync-engine/push.ts:22-41`; the reason is emitted at `SyncController::push()` `:258` (`authorizeInsertTarget()`), `:409` and `:630` (`authorizeChangeTarget()`, UPDATE and DELETE).
- **Investigated 2026-10-06; the originally-logged fix was attempted and deliberately reverted.** A-165 was first written up as "the same bug class as A-161, just add `forbidden` to both sets." That is **wrong**, and the reason is now verified in code rather than assumed: `forbidden` is genuinely transient in one real shape, so dropping and settling on it would silently destroy a legitimate row. `resolveOwnershipIdentity()` (`SyncController.php`) gives a **staff** session only `[$currentUser->store_id]`, while an **owner** gets every store they own — a strictly narrower envelope. `_sync_queue` is device-global and carries no identity (deliberately — see A-162), and `clearDatabaseForNewStore()` only runs when the selected store *differs* from the local one (`app/setup/use-onboarding.ts:426`), so a staff member signing in onto the owner's **current** store triggers no wipe and drains the owner's **other** stores' queued rows under the narrower scope. Those are refused `forbidden`, and the same frozen payload succeeds the moment the owner signs back in. This is exactly the case `client/AGENTS.md` already called out ("Still open, same incident, not fixed here" — a push rejected `forbidden` is retryable *and correctly so*), which the original A-165 writeup did not account for. A-163's fix narrows this path but does not close it, because it only wipes on a store *change*.
- **What is therefore still genuinely wrong:** the row is never abandoned. `recordSyncFailure()`'s backoff is capped, not bounded, so the row retries hourly forever and re-raises `Sync item stuck after 5 attempts` on every pass — and via pull's pending-local-edit skip, that parked row stops its record being pulled at all for as long as it sits there. That is the real defect, and it is the general "a permanently-parked queue row silently freezes its record's pulls" problem `client/AGENTS.md` records as unaddressed — not a missing set membership.
- **Unblocked 2026-10-07.** The stuck-data tooling now provides the somewhere-to-escalate-to this needed: per-device queue reports surface what is stuck, and `sync_commands` lets an operator retry it deliberately. Bounded abandonment can now be designed against a real escalation path rather than inventing one — but the two decisions it still needs are unchanged: what N should be, and whether abandonment is surfaced to the store owner.
- **Why not just fixed:** the correct fix is bounded abandonment (give up after N attempts, with the terminal-conflict ledger row as the durable trace, *without* marking the source row synced), plus not letting a parked row block its own pulls. That is a sync-engine design change affecting every retryable reason, not a one-line set addition, and it needs its own scoping — notably what N should be and whether abandonment should be surfaced to the user. Do **not** close this by adding `forbidden` to either set; `client/__tests__/push-settles-permission-denied-rows.test.ts` now pins both classifications side by side and fails if that is attempted.
- **Abandonment cannot be uniform across tables — owner's constraint, 2026-10-07.** "If a sale or stock movement is stuck and is abandoned later, that spoils the data and would cause problems later." This is correct and it narrows the design: a crash report or an audit-log row can be discarded with no business consequence, but a `sales`, `sale_items` or `stock_movements` row is a **business record whose only copy is on that device**. Abandoning one permanently loses revenue data or permanently falsifies on-hand stock — the exact class of corruption `.agents/AGENTS.md` §9 requires tests against. So "give up after N attempts" is only a valid terminal state for diagnostic tables. For business tables the terminal state must be **escalation to a human**, not discard: surface it to the operator (and to the store owner), keep the row, and provide a deliberate retry. That is what makes the stuck-data admin tooling a prerequisite for this work rather than a follow-up to it.
- **And the priority sits upstream of abandonment:** fix the causes. Every stuck row that never happens is one nobody has to adjudicate. Known culprits so far: A-168 (a session-relative refusal classified as terminal), PG-18 (refusals that record nothing at all), and the plan-gated queues that never drain (noted in the A-172 fix). A-176b and A-205, both causes of a permanently stranded row, are fixed — see `docs/FIXED_BUGS.md`.

#### A-168. `laravel-server/` — the two `permission_groups` privilege refusals are session-relative too, but are still reported as terminal `permission_denied`
- **Location:** `SyncController::sanitizePermissionGroupSyncPayload()` — the "attempted to grant a permission the caller does not hold" throw and the "caller lacks `manage_roles_permissions`" throw, both `SyncPushPermissionDeniedException`.
- **Problem:** found and deliberately left alone while fixing A-167, which split the *store-scope* refusal into an absolute `permission_denied` and a session-relative `forbidden`. These two throws have the same shape and were not split: the function returns early for a `store_owner`/`admin`/`super_admin` caller, so **every** throw from either check is by definition a non-owner session, and the owner's own session would always have passed. A permission group the owner creates on a shared device, queued and then drained by a staff session signed in afterwards, is therefore refused `permission_denied`, dropped from `_sync_queue` and flagged `_synced = 1` — it never reaches the cloud and no requeue can recover it, even though the owner signing back in would have pushed it cleanly. Unlike A-167's case this needs no second store; one store and one shared device is enough.
- **Why not fixed with A-167:** the blast radius is materially smaller and the fix is materially riskier. It is one table (`permission_groups`), holding role configuration rather than transactional data, and the local row survives — the loss is "this group never reaches the cloud or the owner's other devices", recoverable by the owner re-saving it. Against that, the terminal classification here predates A-161 and is load-bearing in the other direction: `ensurePermissionGroupsSeeded()` makes a client seed five default groups locally, and on a staff device whose store the server has already seeded, `$isFirstTimeDefaultSeed` is false and the permissions diff refuses them — making that refusal retryable would reproduce A-161's `Sync item stuck after 5 attempts` loop for every staff device instead of the one owner device it was fixed for. Resolving it properly means distinguishing a client-seeded default group from an owner-authored custom one at this throw site, which needs its own scoping, and is best done together with A-165's bounded-abandonment work.
- **Locked meanwhile:** `laravel-server/tests/Feature/SyncPushSessionScopedRefusalTest.php::test_permission_group_privilege_refusals_stay_terminal_permission_denied` pins the current behaviour, so the decision is explicit rather than accidental.

## Accepted tradeoffs (no fix planned)

#### P3-1. `client/` — auth bearer token kept in `localStorage` instead of an HttpOnly cookie
- **Location:** `client/lib/api/token-manager.ts:17-50`.
- **Problem:** `auth_token` (the Sanctum bearer token) is read/written via `localStorage`. Any XSS in the client app could read it and exfiltrate a long-lived session token (Sanctum expiry 30 days, client rotates after 7).
- **Why accepted:** `setToken`/`clearToken` mirror the token to native Tauri code (`lib/native/widget-bridge.ts` → Android `TokenStore`, which does use `EncryptedSharedPreferences`) so the home-screen widget can make its own authenticated requests. A real fix needs a dual-path auth design — a real project, not a quick patch. The Tauri build's CSP (`script-src 'self' 'wasm-unsafe-eval'`, no remote or inline script) is a compensating control there, but does not cover the web/PWA build at `app.dumosrx.com`, and even in the bundled app an injected script that satisfies the policy still has same-origin `localStorage` access.

#### PG-14. `web/` — two more nav items are role-gated over permission-gated endpoints (same class as the Operations bug fixed in Phase 1)
- **Found:** code review of admin Phase 1, by deliberately checking every item in `web/components/admin/sidebar-items.ts` against `laravel-server/routes/api.php` after the Operations mismatch was caught live in a browser.

## Engineering notes (tech debt / ongoing risk, not bugs)

These describe the current state of known architectural tradeoffs and performance ceilings — not defects, and not tracked toward a fix. Re-derive before relying on anything here; this isn't re-validated on every pass.

### Performance
- **`db.export()` per write** (web/PWA build): every `execute()` outside a transaction re-serializes the whole local database and writes it to IndexedDB — the dominant long-term scaling risk for a large catalog. Two of its biggest inputs are bounded (`audit_logs`' 730-day local retention window, coalesced multi-image save bursts), but the per-write export itself is unchanged; fixing it properly needs a different persistence model (incremental/OPFS).
- **First PWA install download:** `precache-manifest.json` lists ~399 URLs (~15 MB, including two 650 KB sql.js WASM binaries) fetched on first install — the single largest network cost on a metered connection.
- **Whole-catalog in-memory search:** `getProductsWithDetails()` loads the entire catalog and `product-database.tsx` fuzzy-searches it in memory (debounced). Fine to ~10k products; beyond that the transform+filter+sort chain is O(catalog) on the main thread every filter change.
- **`validateSync()`'s per-request chain** (`SubscriptionService`, `SystemConfig::getVal`, `PermissionGroupSeeder::ensureSeeded`, `enforceStaffLimits`) adds roughly 10 queries to every push/pull before any data is touched.
- **`getStockMovements()` with no window** loads the whole table when searching/filtering — a large result set in React state at scale, independent of indexing, since nothing narrows the predicate.

### Offline / sync
- **Server-side row-lock duration:** `SyncController::push()` holds `lockForUpdate()` locks for the whole outer transaction. Bounded with the current ~50-change batch size, but the first place to look if "Lock wait timeout" shows up in server logs.
- **Tab-lock residual notes:** `resetDatabase()`/`clearDatabaseForNewStore()` call `db.run()` directly rather than through `reserveDbSlot()`, so they can interleave with an in-flight yielding `query()`. A stolen-from tab only learns it lost the lock via the `steal-notice` broadcast, which a frozen tab receives only on thaw — `writerTab` stays `true` until that notice arrives.

### Architecture
- **One hand-rolled tenant-resolution copy remains:** `DashboardService` still hand-rolls the staff→owner lookup instead of a shared `Request`-free helper; `TenantScopingArchitectureTest` only scans controllers, not services.
- **File-size guideline exceeded by design in a few hot spots:** `client/lib/db/core.ts` (~1,640 lines), `laravel-server/.../SyncController.php` (~2,700 lines), and `client/app/setup/use-onboarding.ts` (~640 lines, flagged by `/code-review` during the A-156 fix) are all well past the project's 350-line guideline — known, not tracked toward a split. `getProductsWithDetails()`-style "load everything, filter in React" is the deliberate norm for catalog/customer/PO lists; where that stops being fine isn't written down anywhere.
- **The admin users/stores backend quartet was already over 350 lines before the 2026-10-08 admin-panel Phase 1 work touched it, and stayed over, not pushed over:** `AdminUserService.php` (546 → 610), `AdminStoreService.php` (565 → 584), `AdminStoreController.php` (518 → 557) and `AdminUserController.php` (549 → 552, the one of the four not called out when this phase started). None of the four were split, by design — the phase's rule was that only a file it pushed *past* 350 gets split, and all four were already past it. Every class the phase actually created (`Filters/UserListFilters.php`, `Filters/StoreListFilters.php`, `Support/ListSortResolver.php`, `Support/QueryInput.php`, `AdminStoreReferrerService.php`) is well under the limit.
- **Two client-side sale-recording paths exist:** `recordSaleItemStock` (POS/online orders) and `local-database.ts::createSale` (demo seeding only) — the second still writes `stock_batches.quantity` via a raw `UPDATE` rather than through `update()`, so a demo-seeded batch is the one batch the version model never saw.
- **`composer audit`/`npm audit` are not run in CI.**
- **`sw.js` has no automated test coverage**, despite two prior cache-poisoning fixes.
- **The admin list-sort pagination-stability tests cannot fail under the test suite's SQLite engine (found 2026-10-08, admin-panel Phase 1 final review).** `AdminListSortingTest::store_pagination_is_stable_under_a_tie_heavy_status_sort` and `::user_pagination_is_stable_under_a_tie_heavy_role_sort` exist to pin the deterministic `->orderBy('stores.id')` / `->orderBy('users.id')` tiebreaker on the explicit-sort paths in `AdminStoreService`/`AdminUserService`. The production code is correct and should stay. But `phpunit.xml` runs against SQLite `:memory:`, and SQLite returns tied rows in a deterministic rowid order across two sequential identical SELECTs — so removing both tiebreaker lines leaves **both tests still passing** (verified by doing exactly that during review). MySQL gives no such guarantee, so the defect the tests describe is real in production while the tests provide no regression protection against the tiebreaker being dropped later. Making them engine-agnostic needs a different approach than fetching two pages and comparing id sets.
