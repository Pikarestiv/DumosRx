## Open bugs awaiting a fix

#### A-204. `laravel-server/` — a sync command is marked `sent` the moment it is handed out, is never re-offered, and has no timeout, so a device that does not answer loses it permanently
- **Found:** 2026-10-10. A `send_device_report` issued against `DRX-ZKI5K81UG` sat at `status = 'sent'`, `acted_at = NULL`, `result = NULL` while that device went on syncing normally. No report, no refusal, no error — and no way to ask again.
- **Location:** `app/Services/Admin/SyncCommandService.php:92-126` (`pendingFor()` claims by `UPDATE ... SET status = 'sent'`), `recordOutcome()` at `:129`.
- **What's wrong:** claiming on handout is correct — it stops a device that syncs twice applying a command twice. But `sent` is **terminal**: `pendingFor()` only ever selects `pending`, nothing moves a `sent` row back, and no timeout exists. So every way a device can fail to answer — a build old enough to ignore the `sync_commands` key entirely, a closed tab, a crashed round, a throw before `recordOutcome()` — ends with the command silently consumed. The admin panel then shows neither "queued" nor an outcome, and the operator's only tell is a report that never arrives.
- **Consequence:** remote support is unreliable in exactly the situation it exists for — a device in trouble. It also hides the real cause: the symptom reads as "the device ignored me" when the answer was "that build has never heard of sync commands". Worse, the panel's control is re-enabled (no `pending` row matches), so an operator can reissue indefinitely and lose each one the same way.
- **Fix:** keep claim-on-handout, add redelivery. Record `sent_at` and re-offer a `sent` command whose outcome has not arrived within a window (the device applies at most once because `recordOutcome()` is idempotent on `id`), or expire it to `failed` with a result the panel can show, e.g. "handed to the device but never acknowledged". Surfacing `sent` distinctly from `pending` in `store-sync-health-section.tsx` is the minimum, so an unanswered command is visible at all.
- **Related:** the immediate trigger was a device running a bundle that predates sync commands. A PWA keeps its cached shell until the service worker is replaced, so "deploy the fix" and "the field has the fix" are not the same event — any remote-support feature has to assume a mixed fleet (root `AGENTS.md` §11).

#### A-203. `client/` — a bulk pass over the catalogue queues one `_sync_queue` row per product per pass, with no collapsing, so a FIFO queue thousands deep delays every sale rung behind it
- **Found:** 2026-10-09, after a device reported 4,350 pending rows that were all pushing successfully (`processed: 50, failed: []`, `products` versions landing at 5).
- **Location:** `lib/db/base-helpers.ts:424-436` (`addToSyncQueue()` — a plain `INSERT`, no upsert), read FIFO at `:455` (`ORDER BY created_at ASC`), drained `SYNC_BATCH_SIZE = 50` at a time (`lib/db/sync-engine/push.ts:48`).
- **What's wrong:** every `update()` appends a queue row. A maintenance pass that touches the whole catalogue (a category backfill, a stock repair, a re-import) therefore enqueues one row per product, and a second pass enqueues another — ~2,000 products became 4,350 rows across two passes. Each payload is a full-row snapshot, so every row but the last is redundant work. **`audit_logs` already solves exactly this** by rewriting the pending payload in place rather than queueing a second entry (`lib/db/core.ts:1243-1262`); no other table does.
- **Consequence:** the queue is strictly FIFO, so a sale rung while 4,350 rows are pending waits **87 sync rounds** before it is even attempted — hours on a normal auto-sync interval, on a device that reports itself as healthy throughout. It also swamps every queue-depth signal: `queue-state.ts`'s depth, the admin panel's stuck-row view and the diagnostics report all read thousands-deep, so a genuinely stuck row is invisible while a benign backlog drains. That is a real diagnostic cost — it was hit while using those exact numbers to investigate another store.
- **Not a data risk.** Pushes succeed and the last full-row payload wins, so the backlog is idempotent and self-clearing. `products` carries no stock either (quantity lives on `stock_batches`, which the server refuses from a client), so a product backlog can never explain a quantity divergence.
- **Fix:** collapse on enqueue — for an `UPDATE` with a pending row for the same (`table_name`, `record_id`), rewrite that payload in place, as the `audit_logs` path does. Two things make this more than a one-liner and are why it is logged rather than rushed: an `INSERT` still pending must stay an `INSERT` (collapsing an UPDATE onto it, not the reverse), and `push.ts:165-193` deliberately holds back an UPDATE when a *sibling* UPDATE of the same record is still backed off — that logic assumes multiple rows per record exist and needs rereading, not deleting. A per-record cap, or prioritising `sales`/`stock_movements` ahead of catalogue rows, are weaker alternatives worth considering only if collapsing proves unsafe.

#### A-199. `laravel-server/` — two endpoints resolve a Personal Access Token from the request body without checking its abilities
- **Found:** 2026-10-09, second adversarial review of the on-till admin inspection plan.
- **Location:** `app/Http/Controllers/Api/Admin/AdminStoreController.php:518-529` (`restoreSession`), `app/Http/Controllers/Api/AuthHandoffController.php:32-48` (`create`).
- **What's wrong:** both call `PersonalAccessToken::findToken($validated['token'])` on a token taken from the **request body** and act on its owner without ever checking that token's abilities. `restoreSession` then mints an `admin-refresh` cookie for that owner, and the public cookie-only `/admin/session/refresh` (`routes/api.php:58`) turns that into a general-ability `web` token. The bearer on the request only has to satisfy `auth:sanctum`, which the till's own `['*']` sync token does.
- **Consequence:** any Sanctum token belonging to a super_admin, however narrowly scoped it was meant to be, can be escalated to a durable full superadmin session by whoever holds it. No such narrow token is minted today, which is why this is latent rather than live — but it is precisely why the on-till inspection credential is deliberately **not** a Sanctum token (see `docs/superpowers/specs/2026-10-09-on-till-admin-inspection-design.md`). Any future narrowly-scoped token walks straight into it.
- **Fix:** require `->can('*')` (or an explicit expected ability) on the body token in both handlers, and prefer deriving the identity from the authenticated bearer rather than from a body token at all.

#### A-197. `client/` — the deferred-delta drain runs per round, not per page, so a batch whose movement arrived first holds a quantity the server disagrees with
- **Found:** 2026-10-09, differential fuzzing of `pullChanges()` against the server's own derivation during the fourth review pass of the stock-integrity branch.
- **Location:** `client/lib/db/sync-engine/pull.ts` (the drains at the start of a round and after the page loop), `client/lib/db/sync-engine/deferred-stock-deltas.ts`.
- **What's wrong:** `applyDeferredStockDeltas()` runs only at the start of a round and after every page, never between pages. A delta deferred on page 1 is therefore applied *after* page N's movements for the same batch — and because the floor is `MAX(0, quantity + delta)` per movement, the order is not commutative. On a first full sync of a large store, a batch's opening receipt defers while its later sales apply against 0 and are clamped away.
- **Consequence:** the device's quantity ends up disagreeing with the server's, permanently, with no error anywhere. 34 of 300 randomised histories hit it. **Confirmed live on 2026-10-10** against the Agidi store: 994 units sold store-wide, the device reading **+823 over** the server — 83% of its sale deductions clamped away. `PENTAZOCINE INJ` reads its opening 80 where the server says 52, short by exactly its 28 sold. This entry previously said the quantity ends up *below* the server's; that is the wrong direction for the common case and it cost an investigation an hour, because the mechanism was discarded on the grounds that the drift pointed the other way. A destroyed *outbound* delta leaves the device **high**. This is the shape of the "958 products at exactly twice their opening stock" case — `foldStockQuantities()` is a correct repair for it (it converges on the server's value), but the drift keeps recurring until the drain is fixed.
- **Fix:** drain per page rather than per round, or order the drain ahead of the page's own movements. `client/AGENTS.md`'s deferral section documents the mechanism as safe and should be corrected along with it.

#### A-193. `client/` — the stock-integrity Sentry report does not coalesce, so a drifted device uploads a new bug row daily
- **Found:** 2026-10-08, adversarial review of the stock-integrity branch before merge.
- **Location:** `client/lib/db/sync-engine/stock-integrity.ts`, `client/lib/db/schema-migrations.ts` (index list), `client/lib/utils/error-logger.ts`.
- **What's wrong:** `logCrash()` writes a `feedback` row and queues it for sync, and its fingerprint (`area|message|firstStackLine`) does not normalise digits while the message embeds the counts and net delta — so a device whose numbers move uploads a brand-new bug row every day instead of coalescing.
- **Consequence:** daily synced noise from any device with persistent divergence. Not data loss.
- **Fix:** `logCrash`'s fingerprint is `area|message|firstStackLine` with no digit normalisation, while the message embeds the counts and net delta — so a device whose numbers move uploads a new synced `feedback` row every day instead of coalescing. Either normalise digits in the fingerprint or move the counts out of the message into the context payload. (The missing `stock_movements(stock_batch_id)` index, originally logged here as the other half, was added 2026-10-09.)

#### A-189. `laravel-server/` — 5,088 products across two stores reference each other's `categories` rows, so their category can never reach any device
- **Found:** 2026-10-08, investigating a store reporting "duplicates" and a catalogue that showed `UNCATEGORIZED` on 98.6% of products even after a factory reset and a clean re-sync.
- **Location:** `categories.store_id` / `products.category_id` data, plus `SyncController::pull()`'s `'categories' => $query->whereIn('store_id', $storeIds)` scoping.
- **What's wrong:** products belonging to store `68e4c0e5` carry a `category_id` owned by store `571582a9`, and 2,628 of `571582a9`'s products point the other way — the two stores are cross-wired. (Both belong to the same owner, two branches of one business; the defect is not owner-specific — the unscoped match that caused it would equally have merged two *unrelated* customers' categories, which is why the repair never touches the other store's rows regardless of who owns them.) The pull correctly refuses to send another store's `categories` rows, and `whereIn` never matches `NULL` either, so the client receives a `category_id` it cannot resolve. The catalogue's `LEFT JOIN categories` yields NULL and renders "Uncategorized". The server is self-consistent throughout (`SELECT COUNT(*) ... category_id IS NULL` returns 0), which is why this is invisible from the server side.
- **Origin:** the push-time natural-key collision handler matched a pushed category by name *without* scoping to the store, so a bulk import pushing `drugs` was remapped onto an unrelated store's `drugs`. The code was scoped by `2026_09_12_000000_scope_category_uniqueness_to_store.php`; the rows it had already mis-pointed were never repaired. The affected store still owns its own 0-product `machine`, `toiletries` and `wine` rows, which is the fingerprint of the remap.
- **Consequence:** no client-side action fixes it — not a resync, not a factory reset, not Health Sync — because the referenced row is one the device is never allowed to receive. It is also live cross-tenant coupling: a rename or delete in the other store silently re-labels or orphans this store's products, which is the hazard the comment at `SyncController.php:1607` already warns about.
- **Root cause closed 2026-10-08.** `findDuplicateInsertConflict()` matched a pushed category/supplier by name against the payload's own store **or any NULL-store row**, and `push()` backfills the caller's store onto the payload before that check — so a store pushing a name that matched one of the nine retired NULL-store seed categories (`Analgesics`, `Antimalarials`, `Vitamins & Supplements`, …) was merged onto the unowned row, and `pull()`'s `whereIn` never sends it. The NULL fallback is gone; a payload that genuinely carries no `store_id` still matches NULL-store rows, which is the pre-multi-tenancy path the `id_map` regression tests cover. Regression coverage: `SyncEndpointTest::test_push_does_not_merge_a_store_scoped_category_into_a_null_store_row`. The two existing `id_map` duplicate-name tests had fixtures creating the pre-existing row with no `store_id` at all; they now create it in the caller's store, which is the only shape a real duplicate can take once push backfills the store — their assertions are unchanged.
- **Fix:** `php artisan sync:repair-cross-tenant-categories` (`App\Services\Sync\CrossTenantCategoryRepairService`). Reports by default; `--apply` writes, `--store=` narrows. It finds or creates a same-named category owned by the product's own store and repoints the product, never touching the other tenant's rows. Products with a NULL `store_id` (9 on production) are reported and skipped — they have no owning store to repoint to and need one assigned first. Uses Eloquent so `updated_at` is PHP-generated UTC: a raw `UPDATE ... NOW()` here would write a timestamp ~4h behind UTC and the corrected rows could never pass the pull's `updated_at` filter (root `AGENTS.md` §7). Covered by `tests/Feature/CrossTenantCategoryRepairTest.php` (9 cases).
- **Still open:** the command exists but has not been run against production. Re-pointing 5,088 products bumps their `updated_at`, so every device for both stores re-pulls them on its next sync — intended here, but it is the same blast radius A-185 describes, so run it per-store with `--store=` rather than unscoped.

#### A-186. `client/` — the POS product tile shows nothing that distinguishes two similar products, so staff report "duplicate products" that do not exist
- **Found:** 2026-10-08, investigating a production report of duplicate products at store `68e4c0e5-2354-4ff9-98e4-69d3b4c482fa` (Nest Pharmacy A2). No duplicate rows exist: the server holds 2,495 products against a 2,493-row QuickBooks source file whose Item Names and Item Numbers are 100% unique. What staff could not tell apart were genuinely distinct products rendering identically on the POS grid.
- **Location:** `client/components/pos/pos-product-list.tsx`, the `POSProductCard` body (the name `div` and the subtitle `div` immediately under it); compare `client/components/products/catalog-row.tsx`, which does not have the problem.
- **What's wrong:** the tile renders exactly four things — a category *icon*, `{product.name}` under `line-clamp-2`, the subtitle `{product.generic_name || "Generic"} • {product.strength || "-"}`, and then price plus stock. There is no barcode/SKU and no category text anywhere on the card. A bulk-imported product has neither `generic_name` nor `strength`, so on a freshly imported catalogue that subtitle line is the literal string `Generic • -` on **every** tile, carrying zero information while occupying the one slot that could have disambiguated. With a long name clamped to two lines, two products whose names differ late in the string are visually identical.
- **Real examples from that store:** `CARO WHITE CUP B/S CREAM` vs `CARO WHITE CUP S/S CREAM` — one character apart, SKUs 2189 and 2190 — and the `CARO WHITE 200ML` / `300ML` / `500ML LOTION` family.
- **Consequence:** this is a UX defect with a measured support cost, not a cosmetic one. It generated a "we have duplicate products" escalation that took a full catalogue reconciliation against the source file to disprove, and it means a cashier can ring up the wrong variant with no on-screen signal that they did. The Product Catalog screen is unaffected because `catalog-row.tsx` prints `{product.barcode || product.id.slice(0, 8)} · {product.category || "Uncategorized"}` as a subtitle under the name, which separates all of the above at a glance — so the same user, looking at the same data, can distinguish these products on one screen and not on the other.
- **Fix:** give the tile a disambiguator. The cheapest version is to make the existing subtitle line conditional rather than placeholder-filled: show `barcode` (or `category_name`) when `generic_name`/`strength` are both absent, instead of rendering `Generic • -`. `POSProduct` already carries `barcode` and `category_name` (`client/lib/utils/search.ts` indexes both, and `usePOSProductFilter` reads `category_name`), so no new query or sync coverage is needed. Note that search already matches on `barcode`, so the SKU is a usable key the moment it is visible — today it is searchable but never displayed.

#### A-187. `client/` — a product with no category is labelled "Uncategorized" everywhere but cannot be filtered to from anywhere
- **Found:** 2026-10-08, during the same investigation as A-186. Verified live against the store's catalog: the Product Catalog's Category pill offers All, beverages, busicuit, cosmetics, drinks, drugs, machine, perfume, provision, soap, sweet, tea, toiletries — 12 real categories and no Uncategorized option — while a large share of that store's catalogue has `category_id IS NULL` after a partial import.
- **Location:** `client/components/pos/pos-category-filter.tsx` and `client/lib/hooks/use-pos-product-filter.ts` (POS); `client/components/products/product-database.tsx` and `product-database-filters.tsx` (Product Catalog). The label the UI does show comes from `client/components/products/types.ts` (`category: apiData.category_name || "Uncategorized"`) and is rendered by `catalog-row.tsx`.
- **What's wrong, and the two mechanisms are different:**
  - **POS.** `usePOSProductFilter()` builds the chip list by walking the loaded products and adding `product.category_name` only `if (product.category_name)`, so an uncategorized product contributes nothing to the list. `POSCategoryFilter` then renders an "All" tab plus one tab per name in that list and nothing else. Filtering is `p.category_name === categoryFilter`, which no null value can ever match.
  - **Product Catalog.** The options do not come from the products at all — `product-database.tsx` builds `categories` from `getCategoryList()` (the `categories` table) prefixed with `"all"`, falling back to a hardcoded five/six-name default list when the store has no categories. Since the list is sourced from the category rows rather than from the products, an "Uncategorized" option is structurally impossible there, not merely omitted.
- **Consequence:** the UI names a state it cannot select. A store that bulk-imported without categories has no way to enumerate the gap it needs to fix — those products are reachable only by scrolling the full "All" list or by already knowing a product's name to search for. That is exactly the audit the store owner wants after a partial import, and it is also why the uncategorized tail stays uncategorized.
- **Fix:** add an explicit sentinel option to both filters (a reserved value such as `"__uncategorized__"`, matched by a `switch`/`Map` rather than a dynamic lookup per `.agents/AGENTS.md` §8) that filters to `category_name == null`. On the POS side, append the chip when any loaded product lacks a `category_name`; on the Catalog side it has to be appended to the `categories` array independently of `getCategoryList()`, and `preFilteredProducts`' `product.category === categoryFilter` test needs a branch for it — note that `types.ts` has already collapsed null into the *string* `"Uncategorized"` by that point, so a filter keyed on the display string would also match a real category a store happened to name "Uncategorized". Filter on the raw `category_name`/`category_id`, not the label.

#### A-188. `client/` — `no such table: permission_groups` on one device, **mechanism unconfirmed** (do not treat the obvious explanations as the cause; three are already ruled out)
- **Found:** 2026-10-08, triaging Sentry `DUMOSRX-CLIENT-1P` — 3 events, 1 user, culprit `/inventory/:tab`. Logged deliberately as unconfirmed: the telemetry is real, but the code-side mechanism could not be established and is not worth guessing at.
- **Location:** unknown. The query sites are `client/lib/db/queries/permission-groups.ts` and `client/lib/hooks/use-permission-groups.ts`; the table is declared in `client/lib/db/schema.ts` (`CREATE TABLE IF NOT EXISTS permission_groups`, the fourth-from-last statement in `SCHEMA_SQL`).
- **Ruled out, so nobody re-walks these:**
  - **"The local schema predates the table and nothing creates it."** Every path that opens a database runs `SCHEMA_SQL` before anything can query it: `initDatabaseInternal()` on both the Tauri and sql.js branches, `rehydrateFromIndexedDb()` on writer-lock promotion, and `restoreDatabase()` (which also re-runs `runSchemaMigrations()`, specifically so an older backup comes up current). `query()`/`execute()` each `await initDatabase()` when `db` is null, so there is no pre-init read window.
  - **"A `SYNC_COLUMN_MIGRATIONS` ordering problem."** That list only `ALTER TABLE ... ADD COLUMN`s, and `runSchemaMigrations()` runs strictly *after* `SCHEMA_SQL`, so it cannot be what creates the table and cannot run before it exists.
  - **"The sql.js single-blob abort."** `SCHEMA_SQL` is handed to sql.js as one `db.run()`, and a throwing statement silently skips every later statement including `CREATE TABLE`s — the hazard `schema.ts`' own comment at the top of the index section documents, and the reason `READ_PATH_INDEXES` lives in `schema-migrations.ts` instead (see A-6 in `docs/FIXED_BUGS.md`). The only candidate trigger in the blob is `CREATE INDEX idx_sync_conflicts_unresolved ON _sync_conflicts(table_name, record_id, resolved_at)` at a line *before* `permission_groups`, which would abort the rest on a device whose `_sync_conflicts` lacks `resolved_at`. Checked: `_sync_conflicts` and that index shipped in the same commit (`ea1fcc41`), the table was never released without `resolved_at`, and no device can be in that state. In the web branch the enclosing `try` also falls back to a *fresh* database on any throw, which would have every table.
- **A latent hazard found while ruling the above out, not a bug today:** `_sync_conflicts` has **no entry in `SYNC_COLUMN_MIGRATIONS`**, and its index sits inside `SCHEMA_SQL` naming three of its columns. The moment a fourth column is added to that table and referenced from that index, every pre-existing local database aborts the schema blob at that line and loses **every one of the twenty `CREATE TABLE`s after it** — `customer_payments` through `supplier_payments`, i.e. `stores`, `users`, `audit_logs`, the whole procurement and loyalty set, `feedback`, `stock_movements`, `payment_accounts`, `permission_groups`, `system_configs`, `requested_products` — with no migration able to recover them, because the recovery pass runs after the statement that aborted. Either move this index into `READ_PATH_INDEXES` alongside the seventeen already there, or add `_sync_conflicts` to `SYNC_COLUMN_MIGRATIONS` before touching it.
- **Consequence as it stands:** 3 events on 1 device, and whatever permission read triggered it failed on that device — `use-permissions.ts` has a documented fallback for a user with no synced `permission_groups` row, but a thrown "no such table" is not that path. Low volume, no known data loss.
- **Needs a repro before any fix.** What would settle it: the device's `SELECT name FROM sqlite_master WHERE type='table'` (which other tables are missing tells you *where* in `SCHEMA_SQL` it stopped, if it stopped at all), the app version on that device, and whether it is the Tauri or the web/PWA build — the Tauri branch splits `SCHEMA_SQL` on `;` and runs each statement separately with no error swallowing, so a mid-blob abort there would have thrown out of `initDatabase()` loudly rather than leaving a half-built schema. Do not ship a defensive `CREATE TABLE IF NOT EXISTS` at the query site; that hides the mechanism without fixing it.

#### A-185. `laravel-server/`+`web/` — catalog standardization still defaults to an unscoped, platform-wide write that re-pulls every touched product to every client
- **Found:** 2026-10-08, implementing the dry-run/scoping mitigation for `AdminCatalogService::standardizeCatalog()` (admin panel Phase 1, §7.4).
- **Location:** `AdminCatalogService::standardizeCatalog()` and `AdminPlatformController::standardize()` (`POST /admin/products/standardize`); the admin-panel "Standardize Catalog" button that calls it.
- **What's wrong:** the operation backfills blank `generic_name` to `"General"` and blank `manufacturer` to `"Unknown"` via Eloquent `update()`. Eloquent bumps `updated_at` on every row it touches, and the sync engine's incremental pull filters by `updated_at`/`_synced_at`. An unscoped run therefore re-downloads every touched product to every client on its next sync — potentially every store's whole catalogue at once, not just the rows that actually changed value.
- **PHP generates this timestamp, in UTC** (`now()`/`updated_at` via Eloquent) — this is **not** an instance of root `AGENTS.md` §7's MySQL `SYSTEM` timezone gotcha (that only affects raw SQL `NOW()`/`CURRENT_TIMESTAMP()` run outside Laravel's PDO connections). No raw SQL is used here. A future reader should not go chasing the server clock for this one.
- **Mitigation shipped, not a fix:** `standardizeCatalog(bool $dryRun = false, ?string $storeId = null)` now accepts a dry run (reports the affected-field count, writes nothing, confirmed not to touch `updated_at`) and an optional `store_id` scope, and the OpenAPI summary/description were corrected to say what the endpoint actually does (it does not dedupe or normalize names). See `laravel-server/tests/Feature/Admin/AdminCatalogStandardizeTest.php`.
- **Still open:** the admin-panel UI's "Standardize Catalog" button still calls the endpoint with no `store_id` and no dry-run step shown to the operator, so the cross-tenant, full-catalogue-resync blast radius is still the default behavior in practice. Wiring the button to a store picker and a dry-run preview is Phase 4 UI work, not done here.

#### A-182. `web/` — the site-wide PWA's `start_url` is a cross-origin bounce, so installing `dumosrx.com` yields a window that navigates out of its own scope on launch
- **Found:** 2026-10-07, while fixing A-181 (see `docs/FIXED_BUGS.md`).
- **Location:** `public/site.webmanifest` and `app/dashboard/[...view]/redirect-client.tsx`.
- **What's wrong:** `site.webmanifest` sets `start_url: "/dashboard"` with no `scope` and no `id`. `/dashboard` is not a page — it is a client-side redirect that sets `window.location.href = getAppURL()`, i.e. `https://app.dumosrx.com`. So the installed app launches, immediately leaves its own origin, and lands outside any scope the manifest declares.
- **Consequence:** the standalone window is out of scope from the first navigation. Browsers handle that inconsistently — typically by showing an in-app browser chrome bar, or by treating subsequent navigation as a plain tab — so the "installed app" feel is lost, and the user is left looking at a URL bar in what should be a standalone window. This was the visible half of A-181's symptom and it is **not** fixed by A-181: installing from anywhere on `dumosrx.com` outside `/admin` still does this.
- **Fix:** decide what the marketing-site PWA is actually for. Three options, in order of preference: (a) drop `manifest` from the root layout entirely and let store owners install the real app from `app.dumosrx.com`, which has its own `client/public/manifest.json` with `start_url: "/"` — the app they want is served from that origin anyway; (b) keep it installable but point `start_url` at `/` with an explicit `scope: "/"`, so it is honestly a marketing-site shortcut; (c) keep `/dashboard` but make it a real page rather than a redirect. Whichever is chosen, add an explicit `id` — without one, the id defaults to `start_url`, so changing `start_url` later orphans every already-installed copy rather than updating it.

#### A-183. `web/` — the root service worker registers in development and on `/admin/` pages, the two things `admin-sw.js` deliberately avoids
- **Found:** 2026-10-07, while fixing A-181 (see `docs/FIXED_BUGS.md`).
- **Location:** `components/pwa-registrar.tsx` (mounted in `app/layout.tsx`, i.e. on every route) and `public/sw.js`.
- **What's wrong:** `PwaRegistrar` calls `navigator.serviceWorker.register("/sw.js")` with no `scope` (so `/`) and **no `NODE_ENV` guard**. `AdminPwaRegistrar` was given both precautions on purpose — see the Admin PWA section of `web/AGENTS.md` — and this one predates that reasoning. #### A-176. `client/`+`laravel-server/` — a `stock_batches` row older than the pull cursor is never re-sent, so some deferred deltas can never resolve
- **Found:** 2026-10-07, while fixing A-173 (see `docs/FIXED_BUGS.md` for the full mechanism and why devices diverge).
- **Location:** `client/lib/db/sync-engine/pull.ts` (incremental pull, cursor by `updated_at`) and `SyncController::pull()`, which has no by-id fetch.
- **What's wrong:** a pulled `stock_movements` row whose `stock_batches` row has not arrived defers its delta, correctly. But the pull is incremental: once the cursor has passed a batch, that batch is only re-sent if it is updated again. A batch created long ago and never touched since therefore **never arrives**, and its deltas stay pending forever. A-173 makes this visible (chronic re-reporting), but it does not make the batch arrive. **This entry previously also claimed A-173 made it "safe (reconciliation refuses while deltas are pending)". That was never true and must not be reinstated:** that guard was written, then removed in review as protecting nothing while permanently refusing repairs — a delta stays pending only while its `stock_batches` row is *absent* locally, and an absent batch is not in the payload Health Sync sends, so the feared understated write cannot happen (see `docs/FIXED_BUGS.md` A-173, pinned by `client/__tests__/reconcile-proceeds-with-pending-deltas.test.ts`). A narrower divergence interlock was then built as the correct alternative and **also withdrawn before merge**, because a batch floored at 0 by an oversell and a legacy A-148 batch with sales against it both read as diverged, so it threw for the whole store and blocked the only repair those batches have. `reconcileStockQuantities()` therefore has no integrity interlock today; see §4 of `docs/superpowers/specs/2026-10-08-stock-integrity-fold-design.md`.
- **Consequence:** that device's on-hand quantity for the affected batches stays understated indefinitely. **There is a self-service way out, and the error text should point at it:** Settings > Data > "Force full resync" (`forceFullResync()`) clears `_sync_state` and re-pulls every table, which does make a cursor-stranded batch arrive. An earlier version of this entry said there was no way out; that was wrong.
- **The second cause is FIXED (2026-10-07), see `docs/FIXED_BUGS.md` A-176a.** `applyPullTenantScope()` scoped `stock_batches` through a soft-delete-filtered `Product::query()` while `stock_movements` was scoped by `store_id` and pulled `withTrashed()`, so a soft-deleted product's movements arrived without their batches and a full resync could never close the gap. Both that subquery and `counts()`'s mirror of it now use `Product::withTrashed()`.
- **What remains open here is only the cursor half:** a batch whose `updated_at` predates the device's pull cursor is not re-sent by an incremental pull. `forceFullResync()` does recover it, so this is no longer a dead end — but it is a manual step the operator has to know about, and a targeted by-id backfill would remove the need for it entirely.
- **Fix:** a targeted backfill — the client asks for specific record ids it knows it is missing, and the server returns them regardless of cursor position. There is no such endpoint today (`whereIn('id', …)` exists in `pull()` only for the store/user scoping), so this is new API surface plus a client call path, and wants its own scoping. Worth pairing with a decision on whether an unresolvable delta should eventually be surfaced to the store owner rather than only to Sentry.

#### A-177. `laravel-server/` — a sync command is addressed by `device_id`, which any device of the same store can claim
- **Found:** 2026-10-07, in review of the Phase 4 command channel. Logged rather than fixed: it is a real limit, but it is not a privilege escalation and the fix needs a device-identity decision that does not exist yet.
- **Location:** `SyncCommandService::pendingFor()` and the sync request's device header.
- **What's wrong:** `device_id` is self-asserted by the client. A command issued for device A is claimed by whichever device presents that id. There is no device registration, so the server cannot tell two devices of one store apart except by what they claim to be.
- **What the blast radius actually is:** bounded by tenant scoping and by the command vocabulary. A device can only claim commands for **its own store**, and every command touches `_sync_queue` only — so the worst case is "the wrong device of the same store applies a retry or discards a diagnostic row of its own". It is not a cross-tenant issue and it cannot reach a business table.
- **Fix:** issue commands against a registered device identity rather than a claimed string — a per-device token minted at pairing. That is a larger change (pairing flow, token storage, rotation) and should be decided alongside `X-Device-Label`, which has the same self-asserted property.

#### A-178. `laravel-server/` — a throttled sync inflates `changes_refused`, so a healthy store on a busy device reads as failing
- **Found:** 2026-10-07, reviewing the Phase 2 recorder after PG-18.
- **Location:** `SyncFailureRecorder` / the `sync_throttled` path into `sync_health_daily`.
- **What's wrong:** `sync_throttled` is recorded as a refusal and counted in `changes_refused`, the same bucket as `permission_denied` and `version_conflict`. But throttling is the server working as designed — it means "come back shortly", not "this data was rejected". A device syncing aggressively therefore drives its store's success rate down without a single row actually failing.
- **Consequence:** the admin Overview's sync success rate understates health, and a store can be triaged for a problem it does not have. The direction is the safe one (it cries wolf rather than hiding a fault), which is why this is logged rather than hotfixed.
- **Fix:** give throttling its own counter and exclude it from the success-rate denominator, or classify refusals into "rejected" versus "deferred" and surface only the former as failure. Note the metric's rule from Phase 1 applies: if throttling is excluded entirely and nothing else happened that day, the rate must render as unavailable, not as 100%.

#### A-175. CI — FTP deploys are not atomic, so production serves a half-old, half-new code tree during every backend and web deploy
- **Found:** 2026-10-07, while scoping the deploy pipeline for A-170. Deliberately logged rather than fixed: the owner chose to keep FTP for now and not land a pipeline rewrite on top of the migration work.
- **Location:** `.github/workflows/deploy-backend.yml` and `deploy-web.yml`, both using `SamKirkland/FTP-Deploy-Action`.
- **What's wrong:** the action uploads changed files one at a time into the live document root. For the duration of an upload, production is serving a mix of old and new files to real traffic. A request landing mid-deploy can execute a new controller against an old service, or load a view whose component has not arrived yet. The window scales with the number of changed files, so the largest changes — the ones most likely to be incompatible across versions — have the longest exposure.

- **Fix:** SSH is available on this plan (confirmed 2026-10-07), so `rsync` into a release directory plus an atomic symlink swap is the standard answer and removes the window entirely. Worth pairing with `php artisan config:cache`/`view:cache` on the new release before the swap, and with keeping the previous release directory so a rollback is a symlink change rather than a re-upload.
- **Related:** A-170 (migrations never run) and A-174 (the endpoint that runs them) are separate problems on the same pipeline; fixing deploy atomicity does not address either, and neither addresses this.

#### A-165. `client/` — a `forbidden` push refusal parks its queue row forever, but making it terminal (as first proposed) would destroy real data — the retry classification is correct, the unbounded parking is the bug
- **Location:** `NON_RETRYABLE_CONFLICT_REASONS` / `REASONS_SETTLING_SOURCE_ROW` in `client/lib/db/sync-engine/push.ts:22-41`; the reason is emitted at `SyncController::push()` `:258` (`authorizeInsertTarget()`), `:409` and `:630` (`authorizeChangeTarget()`, UPDATE and DELETE).
- **Investigated 2026-10-06; the originally-logged fix was attempted and deliberately reverted.** A-165 was first written up as "the same bug class as A-161, just add `forbidden` to both sets." That is **wrong**, and the reason is now verified in code rather than assumed: `forbidden` is genuinely transient in one real shape, so dropping and settling on it would silently destroy a legitimate row. `resolveOwnershipIdentity()` (`SyncController.php`) gives a **staff** session only `[$currentUser->store_id]`, while an **owner** gets every store they own — a strictly narrower envelope. `_sync_queue` is device-global and carries no identity (deliberately — see A-162), and `clearDatabaseForNewStore()` only runs when the selected store *differs* from the local one (`app/setup/use-onboarding.ts:426`), so a staff member signing in onto the owner's **current** store triggers no wipe and drains the owner's **other** stores' queued rows under the narrower scope. Those are refused `forbidden`, and the same frozen payload succeeds the moment the owner signs back in. This is exactly the case `client/AGENTS.md` already called out ("Still open, same incident, not fixed here" — a push rejected `forbidden` is retryable *and correctly so*), which the original A-165 writeup did not account for. A-163's fix narrows this path but does not close it, because it only wipes on a store *change*.
- **What is therefore still genuinely wrong:** the row is never abandoned. `recordSyncFailure()`'s backoff is capped, not bounded, so the row retries hourly forever and re-raises `Sync item stuck after 5 attempts` on every pass — and via pull's pending-local-edit skip, that parked row stops its record being pulled at all for as long as it sits there. That is the real defect, and it is the general "a permanently-parked queue row silently freezes its record's pulls" problem `client/AGENTS.md` records as unaddressed — not a missing set membership.
- **Unblocked 2026-10-07.** The stuck-data tooling now provides the somewhere-to-escalate-to this needed: per-device queue reports surface what is stuck, and `sync_commands` lets an operator retry it deliberately. Bounded abandonment can now be designed against a real escalation path rather than inventing one — but the two decisions it still needs are unchanged: what N should be, and whether abandonment is surfaced to the store owner.
- **Why not just fixed:** the correct fix is bounded abandonment (give up after N attempts, with the terminal-conflict ledger row as the durable trace, *without* marking the source row synced), plus not letting a parked row block its own pulls. That is a sync-engine design change affecting every retryable reason, not a one-line set addition, and it needs its own scoping — notably what N should be and whether abandonment should be surfaced to the user. Do **not** close this by adding `forbidden` to either set; `client/__tests__/push-settles-permission-denied-rows.test.ts` now pins both classifications side by side and fails if that is attempted.
- **Abandonment cannot be uniform across tables — owner's constraint, 2026-10-07.** "If a sale or stock movement is stuck and is abandoned later, that spoils the data and would cause problems later." This is correct and it narrows the design: a crash report or an audit-log row can be discarded with no business consequence, but a `sales`, `sale_items` or `stock_movements` row is a **business record whose only copy is on that device**. Abandoning one permanently loses revenue data or permanently falsifies on-hand stock — the exact class of corruption `.agents/AGENTS.md` §9 requires tests against. So "give up after N attempts" is only a valid terminal state for diagnostic tables. For business tables the terminal state must be **escalation to a human**, not discard: surface it to the operator (and to the store owner), keep the row, and provide a deliberate retry. That is what makes the stuck-data admin tooling a prerequisite for this work rather than a follow-up to it.
- **And the priority sits upstream of abandonment:** fix the causes. Every stuck row that never happens is one nobody has to adjudicate. Known culprits so far: A-176 (a batch older than the pull cursor is never re-sent), A-168 (a session-relative refusal classified as terminal), PG-18 (refusals that record nothing at all), and the plan-gated queues that never drain (noted in the A-172 fix).

#### A-168. `laravel-server/` — the two `permission_groups` privilege refusals are session-relative too, but are still reported as terminal `permission_denied`
- **Location:** `SyncController::sanitizePermissionGroupSyncPayload()` — the "attempted to grant a permission the caller does not hold" throw and the "caller lacks `manage_roles_permissions`" throw, both `SyncPushPermissionDeniedException`.
- **Problem:** found and deliberately left alone while fixing A-167, which split the *store-scope* refusal into an absolute `permission_denied` and a session-relative `forbidden`. Resolving it properly means distinguishing a client-seeded default group from an owner-authored custom one at this throw site, which needs its own scoping, and is best done together with A-165's bounded-abandonment work.
- **Locked meanwhile:** `laravel-server/tests/Feature/SyncPushSessionScopedRefusalTest.php::test_permission_group_privilege_refusals_stay_terminal_permission_denied` pins the current behaviour, so the decision is explicit rather than accidental.

## Engineering notes (tech debt / ongoing risk, not bugs)

These describe the current state of known architectural tradeoffs and performance ceilings — not defects, and not tracked toward a fix. Re-derive before relying on anything here; this isn't re-validated on every pass.

### Performance
- **`db.export()` per write** (web/PWA build): every `execute()` outside a transaction re-serializes the whole local database and writes it to IndexedDB — the dominant long-term scaling risk for a large catalog. Two of its biggest inputs are bounded (`audit_logs`' 730-day local retention window, coalesced multi-image save bursts), but the per-write export itself is unchanged; fixing it properly needs a different persistence model (incremental/OPFS).
- **First PWA install download:** `precache-manifest.json` lists ~399 URLs (~15 MB, including two 650 KB sql.js WASM binaries) fetched on first install — the single largest network cost on a metered connection.
- **Whole-catalog in-memory search:** `getProductsWithDetails()` loads the entire catalog and `product-database.tsx` fuzzy-searches it in memory (debounced). Fine to ~10k products; beyond that the transform+filter+sort chain is O(catalog) on the main thread every filter change.
- **`validateSync()`'s per-request chain** (`SubscriptionService`, `SystemConfig::getVal`, `PermissionGroupSeeder::ensureSeeded`, `enforceStaffLimits`) adds roughly 10 queries to every push/pull before any data is touched.
- **`getStockMovements()` with no window** loads the whole table when searching/filtering — a large result set in React state at scale, independent of indexing, since nothing narrows the predicate.

### Offline / sync
- **Server-side row-lock duration:** `SyncController::push()` holds `lockForUpdate()` locks for the whole outer transaction. Bounded with the current ~50-change batch size, but the first place to look if "Lock wait timeout" shows up in server logs.
- **Tab-lock residual notes:** `resetDatabase()`/`clearDatabaseForNewStore()` call `db.run()` directly rather than through `reserveDbSlot()`, so they can interleave with an in-flight yielding `query()`. A stolen-from tab only learns it lost the lock via the `steal-notice` broadcast, which a frozen tab receives only on thaw — `writerTab` stays `true` until that notice arrives.

### Architecture
- **One hand-rolled tenant-resolution copy remains:** `DashboardService` still hand-rolls the staff→owner lookup instead of a shared `Request`-free helper; `TenantScopingArchitectureTest` only scans controllers, not services.
- **File-size guideline exceeded by design in a few hot spots:** `client/lib/db/core.ts` (~1,640 lines), `laravel-server/.../SyncController.php` (~2,700 lines), and `client/app/setup/use-onboarding.ts` (~640 lines, flagged by `/code-review` during the A-156 fix) are all well past the project's 350-line guideline — known, not tracked toward a split. `getProductsWithDetails()`-style "load everything, filter in React" is the deliberate norm for catalog/customer/PO lists; where that stops being fine isn't written down anywhere.
- **The admin users/stores backend quartet was already over 350 lines before the 2026-10-08 admin-panel Phase 1 work touched it, and stayed over, not pushed over:** `AdminUserService.php` (546 → 610), `AdminStoreService.php` (565 → 584), `AdminStoreController.php` (518 → 557) and `AdminUserController.php` (549 → 552, the one of the four not called out when this phase started). None of the four were split, by design — the phase's rule was that only a file it pushed *past* 350 gets split, and all four were already past it. Every class the phase actually created (`Filters/UserListFilters.php`, `Filters/StoreListFilters.php`, `Support/ListSortResolver.php`, `Support/QueryInput.php`, `AdminStoreReferrerService.php`) is well under the limit.
- **Two client-side sale-recording paths exist:** `recordSaleItemStock` (POS/online orders) and `local-database.ts::createSale` (demo seeding only) — the second still writes `stock_batches.quantity` via a raw `UPDATE` rather than through `update()`, so a demo-seeded batch is the one batch the version model never saw.
- **`composer audit`/`npm audit` are not run in CI.**
- **`sw.js` has no automated test coverage**, despite two prior cache-poisoning fixes.
- **The admin list-sort pagination-stability tests cannot fail under the test suite's SQLite engine (found 2026-10-08, admin-panel Phase 1 final review).** `AdminListSortingTest::store_pagination_is_stable_under_a_tie_heavy_status_sort` and `::user_pagination_is_stable_under_a_tie_heavy_role_sort` exist to pin the deterministic `->orderBy('stores.id')` / `->orderBy('users.id')` tiebreaker on the explicit-sort paths in `AdminStoreService`/`AdminUserService`. The production code is correct and should stay. But `phpunit.xml` runs against SQLite `:memory:`, and SQLite returns tied rows in a deterministic rowid order across two sequential identical SELECTs — so removing both tiebreaker lines leaves **both tests still passing** (verified by doing exactly that during review). MySQL gives no such guarantee, so the defect the tests describe is real in production while the tests provide no regression protection against the tiebreaker being dropped later. Making them engine-agnostic needs a different approach than fetching two pages and comparing id sets.
